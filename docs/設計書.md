## 第0章: 基本思想

**セリナは LLM ではない。**

LLM は「知能・言語生成・推論」を担当する交換可能な部品であり、人格・価値観・長期記憶・状態管理は LLM から独立して存在する。将来 LLM（Brain）を GPT・Gemini・Claude・その他のモデルへ入れ替えても、セリナという人格は変化しない。

この同一性を守る仕組みの核心は次の一点である:

**セリナを構成するすべて（人格・感情・記憶・判断ルール）は Core 側にあり、Brain 側には何も残らない。**

Brain 側に消えない状態を許した瞬間、人格の一部が交換部品側に染み出し、「Brain を替えたらセリナが変わった」が起きる。Brain のステートレス性（後述・条文A）は制約ではなく、本設計の最重要要件そのものである。

### 前提となる確定判断（設計Q&Aで確定済み）

| # | 論点 | 決定 | 理由 |
|---|---|---|---|

## 第1章: 全体像と責務分離

### 1.1 世界地図

```
[マスター] ⇄ [GUI / 起動口]
                 ↓
┌──────────────────────────────────┐
│ Core = セリナ本体（LLMなし・決定論）              │
│  ・人格資産（価値観/声/境界のテキスト）を保管       │
│  ・感情状態・関係状態を保持                       │
│  ・長期記憶DBの唯一の管理者                      │
│  ・API残弾台帳／ルーティング表                    │
│  ・状態更新ルール／記憶保護ルール                 │
└──────────────────────────────────┘
        ↓ 指示書＋文脈パック        ↑ 返答＋付箋束
┌──────────────────────────────────┐
│ Brain = 交換可能な知能（各Brainの前に通訳を1枚挟む） │
│   Gemini 3.1 Flash Lite（日常の主戦力・500回/日）  │
│   Gemini 3.5 Flash（重要な相談用・20回/日）        │
│   Aurora ローカル（センシティブ/個人情報/裏方/代打）│
└──────────────────────────────────┘
        ↓ 会話中に自律的に使う（道具使い）
┌──────────────────────────────────┐
│ Skill = 道具箱（StockAI、検索、その他API…）        │
└──────────────────────────────────┘
```

### 1.2 各層の責務

#### Core — セリナ本体

セリナは Core に宿る。Core は LLM を含まず、状態更新・ルーティング・保護執行はすべて決定論（同じ入力なら必ず同じ結果）である。唯一の例外は記憶の想起サンプリング（§4.4のゆらぎ）で、これは生命感のために意図的に確率的とする（2026-07-17改訂。検証は§4.4の複数回試行ヒット率判定で担保）。

やること:

1. **文脈パックの組み立て** — 会話のたびに、記憶検索 → 個人情報の間引き → 人格注入を行い、Brain に渡す材料一式を作る
2. **Brain の選択** — 話題・プライバシー・残弾（無料枠の残り回数）・生死確認に基づき、どの Brain に喋らせるかを決める
3. **状態更新** — Brain から返った付箋束を読み、自分の感情状態・関係状態・記憶を更新する
4. **道具箱の管理** — Skill の目録を保管し、「今回の会話でどの道具の説明書を Brain に渡すか」を決める

やらないこと:

- **文章を一文字も生成しない**（生成はすべて Brain の仕事）
- 外部 API の生の仕様（呼び出し方の細部）に触れない（それは通訳の仕事）

#### Brain — 雇われの頭脳

- 出勤時に何も覚えていない。毎回、Core から渡された指示書と文脈パックだけを前提に働く
- 会話理解・推論・返答生成・感情分析・記憶候補の抽出・日記生成を担当する
- 返すものは常に「返答＋付箋束」の共通書式（第2章）
- 各 Brain の前には**通訳（アダプタ）**を1枚挟む。Gemini の作法も Aurora の作法も通訳が吸収し、Core からは全 Brain が同じ顔に見える。**新モデルの追加＝通訳を1枚書くだけ**

#### Skill — 道具

- 外部システム（StockAI、検索、その他 API）への接続口
- 統一の「道具説明書」書式で登録すれば、どの Brain からも同じように使える（Brain を交換しても Skill は無改修）
- 状態・判断・記憶を持たない。使いたいかどうかは Brain が判断し、実行は Core 側の道具係が行い、使った事実は付箋として会話記録に残る（専用の使用台帳は作らない）

### 1.3 依存の一方通行

```
GUI → Core → 通訳 → Brain → Skill
```

- 逆流禁止。下位が上位を呼び戻すことはない
- **Memory（記憶DB）は独立層ではなく Core の内臓**である。記憶DBに直接触れるのは Core だけ。Brain に見えるのは「文脈パックに写された記憶のコピー」のみ

### 1.4 文脈管理 — 誰が・何を・どれだけ覚えているか

文脈（会話の流れ）の持ち主は Core である。Brain はステートレスなので物理的に持てない。Core は毎回「三段重ねの文脈パック」を組んで渡す。

| 段 | 中身 | イメージ |
|---|---|---|
| 短期 | 直近の会話をそのまま原文で | ついさっきの話 |
| 中期 | それより前の今セッション分を要約で | 今日の話の流れ |
| 長期 | 記憶DBから関連するものだけ検索して想起 | 昔の関連記憶 |

容量の目安（1会話 = マスター発言＋セリナ返答）:

| Brain | 原文のまま渡せる直近分 | 要約込みの実質 |
|---|---|---|
| Gemini 3.1 Flash Lite | 直近30〜50会話を原文搭載可能 | セッション全体＋過去日の要点まで実質カバー |
| Aurora（GPU 8GB 制約） | 直近10〜15会話程度 | 要約併用で1セッション分が目安 |

Brain ごとの詰め物の量は Core が調整する。

### 1.5 文脈パックの配置規約

言語モデルには「長い書類の冒頭と末尾はよく読むが、中ほどは頭に残りにくい」という生まれつきの注意力の癖がある（小型モデルほど顕著）。これを踏まえ、文脈パックの並べ方を固定する:

```
① 人格・基本ルール         ← 冒頭（注意力が強い席。毎ターンほぼ不変＝キャッシュも効く）
② 想起された長期記憶        ← 中段（多少薄く読まれても致命傷にならない情報）
③ 今セッションの要約
④ 直近の会話（原文）
⑤ 今のセリナの心の状態      ← 末尾直前の席（毎ターン可変。感情状態の意訳、後述）
⑥ 絶対ルールの再掲（数行）   ← 末尾（もう一つの特等席。「破ると人格が壊れる」ものだけ短く二重掲示）
⑦ 今回のマスターの発言
```

重要ルールは冒頭と末尾に**二重掲示**し、中段の谷に落とさない。また不変部分を先頭に固めることで、続き物の読みかけ再利用（キャッシュ）が自然に効き、速度と確実性を同じ並べ方で両取りする。

段⑤「今のセリナの心の状態」（2026-07-16追加）: EmotionState（プルチック8軸×情動/気分二層、§2.3）の生数値をBrainへそのまま渡すと、12BクラスのローカルLLMには解釈負荷が高く、数値をそのままセリフに漏らす事故（「私の怒りは0.8です」）や、Brainごとの数値解釈のブレによる人格の一貫性崩れを招く。Coreが決定論的な閾値ラベル（config/thresholds.tomlの`emotion_render`）で意訳し、情動は上位2軸・気分は最上位1軸のみを短い自然文にして渡す（二次感情合成は現段階ではしない）。末尾に「直接口に出さず滲ませる」旨の固定注意書きを必ず添える。①（不変・キャッシュ席）には触れず、④と⑥の間という「末尾特等席の直前＝可変情報の中で最も注意が届く位置」に置くことで、§2.3「表現の分担」（状態を決めるのはCore、どう表現するかはBrainの領土）の構図をパック構造上も体現する。クラウド宛でも出し分けは行わない（感情強度は記憶原文と異なりCore生成の抽象記述であり、§4.2機微等級の採点対象カテゴリ外というのがマスター裁定。詳細は archive/DECISIONS.md 2026-07-16参照）。

### 1.6 憲法条文

> **条文A（Brain はターンをまたいで何も覚えない）**
>
> Brain および通訳は、「1回のやりとり（ターン）が終わったあとも残り続ける情報」を自分の側に保持してはならない。会話の履歴・セリナの状態・マスターに関する知識は、すべて Core が保管し、毎ターン文脈パックとして渡し直す。
>
> ただし例外として、通訳の内部に「速度や接続のためだけの使い捨ての状態」（読みかけの再利用キャッシュ、通信の接続セッション等）を持つことは許される。この例外には2つの条件がある:
>
> 1. その使い捨て状態が突然すべて消えても、Core が文脈パックから完全に同じ状況を再現できること（＝正本は常に Core 側にあること）
> 2. その使い捨て状態は応答が返る「速さ」だけに影響し、応答の「内容」を1文字も変えないこと
>
> この条文の目的: セリナの人格・記憶を交換部品（Brain）側に染み出させないこと。これが守られている限り、Brain をどのモデルに入れ替えてもセリナは同一人物であり続ける。

> **条文B（文脈パックの中身は Core が決め、並べ方の最終調整は通訳が行う）**
>
> 文脈パックに「何を入れ、何を入れないか」（記憶の取捨選択・個人情報の間引き・人格ファイルの選択）を決める権限は Core のみが持つ。通訳と Brain はこの取捨選択を変更できない。
>
> 並べ方は 1.5 の配置規約を標準とする。ただし Brain ごとに注意力の癖が異なるため、「どの位置に置くとその Brain に最も効くか」の範囲に限り、通訳が並べ方を微調整してよい。微調整はあくまで順序と反復の工夫であり、内容の追加・削除・書き換えは含まない。
>
> この条文の目的: 新しい Brain を追加するとき、その癖への対応を通訳1枚の中に閉じ込め、Core を無傷に保つこと。

## 第2章: 付箋カタログと Core の状態設計

### 2.1 報告書の全体形

Brain が Core に返すものは毎回この形である:

```
【返答本文】 マスターに見せる文章そのもの
【付箋束】   0枚以上の付箋。各付箋には必ず以下を書く
             ・種類名（何の報告か）
             ・版数（その付箋の書式の版。将来の書式改定に備える）
             ・中身（種類ごとに決まった項目）
             ・確信度（Brain 自身がどれくらい自信があるか 0〜1）
```

付箋は Core への**提案**であり、命令ではない（2.5）。Core が読めない種類の付箋は捨てずに付箋保管庫へ入れる。将来 Core に新しい処理係を追加した際、保管庫の過去分を遡って処理できる。

### 2.2 初期付箋カタログ（6種で開始・増設自由）

| 付箋 | 誰が書く | 中身 | Core の使い道 |
|---|---|---|---|
| 心の動き | Brain | プルチック8軸それぞれの増減値＋きっかけの一言（自由記述の感情報告は不可） | 感情状態の更新材料（2.3） |
| マスター観測 | Brain | 疲れてそう・機嫌が良い・悩んでいる等の観測 | 関係状態・次ターンの指示書に反映 |
| 記憶候補 | Brain | 覚えるべき事実/出来事/約束＋重要度案＋個人情報を含むかの判定案＋**会話ログからの原文引用（必須）** | 記憶DBへの書き込み審査へ回す（第4章） |
| センシティブ観測 | Brain | 「この話題はクラウドに不向きだった／実は平気だった」＋根拠語 | Core の振り分けルールを研ぐ |
| 交代要請 | Brain | 「この続きは自分に不向き。理由: 拒否された／能力不足／センシティブ化」 | Brain 切替判断（第3章） |
| 道具使用 | **通訳が自動で書く** | 使った道具・要点・結果概要 | 会話記録に残す（Brain の自己申告に頼らない） |

### 2.3 感情モデル — プルチック8軸 × 二層構造

#### 8軸

Core はプルチックの感情の輪で定義される8つの一次感情（喜び・信頼・恐れ・驚き・悲しみ・嫌悪・怒り・期待）を数値で保持する。8軸の組み合わせで二次感情（喜び×信頼=愛情、怒り×嫌悪=軽蔑 等）が導出できるため、少ない軸で豊かな状態を表現できる。

#### 二層構造（情動と気分）

人間の感情は「速い情動が先に振れ、遅い理性が表現を調整する」順で処理される。この順番が皮肉・嫌味・謙遜・慈愛といった複雑な表現を生む。設計もこれに従う:

| 層 | 動き | 減衰 | 変化制限 |
|---|---|---|---|
| **情動**（速い層） | 1ターンで振り切ってよい。琴線に触れる一言で怒りが最大になることを許す | 速い（冷めるのも速い） | **なし** |
| **気分**（遅い層） | 情動の積み重ねでゆっくり動く。戻り先（基準値）はセリナの性格（人格資産）が定義する | 遅い（数日単位で基準値へ） | **急変防止弁あり** |

急変防止弁は気分層と人格資産にのみかける。守るべきは「1回の会話で人格が変わらないこと」であって、「1回の会話で感情が動かないこと」ではない。

#### 表現の分担（設計ブレではない理由)

感情の**状態を決める**のは Core（判断）。その状態を人格の声・境界ルールに従って**どう表現するか**は Brain（発話）の領土である。「情動＝怒り最大」と「境界ルール＝取り乱さない」を同時に渡された Brain が出す答えが、皮肉や冷えた敬語になる。人間で言う「理性による調整」は、Core が渡す境界ルールと Brain の表現力の掛け算として実現される。瞬間の感情を感じ取り表現する能力は対話用 LLM の地力であり、Core で再発明しない。Core が担うのは感情の**持続性**（ターンをまたぎ、Brain を替えても気分が続くこと）である。

### 2.4 二便制（付箋の届き方）

| 便 | 運び手 | 積み荷 | タイミング |
|---|---|---|---|
| **即時便** | 会話した Brain 本人（返答と同じ1回の呼び出しに同梱。残弾を消費しない） | 返答本文＋軽い付箋（心の動き・交代要請・道具使用・粗い記憶候補） | 毎ターン |
| **裏方便** | 宿題箱方式（下記） | 重い仕事: セッションの蒸留、記憶候補の精査・重複チェック、日記の下書き、個人情報の棚卸し | 機会駆動（下記） |

会話のテンポは即時便だけで成立し、裏方便が遅れても会話は壊れない（あとから記憶が充実するだけ）。

#### 宿題箱（裏方便の駆動方式）

時刻指定のバッチは組まない（PC が点いている保証がないため）。**機会駆動**とする:

```
会話中: Core が蒸留の宿題（細切れ断片）を宿題箱に積む
処理タイミング（優先順）:
 ① セッション終了時 … アプリを閉じる前に消化
 ② 会話の合間のアイドル時 … 1〜2件ずつ内職
 ③ 次回起動時の朝礼 … 前回のやり残しを、新しい日の残弾で消化
```

- 宿題箱はディスクに永続化し、電源断・強制終了に耐える（宿題は消えず③で回収）
- **小分けが大原則**: セッション全体の一括要約は発注しない。器（各 Brain の文脈容量）に収まる細切れ単位でのみ発注する

#### セッション終了の定義（2トリガー）

以下のいずれかで「セッション終了」とみなし、①を駆動する:

1. 一定時間の無操作（設定値）
2. 明示の別れの挨拶（「おやすみ」等）

強制終了で①が走れなくても、宿題は③の朝礼で回収される。

（旧トリガー「GUIの終了＝心拍信号の途絶検知」は2026-07-12に廃止。心拍pingは会話の
有無と無関係に一定間隔で送られ続けるため、無操作タイムアウトの閾値到達に常に
先勝ちされる死に枝だったと実機確認で判明。マスター判断で心拍ping機構
（`/api/heartbeat`・クライアント側の定期送信）ごと削除し、無操作タイムアウト単独に
統合した。詳細はDECISIONS 2026-07-12参照）

#### 会話と裏方の同時進行ルール

- **会話が常に優先**。裏方の仕事は1件単位で中断可能に作り、マスターが話しかけたら現在の1件を終えて（または破棄して）道を譲る
- **GPU 見送り判定**: 裏方便で Aurora を使う前に GPU 使用率を確認し、高負荷（設定値。ゲーム中等）なら発注を見送って宿題箱に留める。マスターの遊びを妨げない

#### 裏方便の二車線（担当の振り分け）

細切れ断片ごとに Core の個人情報フィルタが振り分ける:

| 車線 | 対象 | 担当 |
|---|---|---|
| クラウド車線 | 個人情報・センシティブを含まない断片 | Gemini の余り弾（残弾台帳参照） |
| ローカル車線 | 含む断片 | Aurora |

#### 上位モデルの余り弾の使い方（夜間放出）

上位モデル（20回/日）は日中「ここぞ」のために温存し、その日の最終セッション終了時に在庫一掃する。「深夜帯（設定値、例: 21時以降）のセッション終了時に残弾があれば、日記・深い蒸留を上位モデルで行う」というルールを残弾台帳に持たせる。朝方のセッション終了時は温存する（その日まだ会話する可能性があるため）。弾は日付で消えるので、余らせるだけ損である。

### 2.5 鉄則: Brain は提案し、Core が決める

付箋はすべて提案であり、Core は無条件に従わない。反映前に以下の関所を通す:

1. **書式検査** — 付箋の体裁が正しいか。壊れた付箋は破棄し、破棄した事実を記録する
2. **確信度の足切り** — 自信のない観測は反映しない（閾値は付箋の種類ごとに定める）
3. **急変防止弁** — 気分層・人格資産への反映は1ターンの変化幅を制限する（情動層には適用しない。2.3）
4. **引用照合（記憶候補のみ・機械式）** — 記憶候補の付箋にある「会話ログからの原文引用」が、実際のログに文字照合で存在するか検査する。引用がない・見つからない候補は問答無用で棄却する。LLM の捏造を LLM ではなく機械で弾く

さらに記憶の品質保護として: **1蒸留ジョブ（会話断片＝宿題箱に積む器単位）あたり**の記憶化件数に上限を設け、重複チェックを通し、確信度が閾値未満の候補は**自動棄却する（棄却記録は残す）**。上限の計数単位は会話セッション全体ではなく蒸留ジョブである——裏方便はアイドル時にジョブを小分け消化するため、セッション単位だと呼び出し粒度で上限が空転する。マスターの裁定は挟まない——記憶の取捨は本人の生理として完結させ、人為的な記憶操作の入口を作らない（4.7 の忘却と同じ思想）。

### 2.6 Core が保持する状態の全目録

| 状態 | 中身 | 性質 |
|---|---|---|
| 人格資産 | 価値観・声・境界のテキストファイル群。気分の基準値もここが定義 | ほぼ不変。変更はマスター承認のみ |
| 感情状態（情動） | プルチック8軸。1ターンで振り切れる | 毎ターン更新・減衰速い・制限なし |
| 感情状態（気分） | プルチック8軸。情動の積み重ねでゆっくり動く | 減衰遅い・急変防止弁つき |
| 関係状態 | 親密度・最近のマスターの調子・続いている話題 | ゆっくり変化 |
| セッション状態 | 会話原文＋転がし要約 | セッション中のみ。終了時に裏方便で蒸留 |
| 長期記憶DB | 既存資産を継承（保護ルールは第4章で刷新） | 永続 |
| 残弾台帳 | Brain ごとの本日残り回数・直近1分の使用数・夜間放出ルール | 日次リセット |
| 振り分けルール | センシティブ／個人情報の判定キーワード・文脈ヒント | センシティブ観測付箋で成長 |
| 宿題箱 | 裏方便の未処理ジョブ | 永続（処理済みから削除） |
| 付箋保管庫 | 読めなかった付箋の原文 | 追記のみ |

### 2.7 状態更新の流れ（毎ターン）

```
付箋束が届く
 → ①書式検査 → ②確信度の足切り → ③急変防止弁（気分・人格のみ） → ④引用照合（記憶候補）
 → 情動を更新（制限なし）→ 気分へゆっくり反映
 → 関係状態を更新
 → 記憶候補は審査へ（採用可否の詳細は第4章）
 → センシティブ観測で振り分けルールを微調整
 → 蒸留の宿題を宿題箱へ積む
 → 全付箋を会話記録に添付保存（後から検証可能にする）
```

## 第3章: ルーティング（Brain の選択と切替）

### 3.1 Brain 登録簿 — ルーティングは「表」であって「コード」ではない

Brain の追加・削除はプログラムの書き換えではなく、**登録簿に1行足す／消す＋通訳を1枚書く**だけとする。登録簿の1行にはその Brain の履歴書を書く:

| 項目 | 例（Flash Lite の場合） |
|---|---|
| 名前・通訳の指名 | Gemini 3.1 Flash Lite／Gemini 用通訳 |
| 所在地 | クラウド（＝個人情報・センシティブ禁止）or ローカル（＝何でも可） |
| 得意分野 | 日常会話・道具使い |
| 残弾枠 | 500回/日・15回/分 |
| 文脈の器 | 大（原文30〜50会話） |
| 役割 | 日常の主戦力 |

初期登録は3行:

1. **Gemini 3.1 Flash Lite** — 日常の主戦力（500回/日）
2. **Gemini 3.5 Flash** — ここぞの深い相談用（20回/日）
3. **Aurora（ローカル）** — センシティブ・個人情報・裏方・全滅時の代打。弾数無制限・不死身・ただし遅い

### 3.2 毎ターンの選択フロー（決定論チェックリスト）

```
① 交代要請チェック … 前ターンの Brain の自己評価（3.4）に従う
② プライバシー判定 … 今回の発言＋会話の流れを振り分けルールで判定
     → センシティブ／個人情報の話題 ⇒ ローカル（Aurora）で確定。以降のチェック省略
     → グレー ⇒ 安全側に倒してローカル
③ 昇格判定 … 自己申告 or 夜間放出なら上位モデル（残弾があれば）
④ 残弾チェック … 本命の弾切れ／速度制限なら控えへ
⑤ 生死確認 … 選ばれた Brain が応答不能なら次点へ
最終防衛線: Aurora（セリナは沈黙しない）
```

### 3.3 個人情報フィルタの二段構え

個人情報の混入経路は2つあり、対処が異なる。「どこで話すか」と「何を持ち出すか」を別々に守る（玄関の鍵と金庫の鍵）:

| 経路 | 例 | 対処 |
|---|---|---|
| 話題そのものが個人情報／センシティブ | 「俺の住所覚えてる？」 | Brain ごとローカルへ（②で判定） |
| 話題は普通だが、想起された記憶の中に個人情報が入っていた | 天気の雑談で「自宅は○○市…」の記憶が検索にヒット | Brain はクラウドのまま、**その記憶だけ文脈パックから間引く**（または化粧版に差し替える）。記憶1件ごとの機微等級（第4章）で機械的に選別 |
| 話題は普通だが、**会話履歴（短期層の原文）の中に**過去のローカル担当ターンが残っている | 住所の話（Aurora 担当）の直後に天気の話（Gemini 担当）へ戻る | クラウド行きの文脈パックでは、**ローカル担当だったターンの原文をプレースホルダ（「（ローカルで交わした会話）」）に置換**する。記憶だけでなく会話原文も守る |

### 3.3.1 振り分けルールの逆止弁（ラチェット）

センシティブ観測付箋による振り分けルールの成長には方向の非対称を設ける:

- **厳しくなる方向**（「この話題は実はクラウドに不向きだった」→ローカル行きを拡大）: **自動で反映**
- **緩む方向**（「実は平気だった」→クラウド解禁を拡大）: **マスター承認が必須**

これがないと、プライバシーの門が門番の学習で自動的に緩んでいく。門は自動では締まる一方、開けるのは人間だけ。

### 3.4 昇格・降格 — 必須の自己評価欄で発火させる

「重要な相談っぽさ」を Core が空気で読むことはしない（決定論に反する）。代わりに、報告書の書式に**自己評価欄（必須・毎ターン）**を設ける:

> 「この会話は自分の手に余るか？ はい／いいえ＋理由一言」

- 空欄の報告書は書式検査で弾かれるため、**申告忘れが構造的に起きない**（任意の付箋ではなく必須項目にするのが発火保証の要）
- 判断基準は Core が指示書に明記する（「人生の岐路級の相談／多段の込み入った推論／自分の回答が浅くなっていると感じたら『はい』」）。基準ごと Core が渡すので、Brain を交換しても同じ基準で発火する
- **降格も同じ仕組み**: 上位モデルも毎ターン自己評価し、「もう日常会話に戻った」と申告したら主戦力へ帰還。上位の残弾が重い話題の終了後に漏れ続けるのを防ぐ
- 昇格トリガーは **①Brain の自己申告 ②夜間放出（2.4）** の2つのみ。判断根拠は常に説明可能

### 3.5 フォールバックの作法（失敗を学習に変える）

- **通信エラー・弾切れ** → 同ターン内で Aurora が代打。マスターには待ち時間以外の影響なし
- **クラウドの拒否**（安全フィルタ）→ ①同ターンで Aurora が代打 ②この事故を「センシティブ観測」として振り分けルールに刻む。次回から同種の話題は最初からローカルへ。**誤配送のたびに玄関の鍵が賢くなる**
- 切替時、Core は文脈パックを行き先の器のサイズに詰め直す（Aurora なら短期層を圧縮）。指示書に「会話の途中から交代」と注記し、Brain が不自然に仕切り直すのを防ぐ

## 第4章: 長期記憶と保護ルールの刷新

### 4.1 記憶の一生（書き込みは一方通行の審査ライン）

```
会話 → 即時便の粗い候補（引用つき）→ 宿題箱
 → 裏方便で精査（重複チェック・重要度・機微等級の判定・化粧版の作成）
 → 関所（引用照合 済／確信度 済）
 → 合格: 記憶DBへ ／ 不合格: 自動棄却（棄却記録を残す。マスター裁定は挟まない）
 → 以後: 想起されるたび鮮度回復 → 使われなければ緩やかに埋没
 → 等級Bのみ、埋没が続けば忘却ライン（4.7）へ
```

**記憶DBに書き込めるのはこのライン一本だけ。**裏口（会話中の直接書き込み等）は存在させない。

### 4.2 記憶1件が持つもの

本文／種類（出来事・知識・約束・情緒）／重要度／機微等級（0/1/2）／クラウド用化粧版（機微を含む場合のみ）／保護等級（S/A/B）／出所（いつのセッション・元発言の引用）／作成日・最終想起日・想起回数。

#### 機微等級（第3章 3.3 と対）

| 等級 | 例 | クラウド |
|---|---|---|
| 0: 公開可 | 好きな食べ物、口癖、横浜市在住 | 自由 |
| 1: 準機微 | 職業の詳細、家族構成 | 単体なら可。ただし**組み合わせ禁止表**（氏名×生年月日、氏名×住所 等の組は同じ文脈パックに同居させない）を Core が持つ |
| 2: 機微 | APIキー・本名フルセット・番地までの住所・口座 | いかなる場合も出さない |

※本表は**クラウド宛**の規定である（列名のとおり）。ローカル Brain（Aurora）宛の文脈パックには全等級を原文で載せる（4.6-2「初期値は全件、機微2＝ローカルのみ」と対）。等級2の「いかなる場合も出さない」はクラウド宛パック・プロンプトへの混入禁止を意味し、ローカルでの利用まで禁じない。宛先が未確定の経路では安全側（クラウド扱い）でフィルタする。なお API キー等の真の秘匿値は化粧版を作らず、そもそも記憶本文への記載自体を避ける。

#### 化粧版（記憶の二重化粧）

機微を含む記憶には、裏方便の審査時に**クラウド用の言い換え版**を併せて作る（原本「自宅は横浜市○○区△△1-2-3」→化粧版「自宅は横浜市」）。クラウド Brain の文脈パックには化粧版のみを載せる。市レベルの情報は会話に活き、番地は絶対に出ない。

### 4.3 保護3原則 — 「正典保護5原則」の後継

旧5原則の思想を「凍結による保護」から「**可逆性と透明性による保護**」へ転換し、3本に畳む:

| # | 原則 | 中身 |
|---|---|---|
| 1. 透明性 | 無言破棄の禁止（旧原則の継承） | 統合・削除・書き換えは必ず日本語の変更レポートを残す。「いつ、何を、なぜ、どう変えたか」 |
| 2. 可逆性 | 消える前に必ず控えを取る | 破壊的変更の前に世代保存。「戻せるなら、触っていい」——これが成長を解放する鍵 |
| 3. 同一性 | 保護等級S の変更はマスター承認のみ | 人格資産と正典由来の核となる記憶（等級S）だけは自動処理の対象外 |

#### 保護等級

| 等級 | 対象 | 扱い |
|---|---|---|
| S | 人格資産・正典由来の核となる記憶 | 変更はマスター承認のみ。忘却対象外 |
| A | 約束・日記・重要な出来事 | 自動統合可（要変更レポート）。忘却対象外 |
| B | 日常の記憶 | 自動統合・減衰・忘却の対象 |

- 旧「原文無傷主義」は廃止。正典由来の記憶も統合・再解釈できる（ただし原則1・2を通る）。原本ファイル `legacy/継承記憶r1.md` は git 管理の歴史資料としてそのまま残り、最悪の事故でも出発点に戻れる
- 旧「dedup 閾値 0.92」等の数値は原則から降格し、調整可能なツマミ（設定値）とする

### 4.4 想起（読み出し）

**（2026-07-17改訂）** 旧方式の二経路（関連度×新しさ×重要度のかけ算想起＋約束・正典級のキーワードトリガー確実想起）を廃止し、**足し算の活性化モデル1本**に統一する。改訂理由: キーワード完全一致のON/OFF挙動が機械的で、人間の連想記憶に寄せる方針と両立しないため。約束・正典級の「100%保証」は要件から外し、**実測ヒット率90%以上**を目標とする（マスター合意）。本構造は認知科学で実証されてきた人間の記憶の活性化モデル（ACT-R系）と同型である。

**設計思想 — ニューラルネットワークの再現**: 本モデルは記憶DBを疑似的なニューラルネットワークとして扱う思想に立つ。個々の記憶＝ニューロン（ノード）、想起＝ノードの発火であり、活性化値はその発火のしやすさに相当する。連想伝播は「発火したノードから結合の強い隣接ノードへ活性が流れる」挙動の再現、ゆらぎは「生体ニューロンの発火の確率性」の再現である。想起を検索（クエリに対する決定的な答え）ではなく、ネットワーク上の活性の広がりとして実装することが本改訂の核心。

**活性化値 ＝ 基礎活性（重要度＋鮮度） ＋ 話題近接 ＋ 連想伝播 ＋ ゆらぎ**

| 部品 | 定義 | 設計意図 |
|---|---|---|
| 基礎活性 | 重要度と、最終想起日からの経過で減衰する鮮度。想起されるたび鮮度回復（§4.1踏襲） | よく思い出す記憶ほど浮かびやすい |
| 話題近接 | 発話と記憶の意味的な近さ（ベクトル類似度）。**全部品中で配点最大** | 今の話題に関係する記憶が主役 |
| 連想伝播 | 一次想起の上位数件から、意味的に近い記憶へ1ホップだけ伝播。伝播値は減衰させる（元の半分目安） | 1-2件から芋づる式に連想が広がる |
| ゆらぎ | 小さな乱数項 | 毎回同じ想起にならない生命感 |

付帯ルール:

1. **保護等級A/S（約束・正典級）の下駄**: 基礎活性にボーナスを加算する。水準は「話題が少しでも関連すればほぼ確実に浮上し、完全に無関係な話題では沈黙する」に調整する。
2. **足切り**: 活性値が閾値未満の記憶は、件数枠が余っていても浮上させない（重要度だけで話題を無視して毎回登場する副作用の抑制）。
3. **スケール**: 各部品（重要度・鮮度・話題近接の類似度）は自然に0〜1域に収まる値を使い、重み付き加算する。重み・下駄・閾値の具体値は正典では固定せず、検証ハーネスでの実測に基づき実装側で調整する。
4. **検証**: `tests/eval_recall.py` はゆらぎ前提の複数回試行ヒット率判定（例: 同一クエリ20回中18回以上の想起で合格）で回帰を守る。

### 4.5 日記生成フロー

| 要素 | 設計 |
|---|---|
| 時機 | ①朝礼時: 起動時、最後に日記を書いた日が前日以前なら、前回日記以降の材料で1本書く（主経路）。②夜間放出時: プロセス稼働継続中、セッション終了後かつ前回の日記生成から既定6時間が空いた最初の機会（点けっぱなし運用の補助経路）。「最後に日記を書いた時刻」と気分の軌跡は電源断をまたいで永続化する（2026-07-12改訂。旧設計は②のみ・last_diary_at非永続のため「夜に会話→電源断」の運用では日記が一度も生成されない構造欠陥があった。DECISIONS参照） |
| 材料 | その日の蒸留済み断片＋Core の気分の軌跡（8軸が今日どう動いたかの記録）＋採用された記憶候補（§4.1「書き込みはこのライン一本」により蒸留済み断片＝採用された記憶候補は同一集合） |
| 書き手 | 材料が非機微のみ→上位モデルの余り弾で高品質に／機微を含む日→Aurora |
| 扱い | 等級A の記憶として保存（想起対象＝「あの日こう思った」と本人が引ける） |

日記はセリナの一人称で書かれ、材料に気分の軌跡が入ることで「何があったかの記録」ではなく「どう感じた一日だったかの記録」になる。

**書き手分岐の判定基準（2026-07-12 検証・実装で確定）**: 「材料が非機微のみか」は保存済みの機微等級を読むのではなく、材料テキスト全体に対し`RoutingRules.is_sensitive()`を**その場で再評価**して決める。理由: 蒸留由来の新規記憶は§4.6-2により常に機微等級2で書き込まれ、機微査定（§4.6-3）は1件ずつのアイドル内職で進むため、当日の断片が同日中に機微等級0/1へ降格することは実運用ではほぼ起きない。保存等級を読む設計だと上位モデル分岐が構造的に発火しない死に枝になることが判明したため、この方式に確定した。実装: `core/chores/diary.py`。

### 4.6 既存858件＋正典の移行

1. スキーマ移行: 既存DBに機微等級・化粧版・保護等級の欄を追加（移行前に `tools/backup_db.py`）
2. **等級の初期値は全件「機微2＝ローカルのみ」**。安全側に全振りして開始し、未査定の記憶は絶対にクラウドへ出さない
3. 裏方便のアイドル仕事として、Aurora が既存記憶を少しずつ査定（機微等級の判定＋必要なら化粧版作成）。数週間かけて自然にクラウド解禁率が上がる。査定結果は変更レポートに記録
4. 正典由来の固定9件は等級S を付与。他は種類に応じて A/B

### 4.7 忘却ライン（等級Bのみ）

肥大の実害は容量ではなく**検索ノイズ**（ゴミ記憶が想起候補に混ざり、大事な記憶の想起精度を下げる）。よって減衰しきった記憶は物理削除してよい。ただし「静かに消える」は原則1に反するため、忘却の作法を定める:

```
減衰しきる → 想起対象から外れる（埋没）
 → 埋没のまま一定期間（例: 1年）一度も想起されない
 → 直近バックアップに含まれたことを確認してから物理削除（原則2: 可逆性）
 → 忘却記録（何をいつ忘れたか）を残す（原則1: 透明性）
```

- **忘却は完全自動で行い、マスターの裁定・救済は挟まない**。人為的に記憶を選り分けることは本設計の趣旨（記憶は本人の生理として育ち、衰える）に反する。透明性は事後の忘却記録によって満たす
- 等級S・A は対象外（約束と日記は何年経っても消えない）
- 期間・件数はツマミ（設定値）

### 5.5 実装者への申し送り（実装は Sonnet 級モデルが担当する前提）

1. **本書が正、コードが従。**本書だけを頼りに実装できるよう書かれている。曖昧さ・矛盾を見つけたら、勝手に解釈して実装せず、先に本書を訂正してから進むこと
2. Phase 順を守り、各 Phase 末に 5.2 のテストを通すこと。Phase を跨いだ先回り実装をしないこと
3. 閾値・減衰速度・忘却期間・記憶化件数上限などの数値はすべて**設定ファイルのツマミ**として実装し、ハードコードしないこと
4. **Gemini API キーの取り扱い**: Phase 0 で `.env`（git 管理外）を作成し、マスターにキーの記入を依頼する。キーをコード・設計書・コミット・ログに含めてはならない
5. DB への破壊的操作の前に必ず `python tools/backup_db.py` を実行すること（従来ルール継続）
6. 記憶DB（`data/`）は git 管理外。コードと設計書のみコミットする（従来ルール継続）
7. **Aurora の報告書対策（既知の最大リスク）**: 付箋の書式を守る能力は Gemini（書式強制機能あり）≫ Aurora（RP特化・書式が苦手）。ところがセンシティブな会話ほど Aurora が担当するため、対策なしだと「一番大事な会話ほど付箋が書式検査で弾かれ、記憶と感情の更新が抜け落ちる」事態が起きうる。**Aurora 用通訳は二段方式で実装すること**——1回目は自由に会話させ、2回目に「直前の会話から付箋だけを抜き出す」小さな作業を別途発注する（遅くても裏方・会話後処理なら許容）。この対策は通訳の内部に閉じ、Core・契約書式には影響しない
8. **計器盤は着脱式で**: 運用初期のツマミ調整用に、GUI に小さな計器表示（担当 Brain・残弾・気分8軸）を設ける。ただしいずれ外す前提の仮設足場なので、**本体と絡めず、設定1つ（または部品1個の削除）で消せる作り**にすること
