# Serina 憲章（Architecture Reviewer 測定器）

## 概要

憲章とは、`設計書.md` §1〜§4 に固定された構造・責務・判断基準を、**Architecture Reviewer が変更（diff）の適合／逸脱を機械的に判定するための「測定器」**に変換したものである。

- 位置づけ
  - 原典は `設計書.md`（§1〜§4。発火条件の運用注記のみ周辺節を参照可）。本書はその判定基準だけを抜き出し、各原則に「違反の兆候」を付与したもの。
  - 本書は**判定に使う定規**であって、新しい設計思想を発明・追加する場ではない。
- 前提・制約
  - Architecture Reviewer は本書の条文**のみ**を基準に判定する（教科書的な AI エージェント論の一般語彙は持ち込まない）。
  - 条文の追加・変更・削除の権限は**マスターのみ**。番人（Reviewer）は条文を増減できない。
  - 憲章を更新する場合は、先に `設計書.md` を改訂し、その差分を本書へ反映する（原典が正、本書が従）。

---

## 対象レイヤー定義（Serina の実体）

Reviewer が扱う層名は、以下に固定する。一般語彙（Reasoning / Retrieval / Working Memory / Episodic / User Model / Tool Layer 等）および**旧6層名**（Prompt / Memory 独立層 / Connectors / External Services）は使用しない。

| 記号 | レイヤー | 一言責務 | 原典 |
|---|---|---|---|
| C | Core | セリナ本体。決定論。人格・状態・記憶・ルーティングの管理者 | §1.1〜1.2 |
| Br | Brain | 交換可能な知能。生成・推論・抽出 | §1.1〜1.2 |
| Ad | 通訳（アダプタ） | Brain 固有の作法を吸収し、Core から見た顔を揃える | §1.2 |
| S | Skill | 道具。外部システムへの接続口 | §1.1〜1.2 |

- **Memory（記憶DB）は独立層ではない。** Core の内臓であり、層名として Memory を立てない（§1.3）。
- **人格資産（価値観・声・境界）は Core が保管するテキスト**であり、旧 Prompt 層のような独立レイヤー名は使わない（§1.2 / §2.6）。

## 憲章条文（測定器本体）

各条文は「ID／規範（守るべきこと）／違反の兆候（これが起きたら逸脱）」の3点で構成する。Reviewer は差分がどの条文の違反兆候に該当するかで判定する。

### A. 責務配置（各層は自分の仕事しかしない）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| A-C1 | Core は文脈パックの組み立て・Brain の選択・状態更新・道具箱の管理だけを行う（§1.2） | Core が実処理（専門計算・外部呼び出しの中身・文章生成）を持ち始める |
| A-C2 | Core は文章を一文字も生成しない。外部 API の生の仕様（呼び出し方の細部）に触れない（§1.2） | Core が返答本文を生成する／外部 API の引数・エンドポイントを直接組み立てる |
| A-C3 | セリナを構成するすべて（人格・感情・記憶・判断ルール）は Core 側にあり、Brain 側に消えない状態を残さない（第0章／§1.2） | 人格・長期記憶・判断ルールの正本が Brain または通訳の永続状態に染み出す |
| A-Br1 | Brain は会話理解・推論・返答生成・感情分析・記憶候補の抽出・日記生成を担当する（§1.2） | Brain が Core の状態更新ルール・ルーティング決定・記憶DB直接操作を抱え込む |
| A-Br2 | Brain が返すものは常に「返答＋付箋束」。付箋は Core への提案であり命令ではない（§2.1／§2.5） | Brain／通訳の出力を無条件で状態や記憶に反映する経路がある（関所を迂回） |
| A-Ad1 | 各 Brain の前に通訳を1枚挟む。新モデル追加＝通訳を1枚書くだけ（§1.2） | 新 Brain 追加のたびに Core の本体ロジック改修が必須になる |
| A-Ad2 | 文脈パックの取捨選択権限は Core のみ。通訳の微調整は順序と反復に限り、内容の追加・削除・書き換えは含まない（§1.6 条文B） | 通訳が記憶の間引き・人格選択・個人情報フィルタ結果を独自に変更する |
| A-S1 | Skill は状態・判断・記憶を持たない。使いたいかは Brain が判断し、実行は Core 側の道具係が行う（§1.2） | Skill が「やる／やらない」を決め、記憶を持ち、Core を経由せず処理方針を決める |

### B. 依存方向・結合（流れは一方向、逆流禁止）

正規の依存方向：**GUI → Core → 通訳 → Brain → Skill**（§1.3）。

| ID | 規範 | 違反の兆候 |
|---|---|---|
| B-1 | 依存は上記の一方向のみ。逆流禁止。下位が上位を呼び戻すことはない（§1.3） | Brain／Skill／通訳が Core を呼び戻す、または下位が上位の制御フローを握る |
| B-2 | 記憶DBに直接触れるのは Core だけ。Brain に見えるのは文脈パックに写された記憶のコピーのみ（§1.3） | Brain／通訳／Skill から記憶DBへ直接 read/write する |
| B-3 | Brain の差し替えは通訳に閉じ込め、Core を無傷に保つ（§1.6 条文B の目的） | 1つの Brain／LLM 交換が、Core や他 Brain の広範なコード変更を強制する |
| B-4 | Skill は統一の道具説明書書式で登録し、Brain を交換しても Skill は無改修（§1.2） | 特定 Brain 専用の呼び出し方を Skill 本体に焼き込み、Brain 交換で Skill 改修が必須になる |

### C. Brain 憲法（ステートレスと提案／決定の分離）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| C-1 | Brain および通訳は、ターンをまたいで残り続ける情報を自分の側に保持しない。正本は常に Core。ただし**通訳の内部**に限り、**速度・接続のためだけ**の使い捨て状態を持てる。条件は①その状態が消えても Core が文脈パックから完全に同じ状況を再現できる ②応答の内容を1文字も変えない（§1.6 条文A） | 会話履歴・セリナ状態・マスター知識が Brain／通訳側に永続する／Brain 側に使い捨て状態を置く／通訳のキャッシュが応答内容を変える |
| C-2 | 文脈パックに何を入れ何を入れないかは Core のみが決める。通訳・Brain はこの取捨を変更できない（§1.6 条文B） | Brain／通訳が文脈パックの内容を独自に追加・削除・書き換える |
| C-3 | 付箋は提案であり、Core は関所（書式・確信度・急変防止弁・引用照合等）を通してから反映する（§2.5） | 付箋内容が無検証で状態・記憶に直結する |
| C-4 | 感情の状態を決めるのは Core。どう表現するかは Brain の領土。Core は感情の持続性を担い、瞬間の表現能力を Core で再発明しない（§2.3） | Core が発話文を生成して感情表現を内製する／Brain が Core の感情状態そのものを永続改変する |

### D. Skill／外部原則（専門機能は道具として呼ぶ）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| D-1 | 外部システム（StockAI・検索・その他 API）への接続は Skill として登録し、Core／Brain 内に専門処理の本体を内製しない（§1.1／§1.2） | 株分析・検索等の専門処理の本体が Core または Brain 側に実装され、Skill（道具説明書）経由の呼び出しでなくなる |
| D-2 | 使った事実は付箋として会話記録に残す。専用の使用台帳は作らない（§1.2） | Skill 使用の正本が会話記録と別系統の台帳に分岐し、検証不能になる |

### E. 記憶原則（書き込み経路と保護）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| E-1 | 記憶DBへの書き込みは審査ライン一本だけ。裏口（会話中の直接書き込み等）は存在させない（§4.1） | 即時便や会話経路から関所を迂回して記憶DBへ書き込む |
| E-2 | 保護3原則（透明性・可逆性・同一性）を維持する（§4.3） | 統合・削除・書き換えが日本語の変更レポートなし／控えなしで実行される。保護等級 S が自動処理される |
| E-3 | 記憶候補の採否は Core の生理として完結させる。マスターの裁定は挟まない。1蒸留ジョブあたりの件数上限・重複チェック・確信度足切りで自動棄却し、棄却記録を残す（§2.5／§4.1） | 記憶の取捨に人為的な裁定入口を作る／棄却を無言で行う／上限の計数単位を会話セッション全体に戻して空転させる |
| E-4 | センシティブ・個人情報はクラウドに送らない。機微等級2はクラウド宛の文脈パック／プロンプトに載せない。グレーは安全側（ローカル）に倒す。宛先未確定の経路も安全側（クラウド扱い）でフィルタする（第0章 確定判断#2／§3.3／§4.2） | 機微等級2やセンシティブ内容がクラウド行きの文脈パックに混入する／グレーをクラウド側に倒す |

---

## 判定の3観点（3本の定規）

Reviewer は下記3観点で判定する。各観点は上の条文群に対応する。

1. 観点1：責務配置
   - 対応条文：A 群
   - 問い：この処理は「正しい層」に置かれているか
2. 観点2：依存・結合
   - 対応条文：B 群
   - 問い：依存は一方向か。Brain／記憶の差し替えや境界が他層に波及しないか
3. 観点3：憲章違反（Brain 憲法／Skill／記憶）
   - 対応条文：C・D・E 群
   - 問い：Brain への染み出し・関所迂回・専門機能の内製化・記憶保護の破壊が起きていないか

## レビュー発火条件（毎コミットでは回さない）

Architecture Reviewer は**構造に触れる変更のときだけ**発火する。実装の細部だけの変更では起動しない。

- 発火する（必須）
  - 新レイヤー／新モジュールの追加
  - 層をまたぐ依存の追加・変更（import 関係の変化）
  - Brain の追加・削除、通訳の追加・供給配線の変更、登録簿の構造変更
  - 人格資産の置き場所・Core からの供給配線の変更
  - 記憶のスキーマ・保存先・保護ロジック・書き込み経路の変更
  - Skill（道具箱）の契約・登録構造の変更
- 発火しない（任意）
  - 単一層の内部実装のみの変更（関数リファクタ・命名・バグ修正）
  - テスト・ドキュメントのみの変更
  - 閾値・残弾枠などツマミ値のみの変更（条文の規範を変えない範囲）

※ 構造変更時は **architecture-reviewer** を先に通し、PASS 後に実装。作業完了時は `completion-review` → `serina-code-reviewer`（Claude / Cursor 共通の唯一入口）。完了時レビューの「構造ゲート証跡」も本節の発火条件リストのみを用い、独自の構造定義を増やさない。

## 番人の禁則（Reviewer 自身のドリフト防止）

| 禁則 | 内容 |
|---|---|
| 禁則1 | 番人は憲章の「違反」を指摘してよいが、憲章の「内容」を批判してはならない |
| 禁則2 | 憲章条文の追加・変更・削除はマスターのみ。番人は定規を増やせない |
| 禁則3 | 「最新技術だから正しい」で判定してはならない。基準は本書の条文のみ |
| 禁則4 | 一般語彙および旧6層名で監査してはならない。層名は本書の Core／Brain／通訳／Skill に固定 |
| 禁則5 | コード・ライブラリ・実装手段を提案してはならない。改善案は「思想的にどの層へ置くべきか」までに留める |

## 出力形式（Reviewer の返却フォーマット）

```
総合評価: PASS / WARNING / FAIL
違反条文: （該当する条文ID。例: A-C2, E-1）
発生層:   （どの層で起きたか。例: Brain → Core への責務越境）
観点:     （観点1〜3のどれか）
懸念点:   （思想レベルの説明。コード・ライブラリ名は書かない）
改善案:   （どの層へ置き直すべきか、という思想レベルの方向のみ）
```

- PASS：どの条文の違反兆候にも該当しない
- WARNING：違反の兆候はあるが、設計書または DECISIONS で明示済みの移行状態・暫定として許容余地がある
- FAIL：条文に明確に違反し、放置すると設計思想が崩れる
