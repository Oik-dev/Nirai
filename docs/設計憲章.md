# Serina 設計憲章（Architecture Reviewer 測定器）

## 概要

設計憲章とは、`設計書.md` §1〜§5 に固定された構造・責務・判断基準を、**Architecture Reviewer が変更（diff）の適合／逸脱を機械的に判定するための「測定器」**に変換したものである。

- 位置づけ
  - 原典は `設計書.md`（§1〜§5）。本書はその判定基準だけを抜き出し、各原則に「違反の兆候」を付与したもの。
  - 本書は**判定に使う定規**であって、新しい設計思想を発明・追加する場ではない。
- 前提・制約
  - Architecture Reviewer は本書の条文**のみ**を基準に判定する（教科書的なAIエージェント論の一般語彙は持ち込まない）。
  - 条文の追加・変更・削除の権限は**マスターのみ**。番人（Reviewer）は条文を増減できない。
  - 憲章を更新する場合は、先に `設計書.md` を改訂し、その差分を本書へ反映する（原典が正、本書が従）。

---

## 対象レイヤー定義（Serina の実体）

Reviewer が扱う層名は、以下の6つに固定する。一般語彙（Reasoning / Retrieval / Working Memory / Episodic / User Model / Tool Layer 等）は使用しない。

| 記号 | レイヤー | 一言責務 | 原典 |
|---|---|---|---|
| C | Core（司令塔） | 決めるだけ | §3, §5 |
| P | Prompt（人格・原則層） | 価値観を判断へ供給／口調にするだけ | §3, §5 |
| M | Memory（記憶層） | 覚えるだけ（CRUD＋検索のみ） | §3, §5 |
| S | Skills（能力層） | やるだけ | §3, §5 |
| N | Connectors（外部境界層） | 繋ぐだけ | §3, §5 |
| X | External Services（専門AI群） | 呼び出されるだけ | §3, §5 |

- P（Prompt）は内部で2責務に分かれる
  - P-CV：Core Values（価値観・判断原則）→ 判断（Decision）へ供給（`prompt/core_values.md`）
  - P-VS：Voice Style（応答スタイル・口調）→ 発話（Voice）へ供給（`prompt/voice_style.md` ＋ `prompt/boundary.md`）

## 憲章条文（測定器本体）

各条文は「ID／規範（守るべきこと）／違反の兆候（これが起きたら逸脱）」の3点で構成する。Reviewer は差分がどの条文の違反兆候に該当するかで判定する。

### A. 責務配置（各層は自分の仕事しかしない）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| A-C1 | Core は「入力理解・タスク分解・Skill選択・フロー決定・結果統合」だけを行う | Core が実処理（計算・整形・外部呼び出しの中身）を持ち始める |
| A-C2 | Core は Connector を直接制御せず、外部API仕様を直接扱わない | Core から外部APIの引数・エンドポイントを直接組み立てている |
| A-P1 | Prompt は実行ロジックを持たない | 人格ファイル内に処理分岐・アルゴリズムが記述される |
| A-P2 | Prompt は個別データ（事実記憶）を持たない | 人格ファイルにユーザー固有の事実・履歴が直書きされる |
| A-M1 | Memory は CRUD と検索のみを提供する | Memory 層が「何を覚えるか・いつ整理するか」を判断し始める（＝ Core の責務を奪う） |
| A-M2 | Memory は実行処理・人格定義を持たない | Memory 層に人格・口調・タスク実行ロジックが混入する |
| A-S1 | Skills はタスク実行ロジックだけを持つ | Skill が判断（何をするかの決定）を抱え込み、Core を経由せず処理方針を決める |
| A-N1 | Connectors はビジネスロジック・判断処理を持たない | Connector が条件分岐で「やる／やらない」を決める、結果を加工して意味づけする |

### B. 依存方向・結合（流れは一方向、逆流禁止）

正規の依存方向：**Core → Skills → Connectors → External。Memory / Prompt は参照のみ。**

| ID | 規範 | 違反の兆候 |
|---|---|---|
| B-1 | 依存は上記の一方向のみ。逆流禁止 | 下位層（Connector/Skill）が上位層（Core）を呼び戻す |
| B-2 | Skills は他 Skill を直接呼ばない | Skill が別 Skill を直接 import／呼び出す（Core を介さない横結合） |
| B-3 | Skills は外部APIを直接扱わない（Connector 経由のみ） | Skill から外部サービス・DB・ファイルへ直接アクセスする |
| B-4 | Memory / Prompt は参照専用で、上位へ制御を返さない | Memory / Prompt が処理フローを分岐させる・上位へ命令する |
| B-5 | 層の差し替えは他層に波及しない（疎結合） | 1層（LLM・Vector DB・Embedding 等）の交換が、他層のコード変更を強制する |

### C. Voice 憲法（発話は意味を書き換えない）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| C-1 | Voice(P-VS) は Decision と Action Result を入力に、意味を変えず自然言語化する | Voice が判断結果や事実を言い換えの範囲を超えて改変する（結論・数値・可否の反転／捏造） |
| C-2 | 言い換え・口調付けは可、意味の改変は不可 | 「口調調整」の名目で、Decision が下した判断内容そのものを変える |
| C-3 | 判断（何をするか）は Voice 側で変更できない | Voice 層に判断ロジック（検索要否・事実採否など）が持ち込まれる |

### D. 外部サービス原則（専門機能は内部に作らない）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| D-1 | 高度専門処理（株分析・コード解析・検索・自動化 等）は Serina 内部に実装しない | 専門処理のロジック本体が Skills / Core 内に実装される |
| D-2 | Serina は External Service を「呼び出すだけ」 | External を呼ぶのではなく、その機能を内製で再現し始める |

### E. Memory 設計原則（移植可能な単一ファイル）

| ID | 規範 | 違反の兆候 |
|---|---|---|
| E-1 | 記憶は単一ファイルで永続化し、移植可能性を優先する | 記憶が複数ストア・外部依存サービスに分散し、単体で持ち出せなくなる |
| E-2 | 正典保護5原則を維持する（原文保持・上書き禁止・無言破棄禁止 等） | 統合・削除が日本語レポートなしで実行される／正典が他ソースで上書きされる |

## 判定の3観点（9観点ではなく3本の定規）

Reviewer は下記3観点で判定する。各観点は上の条文群に対応する。

1. 観点1：責務配置
   - 対応条文：A 群
   - 問い：この処理は「正しい層」に置かれているか
2. 観点2：依存・結合
   - 対応条文：B 群
   - 問い：依存は一方向か。1層の差し替えが他層に波及しないか
3. 観点3：憲章違反（Voice／外部サービス／記憶）
   - 対応条文：C・D・E 群
   - 問い：意味の書き換え・内製化・正典破壊が起きていないか

## レビュー発火条件（毎コミットでは回さない）

Architecture Reviewer は**構造に触れる変更のときだけ**発火する。実装の細部だけの変更では起動しない。

- 発火する（必須）
  - 新レイヤー／新モジュールの追加
  - 層をまたぐ依存の追加・変更（import 関係の変化）
  - Prompt の分割・供給先変更（判断／発話の配線変更）
  - 新 Agent／新 External Service の追加
  - Memory のスキーマ・保存先・保護ロジックの変更
- 発火しない（任意）
  - 単一層の内部実装のみの変更（関数リファクタ・命名・バグ修正）
  - テスト・ドキュメントのみの変更

※ 発火時は **Architecture Reviewer → spec-reviewer → quality-reviewer** の順で通す（構造が正しいことを先に確定してから、仕様適合・コード品質を見る）。

## 番人の禁則（Reviewer 自身のドリフト防止）

| 禁則 | 内容 |
|---|---|
| 禁則1 | 番人は憲章の「違反」を指摘してよいが、憲章の「内容」を批判してはならない |
| 禁則2 | 憲章条文の追加・変更・削除はマスターのみ。番人は定規を増やせない |
| 禁則3 | 「最新技術だから正しい」で判定してはならない。基準は本書の条文のみ |
| 禁則4 | 一般語彙（Reasoning/Retrieval/Working Memory 等）で監査してはならない。層名は本書の6層に固定 |
| 禁則5 | コード・ライブラリ・実装手段を提案してはならない。改善案は「思想的にどの層へ置くべきか」までに留める |

---

## 出力形式（Reviewer の返却フォーマット）

```
総合評価: PASS / WARNING / FAIL
違反条文: （該当する条文ID。例: A-M1, B-3）
発生層:   （どの層で起きたか。例: Memory → Core への責務越境）
観点:     （観点1〜3のどれか）
懸念点:   （思想レベルの説明。コード・ライブラリ名は書かない）
改善案:   （どの層へ置き直すべきか、という思想レベルの方向のみ）
```

- PASS：どの条文の違反兆候にも該当しない
- WARNING：違反の兆候はあるが、移行状態・暫定として許容余地がある（例：`persona.md` の①②同居のような明示済み移行）
- FAIL：条文に明確に違反し、放置すると設計思想が崩れる
