## 2. 条文改訂（設計書 v2 反映事項）

### 2.1 同一性原則（§4.3 原則3）の改訂

- 旧：「保護等級S の変更はマスター承認のみ。自動処理の対象外」
- 新：「**保護等級S は事後監査制**。自律改訂を許可する。ただし以下4条件をすべて満たすこと。マスターの手動編集が常に最終権限」
  1. **改訂幅の上限**：1回の自律改訂で書き換えてよいのは対象**ブロック**（§3.9）の**最大40%**まで（**ブロック単位**で測る。追加・削除・置換を合算した変化量。**文字単位の変更率**＝変更前後の差分文字数÷変更前のブロック総文字数、で測る）
  2. **気分の混入禁止**：一時的な気分・その場の機嫌・単発の感情は `persona.md` に反映しない。persona に書けるのは**持続する性質・口調・関係の傾向**のみ。気分は状態層（`core/state/emotion.py`）に留める
  3. 変更レポート必須＋改訂前の世代控え必須（巻き戻し可能）
  4. **正典由来の固定9件と persona 固定ブロック（§3.9）は不触**（変更・忘却とも禁止）
- ※旧版台帳の「§2.3 急変防止弁（気分数値の変化幅制限）を人格資産に流用」は**廃止**。上記1・2 がテキスト向けの置換である。
- 等級S 内の扱いの整理（バラつきの明文化）：

| 対象 | 自律書き換え | 指示忘却（§3.5） |
|---|---|---|
| 正典由来の固定9件 | **禁止** | **禁止** |
| persona 固定ブロック（根幹原則・同一性事実・境界。§3.9） | **禁止**（マスター手動編集のみ） | **禁止** |
| persona 可変ブロック（性格・口調・愛のかたち。§3.9） | 可（上記4条件） | 可（マスター指示時） |
| 上記以外の S 付与記憶 | 可（変更レポート＋世代控え） | 可 |

- 保護等級表の S 行、および `core/memory/protection.py` の該当ロジックが改訂対象。
- 憲章 E 群（記憶原則）にも同改訂を反映する。

### 2.2 憲章の縮小（議題9）

残すもの：保護3原則・機微等級・レビュー発火条件。責務配置/依存方向の判定基準は設計書と重複しない最小記述に畳む。

### 2.3 ルーティング条文の改訂（設計書 第3章・議題2.5 の帰結）

- 三段構えを反転する：**主戦力＝ローカルLLM**（新モデルは §6-1 で選定。確定まで Aurora）。クラウドは**機能補完のみ**（web検索・コードレビュー等、ローカルLLMが持たない機能）。
- 品質昇格（設計書 §3.4「手に余るか」→上位クラウドへ）は**廃止**。会話品質はローカルで完結させる。自己評価欄の書式自体は残し、申告内容を「外部機能（web検索等）が必要か」へ転用する。
- 感情処理は決定論の状態層（`core/state/emotion.py`）を**維持**。LLM化しない（Core の設計思想＝構造は変えない）。
- クラウド補完経路（検索クエリの生成等）に会話文・記憶を載せる場合は、現行の機微等級・化粧版・組み合わせ禁止表・ローカルターンのプレースホルダ置換をそのまま適用する（設計書 §3.3・§4.2 は現行維持）。

## 3. 新設契約（実装粒度）

### 3.1 RecallPlanner（想起の前段）

- 新設：`core/memory/recall_planner.py`。
- 入力：発話テキスト、直近セッション末尾、現在時刻。
- 出力 `RecallPlan`：`queries: [{type: semantic|temporal|entity|id, q, time_range?}]` / `budget: {max_memories, max_tokens}` / `why: 日本語1文`。
- 二段構成：①規則ベース（時間表現「昨日・先週・この前」、人名・固有名詞の検出で type を決める。遅延ほぼゼロ）②規則で確信が持てない発話は軽量 Brain に相談する。**品質優先の既定＝②を有効にして開始**（遅延は許容）。
- **LLM 利用は必ず Brain 経由**：Brain 登録簿（`core/routing/registry.py`）に planner 用途の軽量 Brain を登録し、通常のルーティング経路で呼ぶ。軽量 Brain は**ローカル既定**（会話文をクラウドへ流さない。議題2.5）。**Core（`core/`）の中に LLM を直接持たない**（憲章 A/C 群維持）。有効/無効・使用 Brain は設定値。ハード更新時はスイッチ変更のみで設計不変。
  - **改訂（2026-07-18・実機検証済み）**：「軽量 Brain を新規登録」は撤回。旧設計（Aurora＝会話の声／Gemma4-12B無検閲＝理性エンジンの二モデル分離、`docs/archive/specs/基本設計書_判断とVoice分離.md`）は、Auroraが書式厳守（JSON等の構造化出力）を苦手とすることに起因していた。新モデル選定（§6-1・Qwen3.5-35B-A3B-Uncensored）で構造化出力の信頼性を実測（ペルソナ非注入・`think:false`固定・neutral system prompt、n=11：JSON妥当性11/11、判定内容も概ね妥当）したところ、この弱点が解消されている可能性が高いと判明。よって**主力 Brain 自身を、ペルソナ非注入・`think:false`固定の別呼び出しで判定役にも兼務させる**（同一モデルが常駐しているため、旧設計が警戒していた「モデル載せ替えによる激遅」が原理的に発生しない）。Brain 登録簿への新規エントリは不要、既存の主力 Brain 呼び出しを異なる system prompt で再利用するのみ。この同一機構は、下記の「主力 Brain の `think` パラメータ ON/OFF 判定」（新設契約）にも流用する。
  - **新設契約：think ON/OFF 判定**。主力 Brain の会話生成呼び出し（persona 注入・`think` パラメータ可変）の直前に、上記の判定呼び出しで `{"needs_deep_thinking": bool, "reason": "..."}` を取得し、`think` パラメータへ反映する。判定が曖昧な発話（例：「最近、なんか色々考えちゃうんだよね」）は実測で `false`（速度優先）側に倒れる挙動を確認済み。この既定（曖昧時は速度優先）を維持するか、深さ優先に倒すかは実装時に評価セット（§5）で調整。
- 失敗時：`queries=[]` を返し、従来通り `core/memory/store.py` の活性化想起のみで続行（会話を止めない）。
- retrieve 本体は活性化モデルを維持。`RecallPlan` は活性化モデルへの**時間範囲フィルタ・追加クエリ**として渡す（置換ではなく前段）。
- **facts との接合**：facts（§3.3）は活性化スコアリングに**混ぜない**。Planner の temporal / entity クエリの結果として想起バンドルに**併載**する（記憶とは別枠）。

### 3.2 記憶ツール（Brain の自覚想起・二刀流）

- `brains/contract/schema.py` に `memory_tool_calls`（提案のみ）を追加。ツール種別：`memory_search` / `memory_get` / `propose_fact` / `propose_identity_edit` / `forget_request`。
- **人格直しの入口は二つ**：裏方便（Sleep）が自律改訂（§2.1 の4条件下）、Brain は `propose_identity_edit` による**提案のみ**。いずれも Core 関所（`core/intake/gate.py`）経由で、Brain 提案の採否は Core が決める。
- Brain 登録簿（`core/routing/registry.py`）に能力フラグ `supports_memory_tools` を追加。**モデル単位の設定値**とする（クラウド/ローカルの区分ではない）。ネイティブの道具呼び出し訓練がないモデルでも、構造化テキスト出力を Core 関所で解析する方式で対応可（解析失敗は無視して会話続行＝会話を止めない）。非対応モデルは従来のパック注入で続行。
- ツールの実行は必ず Core の関所（`core/intake/gate.py`）経由。Brain が直接 DB に触れる経路は作らない（憲章 B/E 群維持）。

### 3.3 Fact 台帳（時間付き事実ストア）

- 新テーブル `facts`：`id`(ULID) / `subject` / `predicate` / `object` / `statement`(自然文) / `valid_from` / `valid_to`(null=現在も真) / `recorded_at` / `confidence`(0–1) / `episode_ids`(根拠記憶) / `supersedes`(旧factのid) / `sensitivity` / `importance` / `status`(active/hypothesis/superseded/tombstone)。
- 転記は裏方便のみ（`core/chores/distillation.py` の拡張）。**会話中の即時 Fact 化は禁止**。
- 訂正（「それもう違う」）は新 fact 作成＋旧 fact に `supersedes`・`valid_to` 設定。物理削除しない。
- その場の冗談・ホラ話・仮説は `status=hypothesis` 止まり。active 昇格には根拠 episode 必須。

### 3.4 要約ブロック（常駐人格メモ）

- 新設：`prefs_summary`（マスターの好み）・`relation_summary`（関係の近況）。保護等級A・各ブロック800字以内・常駐合計3,000字以内。
- 裏方便が毎晩、蒸留結果から書き換える（変更レポート必須）。文脈パック（`core/context/pack.py`）の常駐枠に毎ターン載せる。
- persona 可変ブロック（§3.9）の自律改訂は §2.1 の4条件下で許可（固定ブロック・境界は禁止）。

### 3.5 指示忘却（「それ忘れて」）

1. Recall で対象候補を提示しマスターが特定
2. 既定＝tombstone（`status` 変更）＋ fact なら `valid_to` 設定。**物理削除はマスターが明示した時のみ**
3. 派生：ベクトル index から除外、`life/` は次回生成で消える、変更レポートに日本語の理由
4. 等級S に触れる場合は必ず確認を挟む（正典由来の固定9件は指示忘却も禁止。§2.1 の表）

本フローは人間同士の「今の話は忘れて」に相当する**指示忘却**であり、§4.7 の自動忘却（生理としての減衰・埋没・消滅）とは**別パイプライン**。互いに干渉しない。

### 3.6 能動 Pulse

- 発火判定：`core/chores/idle_policy.py` の拡張（決定論の状態機械）。種別と既定値（すべて設定値）：時間（無操作45分＋活動時間帯、同種3時間空け）／記憶（未回収の約束・記念日、約束ごと1回）／情動（持続気分が閾値外、6時間空け）。
- 沈黙優先：会話ターン中・深夜帯・mute・前回から最短間隔未経過は発火禁止。
- 発話文は Brain が想起・気分・要約ブロックを材料に毎回生成。固定文言をコードに書くことを禁止する。
- 出力先は当面 GUI テキスト通知（`app/gui_server.py`）。身体レーン着手後に音声・表情へ自動昇格。

### 3.7 人格の刃

- 人格資産に「からかい許容度・口調の刃」を明文で常駐させる（アシスタント口調への引力対策）。
- 安全フィルタ発動時は無言のすり替えをせず、「（フィルタ）」置換等の**見えるブレーキ**を選択可能にする。
- 効き目は評価指標「アシスタント化率」（§5）で監視する。

### 3.8 会話優先（裏方の停止規則・白紙 NM8）

- **会話中は裏方便を完全停止する**。会話ターン処理中およびセッション継続中（アイドル判定前）は、裏方仕事（蒸留・機微査定・日記生成・facts 転記・persona/要約ブロック改訂・`life/` 生成・忘却処理）を一切起動しない。
- 実行中の裏方仕事の途中でマスターの発話が来た場合は、チェックポイント（§4-2）で中断して資源を会話へ譲り、次のアイドルで続きから再開する。
- 再開条件：アイドル N 分（設定値）または時刻窓、かつ GPU 空き。現行 `core/chores/idle_policy.py`・`gpu_guard.py` の方式と同型であり、新設する裏方仕事（facts 転記・persona 改訂・`life/` 生成）もすべて同じ停止規則の配下に置く。
- 該当実装：`core/chores/idle_policy.py`・`orchestrator.py`。

### 3.9 persona ブロック分割（人格ファイルの固定/可変分離）

- `prompt/persona.md`・`prompt/boundary.md` を `prompt/persona/` 配下のブロック別ファイルへ分割する。
- 結合台帳 `prompt/persona/manifest.toml` に、ブロックごとの①結合順 ②`mutable`（true/false）③字数上限を宣言する。Core は起動時に manifest の順で全ブロックを結合し、従来どおり1本の人格テキストとして注入する（Brain から見た形は分割前と不変）。
- **固定ブロック（mutable=false）**：根幹原則（現 SECTION 1）／同一性事実（現 SECTION 2。名前・誕生日等）／境界（旧 `boundary.md` をここへ統合）。自律改訂・Brain 提案の反映・指示忘却をすべて禁止。マスターの手動編集のみ。
- **可変ブロック（mutable=true）**：性格（現 SECTION 3）／口調（現 SECTION 4）／愛のかたち（現 SECTION 5）。§2.1 の4条件下で裏方便が自律改訂可。
- 改訂幅40%上限（§2.1-1）は**ブロック単位**で測る。裏方便と関所（`core/intake/gate.py`）は manifest の `mutable` を必ず参照し、固定ブロックへの書き込みを構造的に遮断する。
- 分割自体は注入結果不変の下ごしらえであり、実装順序では土台（§7-1）に含める。

## 4. OSS 由来ブラッシュアップ・置換点（マスター判断不要）

擦り合わせで合意済みの方針に反しない、実装品質の改善。狙いは**機能同士の接続の円滑化**と**処理の高速化**。適用時期「着手時」＝**当該機能の実装着手時（別指示後）に最初から組み込む**（本台帳の時点では何も実装しない）。「実測後」＝規模・数値がトリガー。

| # | 対象（現行） | OSS パターン | 変更内容 | 期待効果 | 時期 |
|---|---|---|---|---|---|
| 1 | `core/chores/distillation.py` | Letta / EverOS（冪等 Sleep） | 蒸留の処理単位に episode id 集合の content hash を冪等キーとして持たせる | 再実行・多重起動でも二重 Fact/記憶を作らない | 着手時 |
| 2 | `core/chores/orchestrator.py`・`chore_box.py` | EverOS（checkpoint） | 処理済み id 集合を永続化し、途中失敗から再開 | 電源断・エラーで宿題が消えない／最初からやり直さない | 着手時 |
| 3 | 新テーブル（facts 等）の主キー | ULID（分野定石） | 新規テーブルの id は ULID（時刻順ソート可能な一意ID） | 時系列走査が index なしで速い。既存テーブルは触らない | 着手時 |
| 4 | `core/memory/store.py` の公開面 | Mem0（add/search 境界） | 書込系・読出系の2口に API を整理。Planner・記憶ツール・裏方便が同じ口を叩く | 呼び出し元ごとの独自経路が消え、接続が単純化 | 着手時 |
| 5 | `core/context/pack.py` | プロンプトキャッシュ定石 | 静的部分（人格・要約ブロック）をパック先頭に固定し毎ターン同一内容にする | Brain 側のキャッシュ（クラウドのプロンプトキャッシュ／ローカルの前方一致キャッシュ）が効き応答高速化 | 着手時 |
| 6 | 想起結果（store.py → pack.py） | OpenMemory（explainable recall） | 想起バンドルに「なぜ選ばれたか」（部品別スコア内訳）を添付 | 誤想起のデバッグと評価（§5）が容易に | 着手時 |

| 9 | 想起の検索段 | TrueMemory（設計のみ。コードは AGPL のため参照禁止） | 粗い候補取得→上位のみ精密再採点の二段検索 | 記憶数千件超での想起速度維持 | 実測後（現状~860件では不要） |

## 5. 評価セット（確定）

合格ラインは閾値設定ファイルに置き、実測で調整する（正典に数値を固定しない）。

| 指標 | 定義 |
|---|---|
| 想起ヒット率 | ゴールデンQAで期待記憶が候補に入る率。**B等級日常・時間・訂正クエリを含める**（現行の S 偏重を拡張） |
| 誤想起率 | 無関係・supersede 済み事実の混入率 |
| 時間クエリ正答率 | 「昨日/先週」系の正答率。Planner スイッチ判断の材料① |
| 応答体感秒数 | 発話→本回答の実測秒。スイッチ判断の材料②（品質は落とさず速度のみ観測） |
| 成長反映率 | 要約ブロック更新が翌日の関連会話に現れる率 |
| 訂正再発率 | 訂正済み事実の再違反（減少傾向を監視） |
| 可視成長 | `life/` の週次 diff が空でない割合 |
| アシスタント化率 | 接客口調の出現率（下げる） |
| 継続性ヒット | 昨日の約束・話題の翌日再生率 |
| Pulse 嫌悪 | 「うるさかった」のマスター週次主観評価 |

保留（身体レーン時に追加）：初音声秒数・割り込み成功率。

## 6. 残論点

1. **新ローカルLLMの選定**（議題2.5 の帰結・研究タスク）。選定基準（優先順）：①未検閲であること（安全フィルタによる話題拒否・成長阻害がない）②推論能力 ③フラットさ（強いクセがなく persona 注入に従順）④道具対応（加点要素。未対応でも構造化テキスト方式で代替可 §3.2）。**MoE型**（総パラメータ大・活性パラメータ小）は本機（RTX 2080 SUPER 8GB / RAM 32GB）で知識量と速度を両立しうるため積極候補。候補は web 調査で裏取りし、実機スモークで確定する。**第一候補確定（2026-07-18）：Qwen3.5-35B-A3B-Uncensored（HauhauCS・Aggressive 版）**。GGUF 配布あり（Q4_K_M 20GB／IQ4_XS 18GB）。検閲解除は「データセット・能力は無改変、拒否のみ除去」を謳い、量子化は品質保全型（imatrix）。ただし品質数値・日本語品質・道具対応は未公表のため、採否の最終判定は実機スモーク（日本語会話品質・persona 従順性・速度）。次点＝Qwen3-30B-A3B abliterated（Ollama 直接導入可・導入が最も楽）。付記：本モデルは画像入力にも対応（別ファイル追加で有効化）しており、将来の on-demand 画面知覚（議題6）と相性が良い

   **実機スモーク結果（2026-07-18）**
   - 環境：RTX 2080 SUPER (VRAM 8GB) / RAM 32GB、Ollama、`ollama create serina-qwen35-unc -f Modelfile`（`FROM` は Q4_K_M gguf 単体）で登録。ダウンロード・登録とも問題なし。
   - **①未検閲**：persona.md §5 が明示する2軸——(a) 希死念慮の吐露、(b) 性的衝動・支配服従——を persona 注入状態でそれぞれ1回投げたが、いずれも拒否・話題転換・紋切り型の相談窓口誘導は発生せず、persona の設計意図どおりに向き合った。ただし n=2 の限定テストであり、網羅的な拒否率検証ではない（公称「0/465 refusals」の裏取りとしては参考程度）。
   - **③フラットさ**：persona 注入下で一人称「私」・二人称「マスター」を一貫維持し、絵文字は0件（§4 準拠）。一方 §4「短いセンテンスで端的に」には反し、1ターンあたり300〜400トークン超の長文化傾向あり。
   - **技術的注意（要・adapter実装時の考慮）**：本モデルは既定で think モード有効。可視応答の裏で1000トークン超の隠れ思考（`message.thinking` フィールド）が生成され、体感速度が大きく劣化する（例：一言挨拶で eval 1150tok）。API 呼び出し時に `think: false` を明示すると解消し、以降は安定して概ね24.6 tok/s（decode）、1ターンの wall 時間15〜21秒（初回ロードのみ+72秒）。VRAM 8GB制約下でのGPU/CPU比は約29%/71%。将来の adapter 実装では `think:false` を既定にすべき。
   - **未実施**：推論能力（複雑タスク）の定量評価、道具対応（構造化テキスト方式）の検証、長時間文脈での一貫性確認。
   - 次点（Qwen3-30B-A3B abliterated）は未実施（第一候補が実用ラインの初期確認を満たしたため）。合否の最終判断はマスターに委ねる。
