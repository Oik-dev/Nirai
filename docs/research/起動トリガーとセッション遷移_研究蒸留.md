# 起動トリガーとセッション遷移 — 研究蒸留

出所: Gemini研究会話ログ（原本: `docs/research/originals/起動トリガーとセッション遷移の設計_geminiログ.json`）からの蒸留。蒸留日 2026-07-03。

---

## 1. 設計に直結する結論

- **セッション状態は3段階**: `active`（会話進行中、常に最新1件）/ `pending`（終了済み・蒸留未実行）/ `distilled`（蒸留完了・長期記憶化済み）。
- **セッション終了（タイムアウト）判定はハイブリッド方式**。Core起動時に過去の `active` セッションを検査し、以下いずれか合致で `active → pending` へ遷移、新規 `active` セッションを作成する。
  - **条件A（6時間ルール）**: `現在時刻 − 前回最終発言タイムスタンプ ≥ 6時間`。日中の外出・長時間労働からの帰宅など「生活フェーズの切り替わり」検知用。
  - **条件B（生活暦AM4:00ルール）**: タイムスタンプから **4時間** を引いた日付を「生活日（Living Date）」とし、前回発言時と現在時刻とで生活日が異なれば日跨ぎと判定。深夜1:30に就寝→朝6:00起床（経過4.5時間、6時間未満）でもAM4:00を跨いでいれば新規セッションとする救済ロジック。
    ```python
    def get_living_date(dt: datetime.datetime) -> datetime.date:
        adjusted_dt = dt - datetime.timedelta(hours=4)
        return adjusted_dt.date()
    # last_living_date != current_living_date で日跨ぎ判定
    ```
- **リフレクション発火は2経路（B:メイン非同期／A:サブ同期）**。
  - **① 起動時後追い（メイン・非同期）**: 起動時判定で `pending` に落ちたセッションがあっても即実行しない。ユーザーの本日最初のメッセージへの**返答を送信完了した直後**に、バックグラウンドスレッドで `pending` セッションの蒸留を開始。理由: 初回応答の速度を犠牲にしない／ユーザーが返答を読んでいる間はGPUが手薄になりやすい。
  - **② ユーザー指示（サブ・同期）**: 「日記書いて」「整理して」等のインテント検知時は**同期処理**でその場で蒸留し、「整理したよ」と完了保証してから応答する。ユーザーはこの完了を見てから安心してPCを落とせる。
  - **確定した優先度: B（起動時後追い）をデフォルト・ベース動作、A（ユーザー指示）は補助（たまに使う）**。
- **エラー時のステータスはpending維持**。蒸留失敗（LLMエラー等）時はステータスを`pending`のまま据え置き、次回起動時または手動リトライで再試行。ログのロストを防ぐ。
- **物理削除は避け、退避（archive）を原則とする**。`distilled` になった生ログは即物理削除せず `archived_history` テーブルへ退避。デバッグ期はもちろん、本番運用でも同様。
- **パージは手動/自動コマンドで別途実行**: `python manage.py purge-archive --older-than 30d`（30日以上前の退避データのみ物理削除、日数は設定で調整可能）。

## 2. 採用を検討すべき手法（根拠つき）

- **タイムアウト閾値6時間は妥当**（根拠: 他システム調査より）。
  - タスク重視・ビジネス系（Amazon Bedrock Agent 30分、Zendesk AI 2時間、Oracle GenAI 1時間）は「用事が終わったら即クリア」志向でパートナーAIには短すぎる（映画鑑賞・入浴程度でセッションが分断されストレス要因になる）。
  - 生活アシスタント・ライフログ系（例: OpenClaw の `reset: { mode: "daily", atHour: 4 }`）は「日またぎ・AM4時リセット」志向。ケア会話重視のパートナーAIにはこちらの思想が近い。
  - 6時間は「睡眠検知（6〜8時間で必ず跨ぐ）」と「外出程度では割らない」の両立点として妥当という評価（ただしログ内での結論は「先駆者事例との比較からの推定」であり、業界標準として確立された数値ではない点に留意）。
- **生活暦（Living Date、AM4:00を日界とする）はゲーム開発でも使われる手法**として言及されており、6時間ルール単独の欠点（早起き時に日跨ぎを検知できない）を補うハイブリッド化の根拠として採用。
- **GPU競合を避ける実行タイミング設計**: 「返答送信直後」に非同期蒸留を回す設計は、ゲーム起動などとの衝突を最小化する現実的な折衷案として提示された（数秒で終わる想定のため衝突時間は僅少という前提）。
- **PC接続イベント起点は不採用対象として検討されたが、結論として「1（起動時後追い）＋任意」に一本化**。以下の3.のとおりリスク回避のため、より複雑な追加トリガーは見送られた。

## 3. 落とし穴・失敗パターン（ログ内で指摘されたもの）

- **OSスリープ／シャットダウン直前イベントでの蒸留実行は避けるべき**。処理完了前にOSが強制終了し、DB破損・データ消失のリスクがある。
- **アイドルタイマー（例: 30分〜1時間放置で自動蒸留）は却下**。理由: (a) タイマーイベントが確実に発火するか技術的懸念、(b) 時間調整を誤ると「会話を終えてゲームを始めた」直後にローカルLLMが起動し、GPU（グラボ）負荷が競合する。
- **「クローズ・インテント（おやすみ等の挨拶）検知」も却下**。理由: 「おやすみ→即シャットダウン」のパターンで、猶予時間（3〜5分後実行の想定だった）を待たずに電源が落ち、タスクが蒸発（未実行のまま失われる）する漏れが発生しうる。
- **二重抽出（重複）問題**: 長時間セッションで中間蒸留（部分リフレクション）を行った場合、後続の全体蒸留で前半部分が再度抽出され、記憶の重複・ブレが生じる懸念（解決案としてチェックポイント方式`distilled_up_to_id`や、30ターン超過時の仮想的セッション強制終了＋新セッションへの要約引き継ぎが挙げられたが、**この部分は3a確定仕様には未採用・継続検討のまま**、ログ内でも「セッション1で詰める点」として保留）。
- **業務ログの扱いを誤ると記憶が肥大化**: 業務タグでの単純な「除外」は雑すぎる設計と自己修正されている。トピック（仕事か否か）ではなく高度（significance）で切り、業務の細かい操作ログ（実装した関数の列挙等）は捨て、「その日ほぼ一日仕事で疲れていた」等の1件の高度な状態要約に圧縮する（これは3b:蒸留設計に直結する知見であり、ブロック1自体の話ではないが、pendingセッションに蓄積される内容の設計思想として関連）。
- **サーバー型前提の設計をそのまま持ち込むと機能しない**: 「常時起動サーバー」を前提にした「メッセージ受信の都度チェック」設計は、ユーザーの実環境（サーバーなし、PC起動時が起動タイミング、明示的終了コマンドなし）に合わないため、早々に方針転換された。

## 4. Serina現行設計（3a実装済み）との差分メモ

- **状態機械・タイムアウト判定（6時間 or 生活日変化）・archived_history 30日保持は、ログの確定仕様とほぼ一致**。3a実装はこのログの結論をそのまま採用したものと確認できる。
- **既知の限界とログの関係**: 現行実装は「起動時のみ判定」であり、「REPL常駐のままAM4:00や6時間無操作を跨ぐと分断されない」という限界がある。ログでは「起動時後追い（非同期）」をベースとしつつ、常駐中の扱いについて「アイドルタイマー」案は明確に**却下**されている（GPU競合・発火信頼性の懸念）。したがって3bでの対応検討時、単純な「常駐中もタイマーで定期チェック」の再導入は、ログで指摘された同じ懸念（グラボ競合、タイマー発火の信頼性）に注意する必要がある。
- **ターン毎チェック（3b検討事項）に対するログの示唆**: ログでは常駐中のリアルタイム分断策として「アイドル検知」「クローズワード検知」の両方が提案されたが、いずれも一長一短ありとして最終的に不採用（「1＋任意」に一本化）。3bで「ターン毎チェック」を設計する際は、少なくとも「毎ターンでの重い判定・蒸留実行」は避け、軽量な状態フラグ確認に留め、実際の蒸留は引き続き「返答送信後の非同期」または「明示指示時の同期」の枠内で行う設計が、ログの結論と整合的。
- **旧セッション末尾N発言の引き継ぎ（3b検討事項）に効く知見**: ログの「解決案B（仮想的セッション強制終了）」で、30ターン超過時に新セッションへ「直近数ターンの要約」をインジェクションするアイデアが出ているが、**この案自体は確定仕様に採用されず、保留（継続検討）のまま**である点に注意（ログ内では未確定）。二重抽出対策のチェックポイント方式（`distilled_up_to_id`）も同様に未確定・アイデア止まり。
- **ユーザー指示による同期蒸留（トリガーワード）はログでは「日記書いて」「記憶を整理して」等の部分一致検知が想定されていたが、具体的な検知実装方式（ハードコーディングか意図判定か）はログ内でも「議論したい点」として問いかけられたのみで、確定していない**（ログ内では未確定）。
- **エラー時のリトライ方式**（次回起動時 or 手動リトライ）は3a実装で反映済みか要確認。ログでは「ステータスをpending維持し次回再試行」とのみ記載され、自動リトライの具体的スケジュールは未確定。
