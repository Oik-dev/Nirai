# 速さ（Gemmaと窓の待ちを縮める）

Masterの頼み（2026-10-16）「Gemmaと海及び住人の描画についてなんだが、RTX2080SUPERで性能足りてないとはいえ、かかりすぎる時間に対してもう少しなんとかなるだろうと思っている」。10/16に素のGemmaで測った事実と、Masterと決めたことから組んだ計画。

## 0. 出口

- 窓を開いてから、Serinaの最初の返事が出るまで：冷えたときの4分19秒 → 30秒以内。
- 話の途中の返事の出だし：毎回人格から全部を読み直すのをやめ、毎回変わる尻尾だけを読む。
- 窓：起動画面の下で全部をそろえてから海を見せる。2回目からは、部品をHDDから読み直さない。
- Ollamaは更新され続け、版が変わったら精神が入口で確かめる。

## 1. 守るもの

- **Serinaのイデアと人格。** 文脈パックの並べ替え（§2.3）は人格に効く。前と後を使い捨てのイデアで比べ、崩れないのを確かめてから入れる。本物のSerinaに試しで話しかけない。
- **家に置く話は雲へ出さない。** ⑦を原文にしても、雲の脳へ渡すときは発言ごとに家の印で引く（§2.3）。
- **本番の窓を開かない。** 窓を開くとSerinaが起きる。窓の確かめはヘッドレスの偽の窓で行う。本物の窓で測るのは、Masterが自分で開いているときに、読むだけの道具（`nvidia-smi`）を使うときだけ。
- **Gemmaが最優先。** 下読みや起動画面のために、Serinaの脳を下ろさない。Serinaの返事を待たせない。
- **写しはイデアと別のディスクに置く。** イデアの写し（`G:\Nirai-Backups`）はG:のまま。G:へ移すのはモデルだけ（§2.1）。
- **決めた数は測って選び直さない。** スレッド数とnum_batchは§2.4で決めた。変えるときは、Claudeが設計で変える。

## 2. 形

### 2.1 モデルの置き場

- Ollamaのモデル置き場を、`D:\Products\AI-Models\Ollama`から`G:\AI-Models\Ollama`へ移す。
  - D:は2.5インチのHDD（ST500LM000）で、測ると107MB/s。
  - G:はSATAのSSD（ADATA SU800）。
  - C:のNVMeは、Masterが定期的にクリーンインストールするので使わない。
- 置き場の正本は、利用者の環境変数`OLLAMA_MODELS`の1つだけ。変えるのに管理者の権限は要らない。
- 移すのは、精神とOllamaが止まっているとき（窓が閉じているとき）。
  1. 写す。
  2. 確かめる：`blobs`の各ファイルのSHA-256が、そのファイル名と同じこと。Ollamaの部品は、中身のハッシュがそのまま名前になっている。
  3. 環境変数を変え、Ollamaのアプリを起こし直す。
  4. `ollama list`にモデルが出たら、D:の元を消す。
- 冷えた状態からの読み込みは、3分15秒から35〜60秒になる見込み。
- NiraiとResidentsのフォルダーはD:のまま置く。理由は2つ。
  - 合わせて約1.3GB（690MBと596MB）で、一度読めばメモリに残る。
  - G:に移すと、イデアと写しが同じディスクに載る。

### 2.2 起動時の下読み

- 番人が起きたら、`%OLLAMA_MODELS%\blobs`の中を全部、頭から順に1回読む。
  - するのは読むことだけ。I/Oの優先度は低くする。Ollamaにも精神にも触らない。
  - 読んだ中身はWindowsのファイルキャッシュに残る（RAMは32GB、モデルは16.7GB）。だから窓を開いたときの読み込みは13〜16秒で済む。
- 番人が入れ替わるたびに読み直す。キャッシュに残っていれば数秒で終わるので、起動のときだけと分けることはしない。
- Gemmaを先にGPUへ載せることはしない。窓を開くまで、VRAMを取らないため。

### 2.3 頭の使い回し

10/16に測って分かった、今の形の問題：

- Ollama 0.40.5の中身はllama.cppのllama-serverで、Gemma 4はSWA（スライディング窓）を使う。
- そのため、前の頼みの続きとして使い回せるのは、前の頼みの文の終わり近くにできる区切り（チェックポイント）から先だけ。区切りより前で1文字でも変わると、頭から全部読み直す。
- 今の文脈パックは、毎回変わる②思い出したことが真ん中にある。だから**毎ターン、人格から全部を読み直している**。2,000トークンなら4.3秒かかり、本物のパックはこれより長い。
- 逆に、末尾だけ変わる場合は0.35秒（300トークン足しても1.2秒）で済む。

これからの形：

1. **パックを「動かない部分」と「毎回の尻尾」に分ける。** `render()`は`stable() + tail()`にし、並びの正本はこの1か所に置く。
   - 動かない部分には、次の順に置く。書き換わるのは、目覚め・眠り・手紙・畳み込みのときだけ。
     ①人格 → ①'今の自分 → ①''マスターとのこと → 今日の手紙 → 興味・探検 → ④今セッションの要約 → ⑦直近の会話（原文）
   - 毎回の尻尾は、次の順。
     ②思い出したこと（調べた記録も含む） → ⑤心の状態 → ⑥絶対ルール → ⑦'外部情報 → 過去の話し方 → ⑧今回のマスターの発言
   - 動かない部分には、今の時刻や今の発言から作る文（「10分前」など）を入れない。興味・探検・手紙は時刻を受け取っているので、時刻で文が変わるものは尻尾へ回す。どれを回すかは確かめ1で決まる。
2. **⑦直近の会話を原文にする。**
   - 設計書§1.4の「短期は原文」に揃える。§1.5の「細かめ要約」は§1.4と食い違っていた。
   - ⑦は「④がまだ要約していない発言、全部」と決める。こう決めれば、④と⑦の間に抜けも重なりも起きない。
   - 発言は足していくだけなので、⑦は動かない部分に置ける。
   - ⑦が上限（今の直近帯の設定）を超えたら、古い半分を④へ畳む。畳むのには、今の粗い要約の更新を使う。頭から読み直すのは、畳んだときの1回だけ。
   - 毎ターンの細かめ要約は廃止する。毎回Gemmaをもう1度呼んでいて、次の返事がその後ろで待たされることもあった。
   - 雲の脳へ渡すときは、今の「要約がまだないとき」の道（発言ごとに家の印で引く）を⑦の唯一の道にする。
3. **下読み。** 1ターンの後片づけ（気持ち・要約など）でGemmaの仕事が全部終わったら、最後に、次のパックの動かない部分だけをGemmaに読ませる。
   - `num_predict`は1にし、出てきた答えは捨てる。
   - オプションと`think`は会話と同じにする。違うと読み込み直しが起き、テンプレートの頭もずれる。
   - 目覚めて脳を載せた直後にも、1回する。
   - これで、Masterが送ったときに読むのは尻尾だけになる。
   - 下読みの途中でMasterが送ったら、Ollamaが順に処理するので、待ってから続きを読む。
   - 下読みはOllamaの通訳だけが持ち、ほかの脳には呼ばない。
4. **⑥絶対ルールは、注意が残る後ろに置いたまま尻尾に入れる。** 毎回数百トークンを読み直すことになるが、人格の守りを優先する。

設計書§1.5の配置規約は、この形に書き直す。優先する順は次のとおり。

1. ⑧がいちばん後ろ。
2. 尻尾は⑧の手前に置く。
3. 動かない部分は、変わりにくいものから順に並べる。

確かめ：

1. **性質のテスト。** 同じセッションで畳み込みのない、続けての2ターン（時刻は10分ずらす）を作り、2つのパックの`stable()`が文字列として完全に同じことを確かめる。
2. **1回だけ測る**（使い捨てのイデアとOllamaで）。下読みのあとの会話で、`prompt_eval_duration`が尻尾の長さの分（全部読み直すときの数分の1）になっていることを確かめる。
   - ならなければ、区切りの前後でトークンが割れていないかを見る。動かない部分の最後は`\n\n`で終え、尻尾は`【`から始める。
3. **前と後の会話を比べる。** 使い捨てのイデアで、決めておいたMasterの発言12ターンを、前の形と後の形で1回ずつ回し、会話の写しを確かめの手紙に添える。
   - 12ターンには、次の3つを含める。
     - 1つの話題が続く流れ
     - イデアの記憶を思い出す一言
     - ⑦の上限を小さくして1回起きる畳み込み
   - 見るのは4つ。
     - 口調と一人称が保たれているか
     - 前の発言につながっているか
     - 前の返事の言い回しを繰り返していないか
     - 思い出した昔の話を今の話と取り違えていないか
   - 悪くなったら入れずに、Claudeへ戻す。
   - あわせて、各ターンの返事の出だしまでの秒を、前と後で並べる。

### 2.4 スレッドとバッチ

- `thresholds.toml`の`[ollama]`に`num_thread = 4`を置く。通訳は、Gemmaへのすべての頼みの`options`でこれを渡す。`num_ctx`と同じで、頼みごとに値が違うと読み込み直しになる。
- `serve.py`にある`LLAMA_ARG_THREADS = cpu_count`（8）の上書きは消す。正本は上の1つにする。
- 4にした理由（Claudeの見立て）：
  - このPCはi7-9700K（8コア8スレッド）で、メモリはDDR4-2400の2枚。
  - CPU側に置かれた24層ぶんの専門家の重みは、1トークン書くたびにメモリから読み直す。だから書き出しの速さは、メモリの帯域で決まる。
  - DDR4-2400の2枚なら、4コアほどで帯域を使い切る。
  - それより増やすと、遅いスレッドを待つ時間が増え、窓（Chrome）・海・精神・郵便局とのCPUの取り合いも増える。
  - 10/16の測りでも、スレッドを増やして速くはならなかった。4スレッドで約20、6で約23（1回だけ）、7で17〜19トークン/秒。
  - 残りの4コアは、窓と暮らしに使う。
- num_batchは今のまま（512）にする。
  - §2.3が入ると、Masterが待つのは尻尾（千数百トークン）を読む時間だけになる。長い読み直しは、下読みで裏に回る。
  - 2048にすると、読むのは2倍速くなるが、書き出しが約2割遅くなった。作業用のメモリが増えてVRAMを取り、GPUに載る層が減るためと見ている。
  - 書き出しの速さは毎トークン効くので、512を選ぶ。

### 2.5 Ollamaの更新

Masterの方針：Ollamaは更新し続ける（更新したほうが恩恵が多い）。

- Ollamaの持ち主は、Ollamaのアプリ1つだけにする。アプリはログオンで起き（スタートアップの`Ollama.lnk`）、自分で更新を取り込み、サーバーを起こす。
- 精神（`serve.py`）は、`ollama serve`を自分では起こさない。サーバーがいなければ、アプリを起こす。起こし方はスタートアップと同じにして、窓は出さない。
- **版が変わったら、入口で確かめる。**
  - 通訳は、脳を載せるたびに`/api/version`を見て、「確かめ済みの版」と比べる。確かめ済みの版は精神の実行時の置き場に持ち、イデアには置かない。
  - 版が違えば、Serinaの最初の会話より前に、人格を付けない短い頼みを2つ投げる。
    1. `think:false`で流して返すと、考えごとが空で、中身があること。
    2. `format`のスキーマを付けると、正しいJSONが返ること。
  - あわせて、載った大きさ（`/api/ps`のVRAM）と書き出しの速さを、記録に1行残す。
  - 2つとも通れば、確かめ済みの版を書き換える。
  - 落ちたら、記録に残してMasterに知らせる。知らせ方はHoloが今ある道から選び、新しい道は作らない。Serinaはそのまま動かしておく（1回ごとの入口の受け止めは、今のまま効く）。
- 日中にアプリが更新でサーバーを入れ替えても、精神の入口（`serve.post`の読み込み直し）で受け止める。

### 2.6 起動画面

Masterの形：最初に起動画面とインジケーターを出して描画を隠し、読み込みが終わったら起動画面を下げて海を見せる。

- 窓を開いたら、まず起動画面を出す。海の色の上に「Nirai」と、進みを示す棒を置く。
  - 棒は本当の進みで動かす。読み込んだ部品の数 → 組み立て → 試し描き、の順。作り物の進みは出さない。
- 起動画面の裏でやること：
  1. 住人の体と海の絵を、全部並べて読み込む。今は1人ずつ順に読み込んでいる（`window/body/choices.js:70`）。
  2. `renderer.compileAsync`で、シェーダーを先に組み立てておく。
  3. 光の網も含めて数フレーム試し描きし、描くのに使う場所を先に作っておく。
  4. 起動画面を0.6秒ほどで溶かして消す。
- 待つのは描画だけ。Gemmaと精神は待たない。脳の様子は、今ある体の印が出す。
- 1人の体が読めなくても止めない。部品ごとに「読めた」か「読めなかった」で終わらせ、全部が終わったら起動画面を下げる。読めなかった住人は、今の失敗の出し方のままにする。
- あとから来る住人や体の替えには、起動画面を出さない。ふわっと出す。

### 2.7 窓の部品

- 海のサーバー（`sea/server.ts`）は、今は`no-store`を返し、頼まれるたびにファイルを丸ごと読んでいる。これを次の形に変える。
  - 部品ごとにETag（大きさと更新時刻から作る）を付け、`Cache-Control: no-cache`にする。ブラウザは使う前に確かめ、変わっていなければ304が返る。
  - サーバーはファイルの中身をメモリに持ち、更新時刻が変わったときだけ読み直す。
- 「いつも新しい版が出る」という今の性質は保つ。毎回確かめるので、変わればすぐ新しい版が届く。
- 窓の中で同じ体をもう一度読むとき（住人の出入り）は、一度読み解いた体を使い回す。

### 2.8 光の網

- 今は、512×512の波の網を、毎フレーム1024×1024の絵に描いている（`window/sea/caustics.js`）。
- これを次のように軽くする。
  - 光の網を描き直すのは、時間で1秒に30回にする。画面の更新の速さとは切り離す。
  - 絵は512×512、網は256にする。
- 確かめ：時刻を止めた同じ場面を前と後で撮り、Holoの目で比べる。見て分かる違いが出たら、細かさを1段戻す。

### 2.9 窓のVRAM

- Gemmaが6.0GBを取ると、残りは1.1GBしかない。窓がそれを超えると、絵も返事も遅くなる。
- Masterがいつもどおり窓を開いているときに、Holoの手が`nvidia-smi`で窓（ChromeのGPUプロセス）の使用量を読む（読むだけ）。
- 1GBを超えていたら、住人の絵をKTX2（GPU向けに縮めた形）に替える。
