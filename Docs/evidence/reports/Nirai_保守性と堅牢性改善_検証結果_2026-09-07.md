# Nirai 保守性と堅牢性改善 検証結果（2026-09-07）

## 対象と判断

Nirai全体の構成、基本設計・設計ガバナンス・現行実装状況を確認し、日常利用で失うと困る会話履歴・文脈と、接続・終了・音声の障害処理を優先した。作業開始時に多数の未コミット変更があり、それらを保持した状態で改善を追加した。初回改善はAstra単独で行い、レビュー後にHoloが3点の追補修正を実施した。サブエージェントは使用していない。

「居場所が主、タスクは従」、Resident Identity、Public / Private分離、Provider native continuation、Master Approvalの境界を前提にした。AIモデル・推論強度・Provider選択・Embedding Provider・自動課金方針・Avatar・描画品質は今回変更していない。

確認した範囲は、Core起動と停止、Session / Conversation、Brain継続、Memoryの保存と取得、Agent実行境界、World接続・UI・音声、実行設定、関連設計書。全ファイルの全経路を網羅した監査や実機受入完了を意味しない。

## 改善内容

| 領域 | 再現した問題／整理対象 | 変更と効果 |
|---|---|---|
| ChatStoreの保存と復旧 | 旧履歴を読む前の追記、索引書込失敗後の追記で、古い原文が索引から欠ける。末尾の途中行と次の発言が連結する。空にした原文に古い索引行が残る | 通常追記・旧履歴取込・復旧を同じ増分取込処理に統一。原文をflush / fsync後に反映。途中行のbytesを残して改行を補い、次の発言を独立させる。空への短縮も索引transactionをcommitする。追補で、原文fsyncをCommit barrierとしてSidebar metadataを派生SQLiteより先に保存し、索引失敗直後の再起動でもtitle / updated_atが古い状態へ戻らないようにした |
| 旧索引の修復 | 以前の不具合で「ファイル末尾まで反映済み」なのにEntryが欠けた索引は、新しい追記処理だけでは直らない | `user_version=0`の派生索引を一度だけ無効化し、Sessionごとの次回アクセス時にJSONLから再構築。移行済みのcheckpointは維持する |
| AIへ渡す直近履歴 | 全Channel直近80件を取ってから絞るため、他ResidentへのWhisperが85件続くと、対象の公開／個別会話が存在しても空になる。native continuationの古いmarker復旧では、marker以降の全Channelを一度Pythonへ取り出してから公開／個別を絞る経路が残っていた | Channel別のSQLite索引から必要な件数を取得し、追記順で統合。最大20件の契約を維持し、他Channelを混入させない。追補でmarker以降のdeltaも`kind / sender / recipient`条件をSQLiteへ渡し、無関係ChannelのpayloadをPythonへmaterializeしない |
| 履歴表示・既読 | 同じrequest_idの別発言が消える。IDが異なる同文・同時刻の発言がページ連結で消える。旧Entryが重複する | `session + entry_id`を優先する共通識別処理へ統一。旧Entryは各属性と本文の組で識別。Protocol Parserも任意Entry IDを検証する。追補で、同一history page内部に最初から含まれる完全重複legacy EntryもStore取込時に除去する |
| CoreConnection | CLOSING状態の送信を成功扱いする。send例外がUIまで逃げる。古いclose callbackが新接続に余分な再接続を発生させる | OPEN状態確認、共通送信処理、失敗時のfalse返却と再接続、古いSocket通知の無視。UIの既存false処理で入力文を保持。依頼・承認の自動再送は追加しない |
| Coreの終了 | World停止例外でBridge / Coreの片付けが飛ぶ。外部cancelでWorld終了待機Taskが残る | 待機Taskのcancel / awaitを終了処理へ集約し、Launcher停止失敗でもBridgeとCoreの片付けを実行する |
| VOICEVOX | fetchがHeaderを返した時点でTimerを解除し、JSON／音声本文が停止するとTimeoutが効かない | 本文消費まで同じAbortController / Timerを維持。不要なHealth本文をcancel。既存の5 / 10 / 30秒上限を維持 |
| 実行入口と文書 | ルートpackage.jsonに旧構成の`latest`依存と存在しないビルド先が残る | Worldの固定依存とLockfileへ一本化。ルートのtest / typecheck / buildはWorldへ委譲。Coreテスト入口とREADMEを追加し、詳細設計00 / 01 / 02 / 04 / 05とAI_ENTRYを同期 |

### 25万件の合成履歴

実際の会話・記憶を使わず、一時フォルダに1 Session / 250,000件を生成した。公開発言と対象Whisperはそれぞれ100件に1件とし、無関係Channelが大量に続く条件で測定した。定常操作は10回の中央値。Windowsローカルの単発測定であり、すべてのPCでの保証値ではない。

| 操作 | 測定値 |
|---|---:|
| 初回の原文全件取込 | 6,380.85 ms |
| 公開直近20件 | 3.12 ms |
| 対象ResidentのWhisper直近20件 | 3.18 ms |
| UI履歴50件 | 3.06 ms |
| Entry marker以降の差分20件 | 2.89 ms |
| 新規1件の追記（fsync・索引・メタデータ含む） | 32.50 ms |

公開／対象Whisperとも、SQLの実行計画が対応する索引による`SEARCH`であることを確認した。計測用データは削除済み。計測スクリプトで一度SQLite接続を閉じ忘れて一時フォルダ除去が失敗したが、接続を明示closeする形で再測定し、正常終了・除去まで確認した。途中で残った今回作成の一時フォルダ2件も確認して削除した。

Holo追補では25万件Benchmark自体は再実行していない。代わりに、古いpublic markerの後へ無関係Whisperを1,000件置いた回帰テストで、`public_history_after`がSession index JSON 1件と対象Public payload 1件だけをdecodeし、1,000件のWhisper payloadをmaterializeしないことを確認した。

## 残る課題・確認範囲

- **初回移行負荷**：旧派生索引を再構築する最初のSessionアクセスでは履歴量に応じて待ち時間がある。上記25万件の原文取込部分だけで約6.4秒であり、旧索引の無効化を含む実データ全体の移行時間は未測定。通常アクセスの全件scanは復活させていない。
- **復元限界**：再構築できるのは原文JSONLに残った正しいEntry。破損して意味が欠けた原文そのものを推測で復元しない。今回、実際のユーザー履歴・Memory DBの移行や修復操作は実行していない。
- **実機QA**：実Providerへの追加問い合わせ、VOICEVOX実エンジンでの長時間利用、起動中Electronでの手動操作は今回未実施。自動テストと本番ビルドの成功を実機受入完了へ読み替えない。
- **保守性の次候補**：`core/server.py`と`App.tsx`は依然大きく、Protocol routing / Conversation / Task / Presentationの責務を段階的に分ける余地がある。進行中の大きな未コミット更新を一括で組み替えるより、今回のように再現可能な問題を固定してから分離する方が変更を確認しやすい。
- **別工程**：Provider継続の実機確認、Public / Private Memoryの長時間運用、World ReplacementとM3暮らし接続は、既存の工程・検証課題として残る。

既存の未コミット変更を保持し、今回もcommit / pushは行っていない。新たな常駐サーバーやProviderプロセスは起動していない。

最終プロセス確認では、今回起動したテスト・計測プロセスの残存はなかった。一方、作業開始前の15:11 / 15:15 / 15:17に起動した`test_server.py`のpytestプロセス3件（PID 15356 / 8604 / 27728）が存在した。他作業由来のため今回停止していない。
