# Nirai 詳細設計 07：タスク実行と拡張機能

Product Goalは [Nirai_基本設計.md](../Nirai_基本設計.md)、設計判断ルールは [Nirai_設計ガバナンス.md](../Nirai_設計ガバナンス.md)、実作業を行うAgent Runtimeと承認・質問・Plan・進捗UIは [11_AgentRuntimeと実行UI.md](11_AgentRuntimeと実行UI.md) を正とする。

## タスク実行

### 概要

タスク実行とは、Masterが仕事を任せたいResidentへ自然に依頼し、そのResidentが必要に応じて他Residentへ相談しつつ、対応するAgent Runtimeで実作業して報告する仕組みである。

### 標準入口：Direct / Delegated

- MasterがResident Focus中にUIで`仕事`を明示して送った自然文は、そのFocused ResidentへのDirect Taskとして扱う。`/task`等の既存の明示Task Shortcut / APIもTask入口として残してよい
- `/task`専用文法を日常利用の必須条件にしない。自然文で依頼できることと、通常会話をTaskへ自動昇格することは別契約とする
- Direct Taskとして明示された入力で相手が明確で、実作業依頼であることも明確なら、そのResidentを既定担当とする。全Residentへ立候補を求めない
- `会話`modeのWhisperや通常Sayは、相手が明確、`@Resident`指定、または文面が実作業依頼に見えても、それだけを理由にTaskへ昇格しない。相談なのか実作業なのか曖昧な通常会話は会話のまま扱い、Nirai側が推測してFile変更へ進めない
- CouncilはMasterが明示した場合、またはTask化後に担当Residentが追加相談を必要とした場合に使う。通常Say / WhisperをCouncil経由で暗黙Task化する入口にも使わない

### Council：必要な時だけ

担当Residentが他Residentの知見を必要とする場合、方針が割れる場合、複数AIの意見が有益な場合はCouncilを開始できる。Masterが明示的にCouncilを依頼してもよい。

- Council参加者は必要なResidentだけとし、全Resident固定にしない
- Councilは担当決定の必須関所ではない。Direct Taskでは担当Residentを維持したまま相談だけ行ってよい
- 別Residentへ担当移管する必要がある場合は、`agent_work` Capability、現在負荷、Task内容を確認し、Masterへ担当変更を分かる形で報告する
- 相談の安全上限は持つが、M4初期実装の「全員1巡 + volunteer + first eligible」を永久Algorithmにしない

### 共通フロー

1. **依頼受理**
   - Task IDを発番し、Task metadata正本を`runtime\workspace\<タスクID>\task.md`へ保存する
   - 指名Resident、依頼文、対象Folder、origin Conversationを保持する
   - 実作業cwdは指定なしならTask workspace、明示Targetがあれば後述のnamed targetへ分離する
2. **必要なら確認 / Council**
   - 実作業依頼か曖昧ならMasterへ確認する
   - 担当Residentが必要と判断した場合だけCouncilを開始する
   - Council中もPrivate Memoryを他Residentへ漏らさない
3. **担当確定**
   - Resident Roleを担当決定の正本にする。通常Taskの自動候補は`executor`だけ、`resident`と`integrated_auditor`は通常候補へ入れない
   - Direct Taskでは指名Residentを既定担当とし、Roleと`agent_work` Capabilityの両方を検証する。明示指名された`integrated_auditor`は統合監査用途の専門担当としてのみ扱う
   - `commander`は実行Capabilityを持つ場合、実行者不在時のFallback担当になれるが、通常Taskの第一候補にはしない
   - FreshなProvider Usage SnapshotでHard Limitへ到達したResidentは新規割当候補から外す。残量が少ないだけでは固定閾値で禁止せず、同等候補なら残量の多いResidentを優先できる
   - Usageが取得不能・staleの場合はUNKNOWNとして扱い、0%や100%を推測しない
   - Councilで担当変更する場合も、最終担当と理由をMasterへ明示する
4. **実行**
   - `AgentRuntimeManager`が担当ResidentのProviderに対応するAgent Runtime Adapterを起動し、`agent_session_id`を発行する（11参照）
   - Task Metadataと実行UI履歴は`runtime\agent_sessions\<agent_session_id>\`へ保存し、実際のcwdは`tasks.allowed_dirs`内の指定対象へ固定する
   - 担当Residentを`work`状態へ遷移させる。work状態の視覚表現はWorld側が決定する
   - 会話UIへ`task_update`（running）を出し、詳細なCommand / File変更 / Approval / Question / Plan / Todo等は11のAgent Eventで逐次表示する
   - 上限時間は初期値を持てるが、Provider特性・Task種別・実測で合理的に設定し、永久固定値にしない
5. **報告**
   - 成功：Agent Runtimeの最終結果要約と成果物一覧を担当の`bubble`＋`task_update`（done）でMasterへ
   - 失敗・上限超過・Cancel：`task_update`（failed / cancelled）と理由。**失敗を成功と偽らない**。Providerが成功を返しても必要な成果物検証に失敗した場合はdoneにしない
   - 詳細EventはAgent Sessionへ保持し、会話履歴へCommand全文や大量Diffを複製しない
   - タスクの公開経緯と結果はWorld Memoryへ残す。Residentごとに同じ記録を複製しない

### Current Role Routing / Direct Task

2026-09-12 Currentでは、Resident RoleをTask routingの正本とする。旧「全Resident consult→volunteer→first eligible volunteer」を通常の担当決定Algorithmには使わない。

- `task_request`に`resident`がある場合は**Direct Task**としてCouncilを通さず、そのResidentを明示候補として検証する。`resident` Roleは実作業不可。`executor`は通常実作業可。`integrated_auditor`は通常自動候補にはせず、Master明示またはCommanderの統合監査Workflowからだけ利用する。`commander`は自身がAgent Work可能な場合だけ実行できる
- Direct assigneeはQueueへ永続化し、Core restart後も同じResidentを維持する。復旧時にDirect assigneeが無効化・Capability不整合ならQueueをfail-closedする
- `resident`指定なしの通常Taskは、enabledな`executor`だけからRole routingする。ProviderがFresh Hard Limitなら除外し、そうでなければ利用可能枠の小さいResidentを温存するためFresh残量を優先度に使える。ただし残量が1%等の低値だけを理由に固定閾値で禁止しない
- 実行可能Executorがいない場合だけ、Agent Work Capabilityを持つ`commander`をFallback候補にできる。`resident`や`integrated_auditor`へ通常Taskを自動移管しない
- Provider Usageがstale / UNKNOWNならHard Gateにせず、取得不能を利用可能と断定もしない。Task開始直前にもUsageを再取得してFresh Hard Limitを再検証する
- `task_update.assignment_policy = direct | role_routing`と`assigned_resident`を通知する
- 通常Whisperを文字列heuristicだけで自動Task化しない。MasterがUIで`仕事`を明示した入力だけをDirect Taskへ昇格する
- Councilは相談が必要な時の別機能として残すが、通常Taskの担当選定関所にはしない

### Integrated Audit上位Workflow

統合監査は通常Task routingとは別の上位WorkflowとしてCommanderが判断する。Coreに「5時間経過したら必ず監査」という固定Timerを置かず、**成果のまとまり・変更量・重要度・前回監査からの経過・Auditor Usage**をまとめて判断する。

- 小Taskごとに`integrated_auditor`を呼ばない。明確な大区切りを優先し、概ね5時間分の開発成果は監査タイミングの**目安**として扱う
- 5時間経っても機能群が未完成なら延期でき、逆に4時間程度でも大きな完成単位へ達したなら監査してよい。時間だけで`due=true`にしない
- Holo Commanderは`holo_snapshot`からResidentのRole / Provider / Model / Availability / Usage Budgetと、`integrated_audit.last_completed`を取得し、Workflow文脈と合わせて判断する
- 監査すると決めた場合はHolo Local Clientの`audit-start <Dive Session ID> <target> <text>`を使う。Coreはenabledな`integrated_auditor`だけからFresh Hard Limitでない候補を選び、`IA-*`の**書込可能Task**として起動する。通常`executor`や`commander`へ監査を代替Routingしない
- `IA-*`は通常Taskと同じAgent Runtime / staging / rollback / destructive-delete Master escalationを使う。統合監査者はReview専用ではなく、必要ならSource修正・Refactor・Test追加・不要実装置換まで行える
- Nirai自身をTargetにする`IA-*`だけはNirai Repository Rootを専用write targetとして解決できる。通常TaskのNirai本体write禁止は維持し、`.git / runtime / .env* / avatars / material / world_memory / node_modules`等の生成・Credential・Asset領域は統合監査staging / apply対象から除外する
- `IA-*`完了後も通常Task Auto Resumeと同じ所有Conversationへ戻る。Commanderは直後に別の統合監査を連鎖起動せず、その完了を次回cadence判断の基準にする

Quotaは監査を「いつ使うか」の判断材料であり、安全Gateとは分離する。通常時はCommanderが週次等の残量を温存して監査を延期してよいが、Masterが「残りを使ってよい」「今週分は使い切ってよい」「Astraで監査して」等と明示した場合、その**温存判断を上書き**して利用可能な残量を使える。30%等の固定残量閾値をCoreへ持たせない。一方、Fresh Hard LimitはMaster明示でも越えず、Provider側で実行不能なら監査を開始しない。

Resident自身が作業途中に追加Councilを開始するDelegation Orchestratorは将来拡張可能だが、Phase 1のDirect Task成立条件には含めない。

Evidence：`../evidence/reports/Nirai_DirectTask_検証結果_2026-09-07.md`

### Provider Usage Limit / Fallback

Task途中でProvider側Quota / Rate Limitへ到達した場合は、一般FailureやCore Crashと区別する。単なるError文字列だけで推測せず、Providerの構造化codeまたは十分強いquota / rate-limit evidenceがある時だけ`provider_quota_exhausted`または`provider_rate_limit`へ分類する。

1. Providerへ停止要求を送り、Provider Process / Agentが止まったことを確認する
2. Cursor / CodexのWritable Workは実Workspaceを直接触らずStagingで作業しているため、停止後のStaging差分を`runtime/agent_sessions/<agent_session_id>/partial_work/`へ凍結保存する。create / modifyの現Byteとdelete情報、baseline/staged Hashをmanifestへ残す
3. Partial Workはこの時点で実Workspaceへ自動適用しない。Quota中断でMaster Approvalや既存Safety Gateを迂回しない
4. Agent Sessionへ`interruption_reason`と`partial_work_path`をDurable保存し、`run_state=interrupted`へ確定する
5. Session固有Process / Credential / staging cleanupが収束するまでWorkspace Resourceを保持し、収束後に解放する。次Workerが同じWorkspaceへ入れるのはその後だけとし二重実行を防ぐ
6. `task_update` / Agent UIへProvider利用制限で中断したことを明示し、Commanderへ制御を返す。**別Workerへ自動で投げ直さない**。CommanderまたはMasterがPartialを確認したうえで、続行・rerun・破棄等を選ぶ

Quota中断時のPartial保存は、Providerが途中まで行った良い成果を失わないためのRecovery Evidenceであり、完成済み成果として扱わない。Provider停止前のStagingを読み取って保存すること、未レビューPartialを自動Applyすること、Resource解放前に別Workerを同Workspaceへ開始することは禁止する。

### Task Queue / Resource Dispatch

Currentでは、Task受付のDurable QueueとAgent実行Concurrencyを分離する。QueueはCrash recoveryとpre-Agent相談順序を守るために残すが、**Agent Session全体1件**を永久制約にはしない。

- Queue正本は`runtime\task_queue.json`。`active` pre-Agent Task 1件と`pending`をtemp write + replaceで原子的に保存する
- pending上限は32件。Task本文はrequest入口とQueue保存時の双方で32,000文字を上限とし、超過内容を部分保存しない。Queue Store自身もpersisted File 8 MiB上限を持つ
- Queue待機中は`task_update phase=queued`と`queue_position`をWorldへ通知する
- dispatcherはpending順を基本とするが、先頭TaskのWorkspace / Concurrency Resourceだけが使用中なら、後続の独立Workspace Taskを先に開始してよい。Resource競合でTask自体をfailedへ落とさない
- Agent Runtimeの既定Concurrency Budgetは4 Session。実行開始時に同一Workspaceのread/write競合を再検証する。read-only同士は同一Workspaceでも並行可能、Writeは同一WorkspaceのReader / Writerと排他する
- 同一ConversationのTurn順序、Approval / Question / Plan routing、Session専用Credential / staging等は各Session / Resource単位で分離する
- Core再起動時、相談中だった`active` pre-Agent Taskはpendingへ戻して再相談する。古いWorld request IDは再利用しない
- ただし同じ`task_id`のAgent Sessionが既にDurable化されている場合は、Agent Session作成後・Queue active解除前のCrashとみなしQueue recordを再実行せず除去する
- Queue Fileが壊れている、Path / target / origin Chat Sessionの整合が取れない、または永続化に失敗した場合は推測で実行を続けずfail-closedする
- Queue待機中も元Chat Sessionの削除 / World Memory Forget、Resident削除 / Brain変更を拒否する

### 安全枠（厳守）

- 作業できるのは**許可ディレクトリのリスト**（config.tomlの`tasks.allowed_dirs`）の中のみ
  - 既定値は`runtime\workspace\`だけ。Masterがリストに追記して対象を広げる（例：他プロジェクトのフォルダ）
  - タスク依頼時に`/task @対象フォルダ名 依頼文`の形で対象を指定できる（指定なしは`runtime\workspace\<タスクID>\`）
  - `対象フォルダ名`は`tasks.allowed_dirs`に登録された外部Rootのbasenameとcase-insensitive一致するものだけを許可する。Nirai内部状態Root `runtime`とその配下は、`tasks.allowed_dirs`へ明示登録されていてもnamed targetへ選べない。任意Path・相対Path・`..`を入力から解決しない。未知名・不正名・同名Rootが複数で曖昧、または対象Rootが消失している場合はQueue投入時・Queue復旧時・Task Flow開始時・相談終了後のProvider起動直前に再検証してfail-closedする
  - 通常Agent cwdとして`runtime`配下で許可するのは、そのTask自身の`runtime\workspace\<タスクID>`だけとする。`runtime\agent_sessions`、`runtime\chat_sessions`、Queue正本、他Task workspace等のNirai内部状態は`tasks.allowed_dirs`へ書かれていてもProvider cwdにしない。cwd生成を許すのは対象未指定時の自Task workspaceだけで、明示cwdは既存Directoryであることを必須とし、Manager / Adapterの再検証で消失していても`mkdir`しない。Cursor等が安全隔離のため内部stagingを使う場合は通常Task cwd resolverとは分離した専用内部経路で扱う
  - named targetを指定してもNirai管理用`task.md`は設定順に依存せず`runtime\workspace\<タスクID>\`へ固定し、実Project直下へ混入させない。AgentRuntimeManagerへ直接別metadata directoryを渡す経路も拒否する
  - リスト外のパスが依頼に含まれていたら、実行せずMasterに確認を返す
- **通常Taskから動いているNirai本体（core\ world\）を直接書き換えることは禁止**。例外は上記のCommander管理下`IA-*`統合監査だけで、専用Root解決・staging・保護領域除外・rollback・Master destructive gateを通す。任意Task IDや通常Residentへ同じ権限を広げない
- Git操作・外部送信・システム設定変更・秘密情報の取り扱いは既定で無許可実行させない。Task達成に必要な場合は11のApproval UIで「何を・どこで・なぜ」をMasterへ提示し、明示承認された範囲だけ許可する。ProviderのSandboxやPermission機構は追加防御として使うが、Nirai側の境界を代替しない
- 成果物を許可ディレクトリ外へ配置する必要がある場合は、報告に「移動先の提案」を書いてMasterが手動で移す

### 拡張開発タスク（住人がNiraiの拡張を作る）

Niraiの拡張は住人自身が作れる。拡張は隔離構造（後述）なので、**M4の通常Task + Agent Runtimeの仕組みのままで安全にできる**。

1. Masterが担当Residentへ依頼する（例：「weather拡張を作って。本書07の拡張の作法に従って」）。`/task` Shortcutを使ってもよい
2. 担当住人がworkspace\<タスクID>\の中に拡張フォルダ一式（extension.json＋main.py＋動作説明）を作る
3. 報告を受けてMasterが承認したら、拡張フォルダをextensions\へ移す（移すのはMaster。将来self-buildで自動化）
4. 次回起動（または再起動）でロードされる。壊れていてもその拡張だけ無効化され、本体は無傷

### self-build（本体改修。M5+で整備）

Nirai本体の改修をNiraiの中で行うための完全な更新・再起動・rollback手順。**通常Resident / 通常TaskからNirai本体を直接改修するTaskは引き続き受け付けない**。Currentの`IA-*`統合監査は、Commanderが大区切りで起動する限定的なSource working-tree監査・修正経路であり、commit / push /自己再起動 / build切替を自動化する完全self-buildとは別物とする。

2026-09-12 Currentでは、日常保守の基本は引き続きIncident→Holo Local MCP修正→Fresh Review→回帰である。加えて大きな開発単位では、Roleが`integrated_auditor`のResidentへ`IA-*`を発行し、既存Agent staging安全境界内でNirai Sourceの監査・必要修正を行える。`.git / runtime / Credential / private asset`は対象外とし、重大破壊・commit・push・再起動は従来どおりMaster決裁または別手順を要求する。

1. 住人が本体コードの複製をworkspace内に作って変更案を作る
2. 変更の差分と影響範囲をMasterへ報告する
3. Masterが承認したら：本体をバックアップ→適用→再起動→起動確認
4. 起動に失敗したら自動でバックアップに巻き戻して報告する

※self-buildの詳細設計は、M5で着手すると決めたときに個別に書く

## 拡張機能（Extension）

### 概要

拡張機能とは、`extensions\<拡張名>\`に自己完結で置かれ、Coreが起動時に読み込む後付け部品である。**外す＝フォルダを消すだけ**で、本体に影響を与えない。

- 前提
  - 本章の`Extension`はPythonモジュール（Coreと同一プロセスで動く）を指す
  - 本体は拡張が1つも無くても全機能が動く。拡張が消えたら、その機能が無かったことになるだけ（縮退動作）
  - HoloはこのExtension形式へ押し込まない。World UI / ChatGPT Web Surface / Local MCP Bridgeを持つより広い`Holo Addon`として [12_HoloAddonとChatGPTDive.md](12_HoloAddonとChatGPTDive.md) を正とする

### フォルダ構造

```
extensions\<拡張名>\
  extension.json    # マニフェスト（宣言ファイル）
  main.py           # 入口。setup(api) 関数を必ず持つ
  （その他、拡張が必要とするファイル）
```

### extension.json の形式

| フィールド | 型 | 必須 | 説明 |
|-----------|----|------|------|
| name | string | ○ | 拡張名（フォルダ名と一致） |
| version | string | ○ | 拡張自体の版 |
| description | string | ○ | 一言説明（会話UI通知に使う） |
| hooks | array | ○ | 使うフック名の一覧（下記） |
| permissions | array | ○ | 必要な権限。"network"（外部通信）/ "filesystem"（runtime外の読み書き）/ なしは `[]` |

- permissionsに"network"か"filesystem"を含む拡張は、初回ロード時に会話UIへ通知し、config.tomlで明示的に許可されるまで動かさない

### フック一覧（Coreが拡張に開放する接続点）

| フック | 呼ばれるタイミング | 拡張ができること |
|--------|------------------|----------------|
| on_start(api) | Core起動時 | 初期化・定期ジョブの登録 |
| on_tick_context(resident, context) | 生活ティックの入力組み立て時 | contextへ情報を追記（例：天気） |
| register_brains() | 起動時 | 追加Brainドライバの登録（serina等）。Codex / Claude / Cursor / Gemini / Local LLMの初期Provider群はCore側で扱う。Holo Addonは通常Brain Driverとして登録しない |
| on_master_input(text) | 会話UI入力の受信時 | 入力の横取り・変換（例：将来の音声入力）。通常はそのまま返す |
| on_session_end(session) | セッション終了時 | 拡張固有の後処理 |
| world_effect(effect) | 任意（api経由で随時） | Worldへ意味的な演出要求（例：光を強くする）。Coreが検査してWorldへ中継 |

- フックのシグネチャ詳細（引数の中身）は実装時にcore\extensions\のAPI定義ファイル1箇所に集約し、拡張はそれだけをimportする
- World側の具体的なエフェクト実装は04と09に従う。拡張は「雨」「光を強く」などの意味だけを送る

### ロードと隔離の規定

1. Core起動時にextensions\を走査し、extension.jsonを読む
2. 読み込み順：フォルダ名の辞書順（依存関係は作らない。拡張同士は互いを知らない）
3. ロード失敗（jsonが壊れている・setup例外）：その拡張だけ無効化し、ERRORログ＋会話UIへ`notice`
4. 実行中のフック内で例外が起きた場合：その呼び出しを捨てて本体は続行。同じ拡張が**連続3回**例外を起こしたら、その拡張をその日の間無効化して会話UIへ通知
5. 拡張の削除：Nirai停止中にフォルダを消す。次回起動時に何も起きない（参照が残らない設計をCore側が守る）

### Holo Addonとの境界

旧`chatgpt-mcp`郵便受け方式は廃止する。Holoを通常Resident Brainとして登録せず、ChatGPT Web ConversationをHolo Whisperの正本として利用する専用Addon方式へ変更した。

- Holo Addonの要件正本は [12_HoloAddonとChatGPTDive.md](12_HoloAddonとChatGPTDive.md)
- Sleep中のEvent保管はHolo Addon内部Queueとして持ってよいが、それを通常Brain Driverの郵便受けProtocolにはしない
- Holo Addonが停止・未導入でも、本章の通常Extension / Task / Agent Runtimeは成立する

- Voice再生は拡張ではなくWorld標準Presentation（04参照）。特定Providerを初期依存にせず、実装時に選定したProvider Adapterを利用する
- voice-input / browser / weather 等の各拡張の詳細設計は、作ると決めたときに個別に書く（先回りで書かない）
