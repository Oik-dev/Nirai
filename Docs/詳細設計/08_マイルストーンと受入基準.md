## 1. 共通ルール

### 完了判定

Milestone / Sliceは、少なくとも次を満たして完了とする。

- Active Designと実装が一致する
- Product Goal / Invariant違反がない
- 必要な自動Testが成功する
- 見た目・操作・Provider実通信等、自動Testで代替できない項目は実機QAする
- 失敗・Cancel・再起動等の主要Failure Pathが確認されている
- 新規Findingが残る場合は完了扱いにしない。ただし外部Provider制約をMasterが明示受容した場合はProvider Constraintとして記録できる
- 実装後のEvidenceは対応する`*_検証結果.md`へ残す

### 設計品質

「Testが通った」だけでは完了としない。

- 合理性
- 効率性
- 保守性
- Operational Simplicity
- 5年利用時のScaling
- Provider / Model差し替え容易性

を`Nirai_設計ガバナンス.md`に従って確認する。

### Reference-First

大規模実装、新Subsystem、外部Provider統合、主要方式の置換、独自Algorithm等へ着手する前にReference-First Gateを通す。

過去のAITuberKit / AIAvatarKitカンペだけで調査完了とせず、その時点の公式機能・成熟OSS・Reference ImplementationをWebで再確認する。

## 3. M3：暮らしと長期Memory

### 目的

Residentが単に会話へ応答するだけでなく、Worldの現在を知覚し、Brainを無駄遣いせず自然に存在し、必要な時に数年規模の過去を思い出せる状態を成立させる。

### 現在完了しているもの

- World Memory Retriever先行Slice
- Public World Memory lossless Raw SQLite Source
- Public Structured Atomic Memory / Current Fact + provenance / correction / hypothesis gate
- Raw FTS5 + sqlite-vec + Gemini Embedding 2のabstention-oriented Hybrid Recall
- Gemini 3.5 Flash Lite Background Structured抽出
- Session単位ForgetでPublic Raw / Structured / FTS / Vector残存0
- Cloud停止・Quota枯渇時のRaw + Local FTS縮退
- Raw未移行Legacy Sessionだけ旧Episode Retriever fallback
- 旧Public Episodeの全体read+rewriteを廃止しappend-only compatibility View化
- Private Resident別SQLite Raw + Local FTS5 + Legacy JSONL idempotent import
- Private Gemini Embedding 2 768d Semantic Index + abstention-oriented Hybrid Recall
- Private old-Whisper semantic retrievalを実Whisper Contextへ接続し、Public Contextへの非漏洩を回帰
- Public / Privateは同じGemini Embedding 2 rolling 24h quota guardを共有し、Background最大400 / Query最大500 / 合計900をNirai全体で超えない。Nirai RuntimeはローカルBGE-M3を使わない
- Provider native Working ContextでWorld / Private Memory Evidenceの重複注入抑制
- Public / Private混入防止の既存安全境界
- Memory Evaluation Harness v1 / Golden 11 Case / 初回Ablation + Gemini Follow-up
- Public / Private Raw+FTS 250k Synthetic steady-state Scale

現行Retriever / EvaluationのEvidence：

- `../M3_Retriever_検証結果.md`
- `../Nirai_MemoryEvaluation_初回結果_2026-09-06.md`
- `../Nirai_MemoryScale_検証結果_2026-09-06.md`
- `../Nirai_PrivateMemorySemantic_検証結果_2026-09-06.md`

旧Episode RetrieverのSAFEは当時のSlice実装品質を示す。2026-09-06の長期Memory Product Requirement更新後、Public側はEpisode正本を廃止し、lossless Raw + Structured + Hybrid Recallへ製品更新した。初回Evaluationでは`Temporal Fact + abstention-oriented Gated Hybrid`が11/11、Gemini Embedding 2へ置換したFollow-upでも11/11 / false recall 0、Structured抽出Golden 7/7を確認した。Private側はResident別SQLite Raw + Local FTSを維持しつつ、2026-09-07 Master判断でSemantic ProviderもGemini Embedding 2へ統一した。**製品実装そのものをStructured Fact OverlayなしでPrivate 8 Caseへ通し8/8 / false recall 0**、Live Smokeでもdocument embedding / semantic recall / vector込みForgetを確認したため、Private Structured ContinuityはCurrent blockerではなくChallengerへ降格する。旧BGE-M3結果は比較Evidenceとして残すがCurrent Runtimeには含めない。Public / Private Raw+FTSは250k Syntheticでsteady-stateを確認済み。Public / Private Cloud Vector Indexの年単位maintenanceまで含むNirai Memory全体の最終方式とはまだ扱わない。

### 未完了 / 再設計対象

1. World Observation
2. World Natural Idle Scheduler
3. Brain生活ティック
4. Private Structured Continuity / Atomic FactはGolden拡張でRaw Hybrid不足が出た場合だけProductへ昇格するChallenger
5. Public sqlite-vec / Gemini IndexのCloud quota長時間運用確認。Embedding Model / Dimension変更時のRawからのvector-only rebuild queueとbatch rebuildは実装済み

### M3長期受入条件

#### World Observation

- Worldの現在状態を意味情報としてCoreへ渡せる
- Three.js座標やShader値等の生実装情報をBrainへ大量投入しない
- Observationが無い・古い場合に現在状態を捏造しない
- Master Focus、近くのResident、行動状態、時間帯等を必要に応じてContextへ使える

#### Natural Idle

- Brainを呼ばず、数十秒〜数分単位の自然な小移動・漂い・姿勢変化が成立する
- Resident全員が同時に同じ動きをしない
- 会話・Task・明示Actionを邪魔しない
- Natural IdleのためにWorld Memoryを汚染しない

#### Brain生活ティック

- 意味判断が必要な時だけBrainを使う
- Budget / Provider quotaを無視して暴走しない
- `talk_to`、意味Location選択、Masterへの低頻度発話等を行える
- Private Memoryを公開生活Contextへ漏らさない

#### Long-term Memory

- Public / PrivateともlosslessなRaw Durable Sourceを持つ
- Structured ContinuityとRetrieverをRaw正本から分離する
- Structured Memoryは元Raw Entry / Eventへ遡れるprovenanceを持つ
- MemoryOwner / MemoryScopeをStorage・Index生成前段で強制し、Private leakをquery filterだけへ依存させない
- Episode要約・240文字excerpt・小さな`context.md`を唯一の長期正本にしない
- UI Chat履歴削除とMemory保持を分離できる
- 明示ForgetではRaw / Structured / Derivedを整合して削除でき、Forget対象が後続retrieval / cache / promptから再出現しない
- Correctionでは過去Rawを歴史として残しつつ、現行Factを優先できる。Semantic similarityだけで無関係Factを自動supersedeしない
- 同一Whisper ConversationでProvider native continuationを使える場合、毎Turn固定件数のRawを再送しない
- 直近履歴取得で全履歴scanしない
- 1発言追記で巨大Memory全体を書き直さない
- Embedding / Vector Indexが停止・遅延してもRaw保存を失わず、FTS / Structured Context等へ縮退して通常会話を継続できる
- 5年相当の履歴量で、検索・追記・起動・通常会話が実用範囲を維持することをTestまたはBenchmarkで確認する。Raw / FTS steady-stateは250k Syntheticで確認済み。Vector / Cloud / Structuredまで含む長時間運用は別途確認する

### 実装着手前の必須調査 / Evaluation Gate

2026-09-06に長期MemoryのReference-First再調査とSerina既存実装監査を実施した。

- `../Nirai_Reference-First調査_長期基盤_2026-09-06.md`
- `../Nirai_SerinaMemory監査_2026-09-06.md`
- `../Nirai_MemoryEvaluation設計_2026-09-06.md`
- `../Nirai_MemoryEvaluation_初回結果_2026-09-06.md`
- `../Nirai_MemoryScale_検証結果_2026-09-06.md`
- `../Nirai_PrivateMemorySemantic_検証結果_2026-09-06.md`

調査の結果、Serinaをそのまま捨てて置換すべき単一Frameworkは確定しなかった。一方、Raw + Structured Hybrid、FTS/BM25 + Vector、Atomic Proposition、Temporal Hierarchy等に改善余地がある。初回Ablationではnaive RRFがSemantic-onlyより誤想起を増やしたため、「複数Signalを無条件に足す」方式は採らず、abstention / confidence gateを第一級に扱う。

したがってMemoryの物理実装を固定する前に、最低限次を同一条件で比較する。

- Baseline A：Serina方式相当
- Baseline B：A + Raw retrieval + FTS/BM25 + Lexical/Semantic Fusion
- Baseline C：B + Atomic Proposition + Entity / Participant / Privacy Scope
- Baseline D：C + Episode / Scenario / Durable ContinuityのTemporal Hierarchy

複雑なBaselineが単純Baselineを僅差でしか上回らない場合は、単純な方式を採用する。

Evaluationでは少なくとも次を測る。

- factual / semantic / exact lexical recall
- multi-session / temporal reasoning
- correction / contradiction / supersede誤爆
- abstention / false recall / extraction hallucination
- preference / relationship / cognitive latent constraint
- Forget後のRaw / Structured / Index残存0
- Public / Private cross-contamination 0
- pre-birth World HistoryをPersonal Experienceと誤認しない
- query latency / context token / Brain call / CPU / RAM
- Gemini Embedding query latency / quota / failure fallbackとLocal FTS縮退
- 5年Synthetic Scale

調査せず独自Vector DBや独自Memory Databaseを作らない。Cross-Encoder、Graph DB、追加常駐Model、大型Memory Frameworkも、Evaluationで明確な改善を示すまで製品依存へ追加しない。

## 4. Conversation Continuity横断Slice

### 目的

Resident / Holo / Cursor / Codex等との長いConversationで、Nirai Identityを維持しつつProvider native Contextを効率的に利用する。

### 現在

- Holo→Cursor：native Session continuation対応済み
- Holo→Codex：native Thread continuation対応済み
- 通常Resident Cursor / Codex：native continuation + unseen delta送信 + 静的Context再送削減まで対応済み
- 通常Resident Gemini：Interactions `previous_interaction_id` continuationを実装・自動回帰済み。実Provider Live 2-turn Smokeも2026-09-07にSAFE相当を確認済み
- Whisper：公開Chat Session従属を廃止し、Resident単位Private Channel + Provider native Working Contextへ移行済み。Nirai独自の一定Turnローテーションは行わず、Provider native compaction / resumeを優先する

Evidence：

- `../ConversationContinuity_検証結果_2026-09-06.md`
- `../Nirai_Reference-First調査_Whisper長期Conversation_2026-09-06.md`

### 受入条件

- Nirai Conversation ID / lifecycleはNiraiが正本
- Provider Session / Thread IDはTransport Contextとして保持する
- 同一Conversationの後続TurnでProvider native continuationを利用する
- 通常Turnで過去N件のRawを毎回無条件に再送しない
- Persona / Skills / 固定会話ルール等の既共有静的Contextも毎Turn再送しない
- 同じMemory Evidenceを同一native Working Contextへ毎Turn再注入しない。内容変更・Core再起動・Provider reset・検知されたcompaction後は再注入可能にする
- 新しい公開Chat Sessionは新native Contextを開始し、過去の別SessionはWorld Memory Retrieverから関連分だけ参照する
- Whisperは公開Chat Sessionとは独立したResident単位Private Channelとし、5年分RawをProvider Contextへ全投入しない
- Whisperの長大化対策としてNirai独自の一定Turn Sessionローテーションを作らず、Provider自身のresume / compactionを優先する
- compactionを検知できるProviderではnative Conversation IDを維持し、Nirai側のcontext delivery cacheだけを無効化して必要Contextをrefreshする
- compactionを検知できないProviderでは推測でSessionを捨てず、resume/load/保持期限切れ等の実Failure時にNirai Memory / Structured Continuity / 必要RawからWorking Contextを再構成する
- Public / Private / participantの異なるConversationを同一native Sessionへ混ぜない
- Brain交換後もResident Identityは維持する
- 同一ConversationのTurn Queueを保証する
- 独立ConversationまでGlobal 1本へ不必要に直列化しない

### 2026-09-07 Phase 1 Update

旧M4 SAFEは失効しない。その上にPhase 1長期利用更新を重ねた。

- Focused Residentで`会話 / 仕事`を明示切替し、`仕事`時は自然文をそのままDirect Taskへ送れる。`/task`は互換Shortcutであり必須ではない
- 指名Residentがある`task_request`はCouncilを通らず直接担当し、Queue / restartでもassigneeを保持する。実作業不能でも別Residentへ自動移管しない
- Global 1-Agent制約を撤去し、既定4 Session Budget + Workspace read/write Resource Policyへ移行した
- 独立Workspace Workとread-only Conversation / Reviewを安全境界が独立する範囲で並行可能にした
- Core crash後の`interrupted` Sessionは自動Write resumeしない。`resume`はProvider Session IDに加えてAdapterが`crash_resume` Capabilityを明示した場合だけ提示し、それ以外は`rerun / abandon`を提示する。Current Built-in Adapterは`crash_resume`未宣言

Evidence：

- `../Nirai_DirectTask_検証結果_2026-09-07.md`
- `../Nirai_Phase1基盤完成_検証結果_2026-09-07.md`

Resident自身が実作業途中に別Residentへ担当移管・追加Councilを組み立てるDelegation Orchestratorは将来拡張であり、Direct Task成立の必須関所にはしない。Master明示Councilは`resident`無しTaskの互換経路で利用できる。

### 長期M4受入条件

#### Direct Task

- Masterが指名Residentへ自然言語で仕事を依頼できる
- 相手と実作業意図が明確なら全Resident Councilを経由しない
- 実作業意図が曖昧ならFile変更前にMasterへ確認する
- 指名Residentが`agent_work`非対応なら勝手に別Residentへ移管しない
- Councilは担当ResidentまたはMasterが必要な時だけ開始できる
- 担当変更時はMasterへ分かる形で通知する

#### Safety

旧M4 SAFEで成立した次の境界は維持する。

- allowed_dirs
- Project / runtime boundary
- Master Approval
- Provider Permissionだけへ安全を丸投げしない外側境界
- Credential isolation / cleanup
- fail-closed
- bounded Event / Diff / stdout
- Cancel / TimeoutでProcessを放置しない
- Provider固有ProtocolをWorldへ漏らさない

#### Concurrency

- 同一Task / SessionのTurn順序を保証する
- 同一Workspace Writeを競合させない
- Providerが必要とする同時実行制限を守る
- Credential / staging等のSession専用Resourceを共有しない
- 独立Resourceのread-only Review / Conversation /別Project Workまで全体1件へ固定する場合は実測理由を示す
- 並列化する場合、Approval / Question / Plan responseを必ず正しいSessionへroutingする
- CPU / Memory / Subscription枠をConcurrency Budgetで守れる

#### Recovery

ProviderがCore crash後も安全に再接続できるnative resumeを持ち、Adapterが`crash_resume` Capabilityとして明示した場合だけ、Masterへ`resume existing provider work`を追加提示する。

Current共通選択肢：

- fresh rerun
- abandon
- resume existing provider work（`crash_resume`対応Providerのみ）

Provider Session / Thread IDが保存されているだけでは`resume`可能とみなさない。Crash後にWrite Workを自動再開せず、Current Built-in Adapterでは`rerun / abandon`だけを返す。

## 7. World Replacement：DNA → UE4.27 feasibility / migration

### 位置づけ

このPhaseは、M0〜M4のCore基盤を第一完成させた直後に行う独立工程とする。

目的は、現行Three.js海中Worldを磨き続けることではなく、DNAの既存Scene / Assetを土台としてUE4.27上へNirai Worldを載せ換えられるかを実機で確認し、可能ならそのまま新Worldへ移行することである。

現行Three.js海中Worldは削除しない。**DNAを含まない配布可能な標準World候補**、Fallback、将来の再整備対象として凍結・退避し、当面のWorld品質向上投資は止める。

DNA由来WorldはMasterローカル専用の**Private World Addon**として扱う。DNA由来Asset / SceneをNirai本体、公開Repository、配布Packageへ含めない。Addonが存在しなくてもNirai本体と配布可能な標準Worldが成立することを必須とする。

詳細方針は`../Nirai_DNA_UE4.27_WorldAddon方針_2026-09-06.md`を正とする。

### Feasibility Gate

実装開始前にReference-Firstで次を確認する。

- DNAから実際に取得・再利用可能なScene / Mesh / Material / Texture / Animation / Lighting / Shaderの範囲
- UE4.27へ持ち込める形式と変換手段
- Runtime上で再現が必要なものと、Assetとして抜き出せるものの境界
- Nirai Core / World ProtocolをUE側へ接続する方法
- VRM ResidentをUE4.27へ載せる現実的手段
- 利用条件 / 再配布条件 / 私的利用と配布版の境界
- AIまたはCLIからUE4.27制作工程をどこまで自動化・再現可能か

最初から全面移行せず、最小Spikeで「1 Scene + 1 Resident + Core接続」まで確認する。

### 判定

- **Feasible**：DNA由来WorldをUE4.27へ載せ換え、以後のWorld / 暮らし実装は原則UE側で進める
- **Not Feasible / Cost過大**：理由をEvidence化し、Three.js海中Worldへ戻るか別World候補を再調査する

この判定前にThree.js海中表現を追加で磨き込まない。
