# Nirai 詳細設計 01：通信プロトコル

正本は [Nirai_基本設計.md](../Nirai_基本設計.md)。全体像は [00_全体構成.md](00_全体構成.md)。

## 概要

通信プロトコルとは、CoreとWorldがWebSocketでやりとりするメッセージの取り決めである。

- 前提
  - CoreがサーバーでWorldがクライアント
  - 接続先：`ws://127.0.0.1:8765`（ポートはconfig.toml）
  - メッセージは全てJSONテキスト1件＝1メッセージ
  - 知らない`type`を受け取った側は、WARNログを残して無視する（落ちない）
  - 会話UIはWorld内にある。Master入力と会話ログ表示も、この接続のうえで運ぶ

## メッセージ共通形式

| フィールド | 型 | 必須 | 説明 |
|-----------|----|------|------|
| type | string | ○ | メッセージ種別 |
| id | string | — | 応答が必要なメッセージの相関ID（`action`と`action_done`の対応付け等） |
| ts | string | ○ | 送信時刻（ISO 8601） |
| payload | object | ○ | 種別ごとの中身（空でも`{}`） |

## 接続開始

1. Coreは起動ごとにWorld専用の高強度Secretを生成し、Coreが子Processとして起動するElectronへだけ実行時情報として渡す。永続設定・Git管理File・通常Logへ保存しない
2. Worldが接続し、最初に`hello`を送る
   - `payload: { "role": "world", "secret": "<起動時Secret>" }`
   - CoreはSecret一致を確認するまでWorld接続として登録せず、Snapshot・Session・Agent状態等も返さない
   - Secret不一致または欠落は接続時点で拒否し、現在の正規Worldを置換しない
3. Coreは認証成功後に`hello_ack`を返す
   - `payload: { "residents": [住人の初期情報の配列], "locations": [Location定義の配列], "time_of_day": "day", "settings": { "audio_volume": 100 }, "active_session": "S-..." }`
   - `residents`配列順は`[residents].enabled`の順序と一致させ、右Resident Sidebar表示順と複数Resident初期配置順の初期同期に使う
   - 住人の初期情報：`{ "name": "…", "brain": "codex", "brain_model": "gpt-5.6-sol", "brain_reasoning_effort": "high", "avatar": "…", "location": "…", "tts": { "enabled": true, "provider": "voicevox", "speaker_uuid": "…", "style_id": 3, "speed": 1.0, "pitch": 0.0, "intonation": 1.0 } }`。`brain_model` / `brain_reasoning_effort`等の未設定項目は`null`を許容する
   - Location定義：`{ "id": "center", "name_ja": "光の柱" }`
     - Coreは意味的なLocation IDと表示名だけを持つ
     - 実座標・移動経路・接地はWorldの責務。初期は複雑なNavMeshを前提にしない
     - Worldは受け取るまで既定配置で描く（Coreがいなくても風景が出る）
4. 認証済みの同じroleの二重接続が来た場合だけ、Coreは古い方を切断して新しい方を採用する

## Core → World

| type | payload | 説明 |
|------|---------|------|
| spawn_resident | `{name, avatar, location, tts?}` | 住人の身体を出現させる。`tts`はResident固有の音声設定 |
| remove_resident | `{name}` | 身体を消す（住人が「留守」のとき） |
| action | `{name, command, args}` | 行動コマンドの実行指示。idを付ける |
| bubble | `{name, text_short, text_full?, duration_sec, tts?, request_id?}` | 独立した発話表示指示。M1のMaster会話では`resident_say` / `resident_whisper`の`chat_append`からWorldが同等の頭上吹き出しを派生してよい。M2以降の自律発話・短文化表示等で独立指示が必要な場合に使う |
| time_of_day | `{phase}` | 時間帯の切り替え（下記） |
| pause | `{}` | 省エネモード開始（描画負荷を下げる） |
| resume | `{}` | 省エネモード解除 |
| shutdown | `{}` | 終了指示 |
| chat_append | `{entry}` | 会話ログ1件の追加（会話UI用。下記の会話ログ形式） |
| history_response | `{session_id, entries, next_before}` | 選択中チャットセッションのログ配列。`next_before`は古い履歴が残る場合だけ次回`history_request.before`へそのまま返す不透明Cursor、最古到達時は`null` |
| chat_session_list | `{sessions, active_session}` | 左サイドバー用。`sessions`は`{id,title,created_at,updated_at}`の配列 |
| response_state | `{active, request_id?, session_id?}` | Master発話1回へのAI応答が進行中か。送信ボタンの↑/停止表示に使う |
| brain_provider_list | `{providers}` | AI連携UI用。各Providerの`name, available, connected, configuration_mode, models, default_model, default_reasoning_effort, custom_model_allowed`を返す。M4以降は任意の`capabilities`を追加し、少なくとも`conversation / agent_work`をboolで持たせ、11のApproval / Question / Plan等の対応可否も追加できる。M4実装前は`capabilities`省略を許容する。Codexの`models`は`{id,display_name,default_reasoning_effort,reasoning_efforts:[{id,display_name}]}`を返し、他Providerは不要なReasoning項目を省略できる |
| resident_settings_updated | `{resident}` / 削除時のみ`{resident:null, deleted_name}` | Resident作成・Brain/Avatar/VOICE変更・削除後の設定UI同期。削除時は削除済みResidentの設定Objectを捏造せず`deleted_name`で一覧・Worldから除去する |
| resident_roster_updated | `{residents}` | Resident並べ替え保存後の一覧同期。配列順は`[residents].enabled`と一致し、Worldの初期配置順として扱う |
| status | `{residents, ecomode, budgets}` | 状態表示用（住人の現在Location・状態、省エネ中か、予算消費） |
| world_observation_request | `{reason?}` | M3以降。Coreが最新の意味的World Observationを要求する。通常はCacheを使い、未取得または古い場合だけ要求してよい |
| task_update | `{task_id, phase, text, agent_session_id?}` | タスクの高水準進捗。phase：consulting / assigned / running / done / failed / cancelled。CommandやDiff等の詳細は`agent_event`へ分離する |
| agent_event | `{event}` | M4。11で定義するNirai共通Agent Event 1件。Provider固有Protocol名や生JSONをWorldへ漏らさない |
| agent_session_snapshot | `{agent_session_id, task_id, provider, state, events, pending_input?}` | M4。World再接続・詳細画面再表示用のAgent Session復元Snapshot。`pending_input`は未解決Approval / Question / Plan等がある場合だけ含む |
| notice | `{level, text}` | Masterへの通知。Worldは画面へ表示し、Resident作成・AI変更等の設定操作が応答待ちならpendingを解除して再操作可能にする |

- time_of_dayのphase（Coreが実時刻から決めてWorldへ送る）
  - morning：5時〜9時
  - day：9時〜16時
  - evening：16時〜19時
  - night：19時〜5時

### 行動コマンド語彙 v1（正はこの表。03・04はここを参照する）

| command | args | 意味 |
|---------|------|------|
| move | `{location}` | Locationへ移動する。Worldは2026-08-26変更前の旧Move Bの演技を標準として使う |
| approach | `{target}` | M2以降。指定Residentへ会話距離を残して近づく。意味Locationが同一でも対象Residentの現在Presentation位置をWorld側で解決し、完全重複は避ける |
| gather | `{participants:[Resident名...]}` | Group Conversation用。2〜10人をscreen-safe範囲内の会話Formationへ集める。3人は三角形、4人以上も同じ輪状計算を使い、人数別の専用座標表は持たない |
| wander | `{}` | 現在地付近をゆっくり漂う。自然移動用の水中遊泳Primitiveを使う |
| stand | `{}` | LOCOMOTIONのIdleで立ち待機へ戻る |
| afk | `{}` | IDLE / AFK Animationで休憩する |
| expression | `{kind}` | 意味的な表情。Emotionはneutral / happy / angry / sad / relaxed / surprised / awkward / doubt、ほかblink / aa / ih / ou / ee / oh等の口形・瞬きを扱う |
| face | `{target}` | 対象（住人名または"master"＝画面手前）の方を向く |
| work | `{}` | 作業状態へ遷移する。視覚表現はWorldが決める |
| sleep | `{}` | SLEEP Animationで眠る |

- 語彙の追加はこの表への追記で行い、既存コマンドの意味・引数は変えない（後方互換）
- Worldは未知のcommandを受けたら`stand`扱いにしてWARNログ
- `expression`はVRM Runtime経由でAvatarのExpressionへ適用する。CoreはAvatar固有Expression名を送らず意味名だけを送る。WorldはVRM0の`joy / sorrow / fun`やAvatar固有の`happy01`等を意味名へ解決し、同一Emotionに複数候補がある場合はEmotionへ入る時に候補から選択する。頭上アイコンにはしない
- 発話の正本はテキスト。TTSはWorld側の任意表現であり、Mute中でも`bubble`と`chat_append`は通常通り表示・保存する
- `text_full`がある場合、WorldはTTS入力に必ず全文を使い、`text_short`だけを読み上げない

※メモ：`gesture`と`talk`は対応Animation Asset追加後に語彙へ追加する。`sit / stretch / think`は追加予定に含めない。

## World → Core

| type | payload | 説明 |
|------|---------|------|

| action_done | `{name, ok, reason?}` | 行動完了。指示のidを引き継ぐ。失敗時はok=false、reasonに理由 |

| master_whisper | `{to, text, request_id}` | 現在選択中チャットセッションでWhisperを送信（toは住人名） |

| chat_session_list_request | `{}` | 左Sidebar用のセッション一覧を要求 |

| chat_session_select | `{session_id}` | 過去セッションを選択し、会話を再開可能にする |
| chat_session_delete | `{session_id}` | UI上の履歴を削除する。World Memoryは削除しない |
| world_memory_forget_session | `{session_id}` | 指定UIセッション由来のWorld Memory公開Episodeを全て忘れさせ、同じUIチャット履歴も削除する。Private Memoryは削除しない |

| resident_delete | `{name, confirm}` | Character完全削除。`confirm`が`Delete`完全一致でない場合は拒否する |

| error | `{message}` | World内部エラーの報告 |

### World Observation（M3以降）

Residentが現在のWorldを「設定として知る」のではなく「観測して判断する」ための意味的Snapshot。

例：

```json
{
  "captured_at": "2026-08-29T01:00:00+09:00",
  "master_focus": "Lapan",
  "environment": {
    "light": "bright",
    "water_surface": "calm",
    "visibility": "clear",
    "caustics": "normal"
  },
  "residents": [
    {
      "name": "Lapan",
      "location": "center",
      "state": "stand",
      "nearby": ["Codex"]
    }
  ]
}
```

規則：

- Worldは描画の生値ではなく、会話・行動に意味のある離散化済み情報だけを送る
- 正確な`x/y/z`、Camera Matrix、Shader Uniform、FPS等をBrain Context用Snapshotへ常時載せない
- `master_focus`は現在World上でMasterがFocusしているResident名。Focusなしは`null`
- `environment`は実際にWorldが現在描画している状態から生成する。固定Promptの世界説明をそのまま複製した値にしない
- `residents`は身体がWorldに存在するResidentの現在Location・意味状態・近接関係を表す。近接は必要なら`near / same_area / far`等へ拡張してよい
- 毎Frame送信は禁止。意味のある状態変化時に更新し、Coreは最新SnapshotをCacheする
- Brain呼び出し時にSnapshotが未取得または古い場合、Coreは`world_observation_request`で更新を要求してよい
- World未接続・Snapshot取得不能時は「観測なし」として扱い、推測で現在状態を補わない

## IDの使い分け

- Message共通`id`：WebSocket Message 1件の相関ID
- `session` / `session_id`：UI上のチャットセッションID
- `request_id`：Master発話1回と、その発話に対する全Resident応答を束ねるID。Rendererが`crypto.randomUUID()`で生成する
- `invocation_id`：Core内部のBrain 1回呼び出しID。World Protocolへ常時露出させない
- `task_id`：Nirai上の仕事1件のID
- `agent_session_id`：Task担当Agent Providerとの実作業Session ID。再実行・Provider交代では同じTaskに複数Sessionを持ち得る
- `event_id`：Agent Session内の構造化Agent Event 1件の一意ID

会話停止対象は`session_id`ではなく`request_id`で特定する。同じChat Session内の過去発話まで停止対象に含めない。実作業停止は`agent_session_id`で特定し、会話の`cancel_response`と混同しない。

## 会話ログ形式（chat_append / chat_sessions共通）

`runtime\chat_sessions\<session-id>.jsonl` に1行1件で追記する。セッション一覧用メタデータは`runtime\chat_sessions\index.json`に保持する。

| フィールド | 型 | 説明 |
|-----------|----|------|
| entry_id | string | Chat Entry 1件の安定ID。同一Entryのretryでは同じ値を使い、同文の別発言には新しい値を発行する |
| ts | string | 時刻 |
| kind | string | say / whisper / resident_say / resident_whisper / resident_chat / task / system |
| from | string | 発言者（"master" または住人名） |
| to | string? | whisperの宛先、またはresident_chatで発言者が明示的に話を振った参加Resident。Group全体向けresident_chatでは省略 |
| text | string | 本文（全文） |
| session | string | セッションID |
| request_id | string? | Master発話に紐づくEntryの場合のRequest ID。Resident自律会話等では省略可 |
| task_id | string? | Taskの高水準Entryの場合のTask ID。通常会話では省略 |
| agent_session_id | string? | Task実行の詳細Agent UIへ辿る必要があるEntryの場合のAgent Session ID。Command全文やDiff自体はChat Entryへ複製しない |

- 例1：Masterが全体に話す
  - `{"ts":"…","kind":"say","from":"master","text":"みんなおはよう","session":"S-20260821-001"}`
- 例2：住人AがBに話す（住人同士の会話）
  - `{"ts":"…","kind":"resident_chat","from":"A","to":"B","text":"この実装、手伝ってくれない？","session":"S-20260821-002"}`

### チャットセッション規則

- 新規チャットはTemporary Contextだけを新しくする。World Memory、Private Memory、Resident人格は維持する
- Chat Session履歴には削除済みResidentの過去発言を歴史として残してよい。ただしBrain Contextには履歴とは別に現在有効なResident一覧を渡し、削除済みResidentを現在参加者として扱わせない
- セッションタイトルは追加のBrain呼び出しを使わず、最初のMaster発話を短く切り詰めて生成する
- 過去セッションを選択した場合、その履歴を表示し、そのセッションの続きとして発言できる
- `chat_session_delete`は`runtime\chat_sessions`側の履歴だけを削除する
- `world_memory_forget_session`はそのUIセッションに紐づく公開EpisodeをWorld Memoryから除外・削除し、同じ`runtime\\chat_sessions`側のUI履歴も削除する。Private Memoryは削除しない

## 再接続と異常時の規定

1. World切断をCoreが検知した場合
   - 住人の行動指示を保留（捨てない。再接続時に最新状態だけ送り直す。個々のactionは再送しない）
   - 会話ログはセッションファイルに書き続ける（再接続時にhistory_requestで取り戻せる）
2. Core切断をWorldが検知した場合
   - 1秒→2秒→4秒→8秒→16秒→30秒の指数Backoffで再接続し、以後30秒を上限として継続する。接続成功時は1秒へ戻す
   - Worldは再接続中もアイドル演出（住人がその場で待つ・歩き回る）を続ける
3. 応答待ちのタイムアウト
   - `action`に対する`action_done`が60秒来ない場合、Coreは失敗扱いにして次へ進む（WARNログ）
4. 生存確認
   - 独自Heartbeatプロトコルは初期実装しない。WebSocket標準の接続状態・切断検知を利用する
   - 実装上必要になった場合は、AITuberKit等の既存実装をベンチマークにして追加し、Nirai独自方式を発明しない
