# Nirai 設計書棚卸 2026-09-06

## 0. この文書の目的

この文書は、現行Niraiの設計書が「過去の設計を守れているか」ではなく、MasterがNiraiで最終的に実現したい体験へ長期的・合理的・効率的に到達できる構造になっているかを点検するための棚卸しである。

本棚卸しでは、設計書を次の4種類へ分離して考える。

1. **Product Goal / Philosophy** — 何を作るか。長期間変えない最上位目的。
2. **Invariant / Guardrail** — 何があっても守る安全・プライバシー・Identity等の制約。
3. **Current Architecture / Design** — 現時点で最も合理的と判断して採用している方式。将来の実測で変更可能。
4. **Implementation Record / History** — 過去の実装順、検証結果、レビューFinding、当時の暫定判断。現行設計を拘束しない。

2026-09-06にMasterレビューで主要判断を確定し、本棚卸しに基づく設計書再編を開始した。`Nirai_設計ガバナンス.md`を新設し、基本設計・00・02・03・06・07・08・10・11・13・AI_ENTRYへ第一段階の反映を行った。

本書は「何を残し、何を直し、何を降格・退役させるか」の判断記録として維持する。各Active Designの詳細実装方式は、必要なReference-First調査を経て別途確定する。

## 1. Masterの目的との適合判定

### 結論

**上位思想はMasterの意図に沿っている。詳細設計と文書運用には設計ドリフトがある。**

特に、次の上位目的は現在も一貫している。

- AIを道具として使うことより、AI Residentが「そこに存在する」ことを中心にする
- MasterとResident、Resident同士が長期間関係を継続できる
- 「居場所が主、タスクは従」
- NiraiをMasterのAI活動の基地にし、専用CLIを日常的に直接使わなくてよい状態へ近づける
- 人格・記憶・Brain・Avatarを分離し、Brain交換や将来技術の変化でResidentを作り直さない
- WorldとCoreを分離し、表示や実体が変わってもResidentのIdentityと記憶を持ち運べる
- Public / Private Memoryを明確に分離し、Whisperを他Residentへ漏らさない
- 実作業はMaster Approval、安全境界、許可Directory等を通す
- Holoを通常Resident Driverへ無理に押し込めず、ChatGPT Webを正本にする専用Addonとして扱う

一方、下位設計では次の傾向が出ている。

- M1/M2/M4で採用した**一時的な単純化**が、最終アーキテクチャのように書かれている
- 安全のための直列化と、単なる実装容易性のための直列化が区別されていない
- 会話・記憶の「長期継続」という製品目的より、直近N件・単発CLI呼び出し等の実装都合が勝っている箇所がある
- M4「仕事」の設計・検証記録が巨大化し、M3「暮らし・記憶」より文書上の存在感が大きい
- 検証履歴が現行仕様へ混入し、後続AIが古い制約を「今も守るべき仕様」と誤認しやすい
- 基本設計・00・08・10・AI_ENTRYがそれぞれ強い命令権を持ち、Source of Truthが実質多重化している

したがって、Niraiの現在の問題は「思想が間違っている」ことではなく、**設計ライフサイクルと正本階層が弱いため、過去の局所最適が永久ルール化しやすいこと**である。

## 2. 今後も長期間守るべきProduct Goal

以下は、実装方式が変わっても維持する最上位目的とする候補である。

### PG-01 存在が主
NiraiはAI作業ツールを3D化したものではなく、MasterとAI Residentが継続的に存在・交流する場所である。

### PG-02 関係とIdentityの継続
ResidentのIdentity・人格・関係・記憶は、Brain Provider、Model、CLI、Avatar、Worldの交換で失われない。

### PG-03 長期利用を前提にする
数日だけ動くDemoではなく、**最低5年間の日常利用で根本作り直しを必要としないこと**を設計目標とする。履歴・記憶・Event・Conversationが増えても、性能・コスト・操作性・保守性が破綻しない構造を採る。

### PG-04 暮らしが主、仕事は暮らしの一部
Task / Agent Runtimeは重要だが、Niraiの中心目的へ昇格させない。仕事機能の都合で通常会話・暮らし・他Residentの活動が不必要に停止しないことを目指す。

### PG-05 専用クライアント依存を減らす
Cursor / Codex等をNirai内から自然に会話・相談・実作業できるようにし、通常利用で専用CLIクライアントを常用しなくてよい状態を目指す。

### PG-06 Masterの運用負荷を増やさない
安全性を維持しつつ、単純Taskのたびに全員会議・過剰な承認・不要な手動操作を要求しない。複雑さはシステム側で吸収し、Masterへ不要な儀式を押し付けない。

### PG-07 既存技術を使い、再発明を避ける
Providerが持つSession / Thread / Resume、既存DB、既存OSS等で解ける問題をNirai独自方式で再実装しない。ただし外部Provider固有状態をResident IdentityやMemoryの唯一の正本にはしない。

### PG-08 将来変更可能な構造
現在のProviderやModelの制約を永久仕様へしない。将来、より自然な並列処理、自律AI、ロボット等へ移行してもCore全体を作り直さず差し替えられる構造にする。

### PG-09 合理性・効率性・保守性を品質要件にする
安全に動くだけでは採用しない。目的に対して合理的か、Token・Brain call・Disk I/O・待ち時間・Master操作・実装量に無駄がないか、責務が明確で後から変更・検証・削除しやすいかを設計品質として評価する。暫定実装を採る場合は、暫定である理由と解除条件を明示する。

### PG-10 Reference-First / 再発明防止
新しいSubsystem、外部Provider統合、複数層へ跨る大規模変更、または一般的に既存解が存在し得る問題へ着手する前に、Webを広く調査し、公式機能・成熟OSS・公開Reference Implementation・類似製品・技術記事・Issue/Discussion等に利用可能な先行知見がないか確認する。優秀なカンニングペーパーが存在する場合は、LicenseとNirai要件を確認したうえで積極的に設計へ利用し、同じ問題を独自方式で再発明しない。

## 3. Invariant / Guardrail候補

以下は「現在方式」ではなく、明示的に変更しない限り守るべき境界として独立させる価値が高い。

- Public MemoryとPrivate Memoryの分離。Whisperを他Resident / Public Retriever / World Memoryへ混ぜない
- Resident IdentityをProvider native Session / Thread IDへ従属させない
- Brain Provider交換でpersona / Nirai Memory / Avatar / Relationshipを失わない
- Retriever IndexやCacheは派生データであり、再生成可能とする
- WorldとCoreを責務分離する
- Holo Addon停止で通常Niraiが停止しない
- Brain会話とAgent Workを分離し、会話経路からFile変更・Approval回避を発生させない
- Task作業Directoryを明示境界で制限する
- Nirai内部状態、Credential、Private MemoryをProviderへ不要に露出しない
- Git操作、外部送信、System設定、秘密情報等の高リスク操作はMasterの明示承認なしに実行しない
- File Change / Approval等はProvider任せにせず、必要な場合はNirai側でもfail-closed境界を持つ
- Crash / Cancel / Timeoutで無期限待ちにしない
- 履歴・Memory・Event等の正本を、上限なしのPrompt再送やProvider固有Contextだけへ依存させない

### Invariantにしてはいけないもの

次は現在の安全な実装方式ではあっても、原則として永久Invariantにしない。

- Brain呼び出しは全Niraiで常に同時1件
- Agent Sessionは永久に全Provider合計1件
- Taskは必ず全Resident会議から開始
- Conversationは直近20発言を毎回再送
- Private Contextは常に数KBの1ファイルだけ
- World Memory Episodeは短文要約だけを正本にする
- M0〜M4の実装順
- 特定Provider CLIの現在の起動方式
- 現在のProvider制約に由来するSandbox / Capabilityの詳細

これらはCurrent ArchitectureまたはProvider Adapter制約として扱う。

## 5. 重大な設計ドリフト

### D-01 Source of Truthの多重化

現在は基本設計が正本とされつつ、00が実装AIの行動規則を持ち、08がTask順と受入を強制し、10がFile/Class/実装順の正本とされ、AI_ENTRYがさらに最新状態を大量に上書き説明している。

この状態では「どれを守るべきか」よりも「全部守ろう」となりやすく、古い判断を温存する。

**是正方針**

- Product Goalが最上位
- Invariant / Guardrailが次
- Active Designはその下
- Milestone / AcceptanceはActive Designの実現順
- Verification / Historyは設計を拘束しない

### D-02 「質問する安全性」が「改善しない安全性」へ変質

00の「書いていないことを発明しない」「矛盾したら実装停止」は、初期のAI実装暴走を防ぐには合理的だった。

しかし長期運用では、明らかな非効率や外部Providerの新しい正式機能を見つけても、旧設計を守る方向へAIを誘導する。

**是正方針**

- Invariant違反の疑い → 停止してMasterへ確認
- Product Goalとの衝突 → 停止してMasterへ確認
- Current Designより明確に合理的な代替を発見 → 実装せず、差分・利点・リスクを提示して設計変更を提案
- 単なる未記載の実装詳細 → 局所判断可能な範囲を明示

### D-03 会話の継続方式がResidentとHoloで二重化

Holo Conversation Runtimeでは2026-09-06にProvider native Session / Thread continuationを再利用する方式へ改善された。

一方、通常Resident Brainは現在もone-shot / latest-N再送を前提とする設計が残る。

これは同じ「AIとの継続会話」に二種類の思想があり、通常Residentだけが長期会話に不利な状態である。

**是正方針**

共通Conversation Continuity Contractを作り、Providerがnative continuationを持つ場合は利用する。ただしProvider IDはNirai Conversation / Resident Identityの正本にはしない。

### D-04 長期Memoryの正本が弱い

現行World Memoryでは、公開会話全文はUI用`runtime/chat_sessions`、AI記憶はEpisodeへ分離されている。履歴を削除してEpisodeを残せるため、Episodeが短縮・要約されると失われた原文を後からRetrieverで取り戻せない。

Private Memoryは`whispers.jsonl`全文正本がある点は良いが、`context.md`の小容量前提だけでは数年規模の関係継続に十分とは限らない。

**是正方針**

Memoryを最低でも次の3層へする。

1. **Raw Durable Source** — losslessな事実・発話の正本
2. **Structured Continuity Memory** — 人物・関係・未解決事項・重要事実等の圧縮された継続状態
3. **Derived Retrieval Index** — FTS / Embedding等。削除・再生成可能

Public / Privateはこの3層の前段で完全分離する。

### D-05 Global Lockが「暮らし」を止める

「Brain呼び出しは常に同時1件」はM1/M2の安全な初期実装としては合理的だが、Nirai全体のInvariantにすると、Masterが1人と長く話しているだけで他Residentの自然活動や別Conversationが必要以上に止まり得る。

M4のAgent 1件制限も同様で、Provider・Credential・Workspace等の衝突理由がないなら永久制約にする理由は薄い。

**是正方針**

Global Lockではなく、Resource / Provider / Conversation / Work対象ごとのConcurrency Policyへ分解する。

例：

- 同一Providerが本当に1実行制限ならProvider Lock
- 同一ConversationのTurn順序はConversation Queue
- 同一Task WorkspaceへのWriteはTask/Workspace Lock
- 別Residentのread-only Conversationは独立実行可能
- TTSだけは人間に聞き取れるようPresentation Queueで整列

### D-06 全Task会議は「仕事を暮らしの一部」にするには重い

複雑な仕事をResident同士が相談する姿はNiraiらしい。一方、単純な依頼まで必ず全Resident相談→立候補→担当決定を通すのは、Masterの操作コスト、Brain利用量、待ち時間を増やす。

**是正方針**

最低2経路に分ける。

- **Direct / Delegated** — Masterが相手を指名、または明らかな担当へ直接依頼
- **Council** — 誰に任せるか、方針が割れる、複数AIの意見が有益なTaskだけ相談

将来自動判定する場合も、Masterが明示的に経路を選べることを優先する。

### D-07 M4文書量が製品重点を歪める

M4の安全性は重要であり、実装品質も高い。しかし08やAI_ENTRYではM4のレビュー履歴が巨大化し、M3「暮らし」「長期記憶」よりも現在のNiraiの中心であるかのように読める。

これは実装AIに対しても「Nirai = Agent実行基盤」という誤った重心を作りやすい。

**是正方針**

Verification履歴を別文書へ置き、Active Designでは「現在どう動くべきか」だけを書く。Product Goalの「居場所が主、タスクは従」を文書量・入口順でも守る。

## 6. 推奨する新しい設計階層

### Level 1: Product Constitution

`Nirai_基本設計.md`

保持するもの：

- Niraiとは何か
- Product Goal
- 「居場所が主、タスクは従」
- Resident Identityの考え方
- World / Core大枠
- Public / Private分離
- 将来交換可能性
- Master Approval等の最上位安全原則

持たせないもの：

- 現在のCLI引数
- latest 20等の数字
- Global Lock
- Taskの細かな相談Algorithm
- 過去のMilestone実装順
- Test count / Review history

### Level 2: Invariants / Contracts

新規に独立文書化するか、00をこの役割へ縮小する。

- Privacy Boundary
- Identity / Memory Ownership
- Security / Approval Boundary
- Source of Truth rules
- Crash / Fail-closed原則
- Document Governance

### Level 3: Active Design

01〜07 / 09 / 11 / 12等。

「現在どう実装するか」を記述する。より合理的な方式が見つかった場合は更新可能。

各設計判断へ必要に応じて次を付ける。

- `Invariant`: 変更禁止級
- `Current`: 現在方式
- `Temporary`: 暫定制約
- `Provider Constraint`: 外部仕様による制約
- `Future Candidate`: 未採用案

### Level 4: Milestone / Acceptance

08は現在の未完了Milestoneと受入条件へ集中する。

Stable済みM0〜M2、SAFE済みM4の詳細な歴史は検証結果へ参照を張るだけにする。

### Level 5: Evidence / History / Reference

- `*_検証結果.md`
- `Holo_Gate0検証結果.md`
- 過去Review Finding
- AITuberKit分析
- AIAvatarKit参考カンペ
- Archive plans

現行設計を拘束しない。

### AI_ENTRY

設計階層とは別に、AI向けRouterにする。

目標は「Niraiへ入ったAIが数分で現在位置を誤解しないこと」。

推奨内容：

1. 30秒で分かるNiraiの目的
2. 今のMilestone状態
3. 今のBlocking / Known Limitation
4. 作業種別ごとの読むべき文書
5. 検証Command / baseline
6. Historyを読みたい場合のリンク

大量のReview履歴を本文へ置かない。

## 7. 設計変更前に採るべき合理性チェック

今後、設計案を採用する前に次を確認する。これは推奨項目ではなく、設計レビューの標準チェックとする。

1. **目的適合** — Niraiの居場所・関係・長期継続を良くするか
2. **必要性** — 実測上まだ存在しない問題を先回りで解いていないか
3. **既存手段** — Provider / OSS / OSに既に正式な仕組みがないか
4. **正本** — 何がIdentity / Memory / Stateの正本か明確か
5. **Lossless** — 圧縮・要約・Indexを消しても重要な原情報を再構成できるか
6. **Scaling** — 1日ではなく1年使っても全件scan、全文rewrite、Prompt肥大が起きないか
7. **Concurrency** — Global Lockが本当に必要か。より小さなResource Lockに分けられないか
8. **Failure** — Provider停止、Crash、再起動時にどうなるか
9. **Cost** — Brain call、Token、Disk、待ち時間、Master操作回数を無駄に増やさないか
10. **Replaceability** — Providerを交換すると壊れる設計になっていないか
11. **Privacy/Security** — Public / Private / Credential / allowed_dir境界を破らないか
12. **Complexity Budget** — 得られる価値に対して実装・運用複雑性が過大でないか
13. **Maintainability** — 責務分離、局所変更可能性、Test容易性、削除容易性、Provider差し替え容易性が確保されているか
14. **Operational Simplicity** — Masterが日常利用する際の手順・承認・待ち・設定・復旧操作を不必要に増やしていないか
15. **Reference-First** — 同じ問題を既に解いている公式機能、成熟OSS、Reference Implementation、類似製品がないか十分調べたか
16. **Evidence** — 採用理由が「なんとなく良さそう」ではなく、公式仕様・実測・先行実装等で裏付けられているか

「安全だから直列化」「将来使うかもしれないから抽象化」だけでは採用理由にしない。どの危険を防ぎ、どのコストを払うかを明示する。

## 10. Master判断の確定事項

2026-09-06に以下を確定した。以後はCurrent Designではなく、Product Goal / Design Principleとして設計判断へ反映する。

1. **Resident Identity継続: YES** — BrainをCodex→Cursor→将来の別AIへ交換しても同じResidentである。Provider native Session / ThreadはConversation Contextとして利用してよいが、Resident Identityや唯一の長期Memoryにはしない。
2. **Private Memory長期化: YES** — Whisperも年単位・数年単位で蓄積する前提とし、「量が少ないから小さなcontext.mdだけで足りる」という前提を廃止する。Raw全文 + Structured Continuity + Retrievalを基本構造とする。
3. **Resident並行生活: YES** — Masterが1 Residentと会話中でも、独立Residentの生活判断、別Conversation、read-only相談等は安全な範囲で並行可能とする。人間向け表示・音声だけPresentation Queue等で交通整理する。
4. **Task標準入口: A** — Masterが指名したResidentへ通常の言葉で「これやって」と頼めることを標準体験とする。必要ならそのResidentが相談を提案・開始する。通常会話をNiraiが勝手にTask化してFile変更を始める方式は採らない。
5. **設計耐用年数: YES / 最低5年** — History / Memory / Event / Conversation等は、日常利用5年程度で根本作り直しを必要としないことを設計目標とする。全件scan、全体rewrite、無制限Prompt再送等を常用経路へ置かない。
6. **新規Residentと過去World Memory: C** — 入居前のWorld Memoryは世界史・共有知識として参照可能。ただしResident自身がその場にいた、体験した、自分の思い出であるとは扱わない。World HistoryとPersonal Experienceを分離する。
7. **Memory訂正 / Forget: A** — 訂正では過去Rawを歴史として残し、Structured Continuityで旧情報を訂正済みとして現行値を優先する。Masterが明示的にForgetした場合だけ、対象Raw / Structured / Derived Indexを整合して削除する。
8. **Post-Audit実作業順: 1→4→2→3→5** — 意味上は`基盤完成 → DNA/UE4.27成立確認と移植 → M3暮らし接続 → Core/Protocol v1固定 → M5+拡張`とする。Three.js海中Worldの追加磨き込みをWorld Replacement確認より先に行わない。
9. **DNA / UE4.27 World: Private Addon** — DNA由来Asset / SceneはMaster個人利用限定の前提で扱い、Nirai本体・公開Repository・配布Packageへ同梱しない。現行Three.js海中Worldは削除せず、Distribution-safe standard World / Fallback候補として凍結・退避する。

## 11. 大規模実装前のReference-First Gate

### 適用対象

次のいずれかに該当する場合、実装前のWeb調査を必須とする。

- 新しいSubsystem / Runtime / Memory方式 / Agent統合 / Audio・Animation・Input方式等を導入する
- Core / World / Provider / Storage等、複数責務に跨る設計変更を行う
- 外部ProviderやProtocolへ新規統合する
- 独自Algorithm、独自Parser、独自Scheduler、独自State管理等を新たに作ろうとしている
- 既存方式を大きく置換する
- 実装担当AI自身が「一般的な問題であり、既存解がありそう」と判断する
- 大規模か迷う場合は、再発明防止を優先して調査側へ倒す

### 調査対象

最低限、次を横断して探す。

1. 公式Documentation / SDK / Example / Protocol
2. 成熟OSS / GitHub Repository
3. 同等機能を持つ製品・ProjectのReference Implementation
4. MaintainerのIssue / Discussion / Migration Guide
5. 必要に応じて技術記事・Benchmark・実利用報告

調査では「そのままコピーできるか」だけを見ない。次を抽出する。

- 解決済みの責務分割
- 正式API / Protocol
- Failure / Retry / Cancellation / State管理
- Performance / Scaling上の工夫
- Security Boundary
- 実装時に踏みやすい既知の罠
- Licenseと利用可能範囲

### 実装着手条件

大規模実装の前に、少なくとも次を短く記録する。

- 調べた先行実装 / 公式機能
- 採用する考え方
- 採用しない部分と理由
- Nirai固有で新規実装が必要な差分

「設計書に既に方式が書いてある」ことを理由にWeb調査を省略しない。設計作成後により良い公式機能・先行実装が登場している可能性も評価する。

### 過去からの教訓

AITuberKit / AIAvatarKit等の先行実装を早い段階で十分に参照すれば、Nirai側で試行錯誤・再設計・独自実装せずに済んだ領域が複数あった。今後はこれを個別の反省で終わらせず、**Reference-First Gateを通さず大規模実装へ入らない**ことで再発を防ぐ。
