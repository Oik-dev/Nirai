本監査は、既存設計書への準拠確認や、過去Findingの再確認だけを目的としない。

`D:\Products\Nirai` のCurrent実装を製品として扱い、次を徹底的に洗い出す。

## 3. 監査原則

### 3.1 設計書を正解として扱わない

設計書は目的・Invariant・Current Designを理解するために読むが、Current Design自体も評価対象とする。

「設計どおりなので問題なし」は判定理由にしない。

### 3.2 既知Finding探しに偏らない

過去Reviewを読んだ後は、それと同型の欠陥だけを探さない。

各Roundで監査観点を固定し、別種の問題を意図的に探す。

### 3.3 FindingはEvidence付きで確定する

可能な限り次のいずれかで裏付ける。

- 実コードの制御フロー
- 既存Test
- 追加の隔離Probe
- Failure Injection
- 実測Benchmark
- 実ユースケース再現

疑わしいだけの箇所はCandidateとして分離し、確定Findingへ混ぜない。

### 3.4 修正と監査を混ぜすぎない

各Roundは原則として、

1. 探索
2. Finding確定
3. 修正
4. 正方向Regression追加
5. Round再検証

の順に進める。

修正途中で別問題が見つかった場合は派生Findingとして記録する。

### 3.5 Fresh Contextを活用する

同じReviewerが同じ前提へ慣れすぎないよう、必要に応じてRoundごとにFresh Contextで再監査する。

特に「設計合理性」「削除監査」「最終敵対レビュー」は、直前の修正理由を知らない視点を入れる。

## 4. 優先度

- **P0**: データ消失、Privacy / Credential漏えい、任意範囲への未承認Write、致命的Security境界破壊
- **P1**: 通常利用で重大機能停止、永続不整合、Recovery不能、誤ったMemory / Identity / Task実行
- **P2**: 条件付き機能不良、長期運用上の性能・保守性問題、合理性を大きく損なう設計
- **P3**: 局所的な改善余地、可読性、軽微な重複、低頻度の運用負担

P0/P1は原則Blocking。P2は「直す / 許容する / 後工程へ送る」を明示する。

## 11. Round 1 Findings

### R1-F01 — [P1] Private ForgetとRaw挿入が直列化されず、Forget済みWhisperが復活できる

`core/memory/private.py`では、`_insert_raw_entry()`が`forgotten_entries`を確認した後にRawを書き込むが、確認前にwrite transactionを取得していない。一方、`forget_entry()`も対象`raw_id`を`BEGIN IMMEDIATE`より前に取得している。

このため、Raw appendとForgetが競合すると、以下のいずれかが成立し得る。

1. appendが「未Forget」を確認
2. Forgetがtombstoneをcommit
3. 遅れてappendがRawをcommit
4. tombstoneとRawが同時に存在し、Forget済みWhisperが復活する

また逆順では、Forgetが`raw_id=None`を先に読んだ後にappendがcommitし、その後Forgetがtombstoneだけをcommitして新Rawを削除しない経路も成立し得る。

Public World Memory側は`_append_raw_entry()`と`forget_session()`を`BEGIN IMMEDIATE`で直列化しており、Private側だけ契約が弱い。

**Evidence:** `.tools/test_general_audit_round1_20260908.py::test_private_forget_can_be_resurrected_by_late_raw_insert`。Forget commit後にlate insertを解放し、`forgotten_entries`と`raw_entries`が同時に存在することを再現した。

**Root Cause:** Forget tombstone確認 / 対象Raw決定 / Raw insertを同一SQLite write serialization境界へ入れていない。

**Recommended Fix:** appendとForgetの双方で、tombstone確認・Raw対象決定より前にwrite transactionを取得し、同じDB内で直列化する。

### R1-F02 — [P1] Chat削除でJSONL除去に失敗すると、Sessionだけ消えて再試行不能になる

`core/sessions/chat_store.py::delete_session()`は、先に`index.json`からSessionを除去し、その後でChat JSONLをunlinkする。

JSONLがFile lock / Permission / I/O障害等で削除できない場合、APIは例外を返す一方でSessionは既にSidebar正本から消えている。Raw JSONLは残るが、次回`delete_session(session_id)`は`unknown chat session`となり、同じ通常経路では再試行できない。

Chat JSONLにはPublicだけでなくWhisper本文も含み得るため、「削除失敗なのにUIから消えてRawだけ残る」状態は単なる表示不整合ではない。

**Evidence:** `.tools/test_general_audit_round1_20260908.py::test_chat_delete_unlink_failure_hides_session_and_prevents_retry`。対象JSONLのunlinkへ`PermissionError`を注入し、`has_session=False`かつRaw file残存、再削除不能を再現した。

**Root Cause:** 複数永続物に跨る削除を、rollback可能なstagingなしで部分commitしている。

**Recommended Fix:** Raw JSONLを一旦同一Directory内のdeleting stagingへatomic renameし、Index / SQLite cleanup / 最終unlinkの全工程に失敗rollbackを設ける。失敗時はSession可視性とRawを元へ戻し、通常APIから再試行可能にする。

### R1-F03 — [P1] World Memory ForgetとChat削除が跨ぎtransactionになっておらず、失敗時にMemoryだけ不可逆削除される

`world_memory_forget_session`は監査時点で、`WorldMemoryService.forget_session()`をcommitした後に`SessionManager.delete_session()`を実行していた。

Chat側削除がFile lock / Permission / I/O等で失敗すると、Protocolは失敗通知を返すが、World Memory側では既にtombstone・Raw削除・Derived削除・Episode削除がcommit済みとなる。Chat Sessionは残るため、「操作は失敗したがMemoryだけ消えた」という跨ぎ正本の半端状態になる。

**Evidence:** `.tools/test_general_audit_round1_followup_20260908.py::test_world_forget_partially_commits_when_chat_delete_fails`。Chat deleteへ`ChatStoreError`を注入し、ProtocolがWARNを返した後もChat Sessionは存在する一方、`forgotten_sessions`は成立し、Raw / Episodeが消えていることを再現した。

**Root Cause:** World Memory DBとChat Storeを跨ぐ破壊操作に、durable intent / retry recoveryがない。

**Fix:** `runtime/pending_world_forget`へsession単位のdurable intentをfsync + atomic replaceで先に保存する。World Forget / Chat Deleteはidempotentな収束処理として実行し、両方完了後だけintentを除去する。Core起動時はChat Raw reconciliation後、Memory outbox replay前に残存intentを再実行する。

これにより、厳密なcross-DB atomic commitではなく、crash-safeなeventual transactionとして扱う。Cloud由来のDerived Memoryを補償復元する必要もない。

**Regression:**

- Chat delete failure後にintentが残ること
- Core再起動時に残存intentを検出すること
- Chat Session削除 / World tombstone / Raw削除 / Episode削除へ収束すること
- intentが最終的に除去されること
- 通常のHistory Delete / World Forget契約を壊していないこと

Round 1 focused regressions: **6 passed**。

### R1-F04 — [P1] Resident recursive delete失敗時にrollbackが半壊Directoryを再有効化する

監査時点の`ResidentService.delete()`は、先にRoot `config.toml`からResidentを無効化し、その後`shutil.rmtree(resident_dir)`を実行していた。recursive deleteが途中まで進んでから失敗すると、例外処理は`enabled`だけ旧状態へ戻すため、既に一部Fileを失ったResidentが再有効化される。

**Evidence:** `.tools/test_general_audit_round1_resident_20260908.py::test_resident_delete_partial_rmtree_can_reenable_a_broken_resident`。Resident自身の`config.toml`を削除した直後に`PermissionError`を注入し、Root config上は再有効化される一方、`ResidentService.load()`不能になる状態を再現した。

**Root Cause:** 非原子的なrecursive filesystem deleteをrollback可能な操作として扱っていた。

**Fix:** Resident Directoryを削除前に`runtime/pending_resident_delete/RD-*`へatomic renameし、durable `intent.json`を持つ削除transactionへ変更した。Root `config.toml`をcommit decisionとして扱い、Core再起動時は以下へ収束する。

- Residentがまだenabled: staged Directoryを元へ復元
- Residentがdisabled: staged / partially deleted bytesのcleanupを再試行

Root/Resident設定のatomic writeにもflush + fsyncを追加した。Recursive cleanupが途中失敗しても、半壊Residentを再有効化しない。

**Regression:** `core/tests/test_residents.py`

- partial recursive cleanup failure後もResidentはdisabledのまま
- pending transactionが残る
- restartで残存bytes cleanupを完遂
- config commit前crash相当ではstaged Residentを復元
- Resident suite: **15 passed**

### R1-F05 — [P1] Resident削除 / Brain変更がActive Resident Conversationと競合し、削除後late writeを許す

監査時点では`resident_delete`が通常AI応答とTask pendingだけを確認し、Holo ConversationおよびResident同士Conversationを排他対象にしていなかった。`resident_set_brain`は通常AI応答もResident Conversationも確認していなかった。

**Evidence:** `.tools/test_general_audit_round1_resident_lifecycle_20260908.py::test_resident_delete_allows_active_holo_conversation_to_write_late_reply`。Blocking BrainでResident Conversationを停止し、その間に`resident_delete`を実行すると削除要求が成功した。その後Brainを解放すると、削除済みResident名義の返答がConversationへcommitされ、Public Chatにもlate writeされることを再現した。

**Root Cause:** Resident設定・削除Lifecycleと、`_conversation_tasks` / `_resident_chat_tasks`のownershipが接続されていなかった。Resident Chat側はTask集合しか保持せず参加者情報も失っていたため、対象Resident単位の排他判定ができなかった。
