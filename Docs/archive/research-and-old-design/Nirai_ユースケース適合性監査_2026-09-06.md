# Nirai ユースケース適合性監査 2026-09-06

## 目的

この監査は、既存設計書への準拠率を判定するものではない。

Niraiの最終目的である、

- MasterとAI Residentが長期間継続して関われること
- AI同士が自然に相談・雑談できること
- Holo / Resident / Cursor / Codex等を日常的に同じ場から使えること
- 専用CLIクライアントを常用せず、NiraiをAI活動の基地にできること
- 記憶・人格・会話の連続性がBrain交換や再起動を越えて保たれること

を実際の利用シナリオから逆算し、現行実装・設計上の制約が合理的かを判定する。

既存設計は評価対象であり、守ること自体を目的にしない。Privacy / Secret / Master Approval / fail-closed等の安全Invariantと、単なる過去の実装選択を分離する。

2026-09-06のMaster判断により、長期設計の基準を次で確定した。

- ResidentはBrain交換後も同じIdentityを維持する
- Private Memoryも年単位・数年単位で蓄積する前提にする
- Masterが1 Residentと話している間も、別Residentの生活・独立Conversationは安全な範囲で継続可能にする
- Taskの標準体験は、Masterが指名Residentへ自然言語で直接依頼する方式とする
- 最低5年間の日常利用で根本作り直し不要を設計目標にする
- 合理性・効率性・保守性を設計品質として評価する
- 大規模実装前にWebを広く調査し、公式機能・成熟OSS・Reference Implementation等の先行解を探すReference-First Gateを必須にする
- 新規Residentは入居前のWorld Memoryを世界史・共有知識として参照できるが、自分自身の体験・思い出としては扱わない
- Memory訂正では過去Rawを歴史として残しStructured Continuityで現行値へ更新する。Masterが明示Forgetした場合だけRaw / Structured / Derivedを整合削除する
- Post-Auditの実作業順は`基盤完成 → DNA/UE4.27成立確認・移植 → M3暮らし接続 → Core/Protocol v1固定 → M5+`とする
- DNA / UE4.27 WorldはMasterローカル専用Private World Addonとして扱い、DNA由来Asset / SceneをNirai配布物へ含めない。現行Three.js海中Worldは配布可能標準World候補として凍結・退避する

## 現時点の総合判定

**NOT READY for long-term daily use**

M4 Agent Runtimeの安全境界・隔離・Approval・Crash時fail-closedは強い。一方、日常会話・長期記憶・作業依頼のUXには、短期Milestone向けの固定値やone-shot実行をそのまま残した箇所があり、Niraiの最終ユースケースへそのまま持ち込むと不合理になる。

2026-09-06にHolo ↔ Cursor / Codex Conversationについては、毎Turn直近20件を再投入する方式からProvider native Conversation継続へ修正済み。CursorはACP Session、Codexはapp-server Threadを再利用し、NiraiはConversation identity / lifecycleを上位正本として保持する。

ただし同型の問題が通常Resident Brain側を含む別経路に残っているため、今回の修正だけで全体をREADYとはしない。

# Findings

## P1-A: 通常ResidentのCursor / Codex会話がone-shotで、今回修正した同じContext問題を残している

### 現状

- `core/brains/codex.py`
  - `codex exec --ephemeral`をBrain呼び出しごとに新規起動
- `core/brains/cursor.py`
  - `cursor-agent -p --mode ask`をBrain呼び出しごとに新規起動
- `core/brains/talk_common.py`
  - `format_history()`が直近20件の原文を毎回Promptへ埋め込む
- `core/server.py`
  - Master Say / Whisper / Resident Chat / Holo→Resident Brainへ直近履歴を投入

### 実利用への影響

- 同じ過去20件を繰り返し投入してToken / Contextを消費する
- 21件より古い短期会話Contextは直接見えなくなる
- CLI Provider自身が持つSession / Thread continuationとcompactionを利用できない
- Holo↔Providerだけnative化しても、ResidentとしてCursor / Codexを使う日常会話は非効率なまま

### 判定

**設計上の穴。P1。**

### 推奨

Brain DriverにもConversation identityを渡し、Cursor ACP Session / Codex Thread等のnative continuationを利用する共通Conversation Backendへ寄せる。

ただしMaster Say、Whisper、Resident Group Chat、Task Consultでは「どの会話を同一native Sessionとして継続するか」のidentity設計が必要なため、単純な20→50件変更では直さない。

---

## P1-B: Private Memoryが「重要な長期記憶」ではなく、実質的に直近12発言のrolling excerpt

### 現状

`core/memory/private.py`の`_refresh_context()`は、

- `whispers.jsonl`から直近12件
- 各発言を240文字へexcerpt
- 最大4096文字

を`context.md`へ書き直す。

`context.md`は設計書上「覚えておくこと / 未解決 / 前回」を保持する長期継続層だが、現実装は意味抽出をせず直近発言を並べるだけ。

### 実利用への影響

昔の重要事項でも12発言を越えれば`context.md`から消える。全文Logは残るが、通常Brain Contextには直近20Whisperしか入らないため、数か月・数年の関係性を自然に維持できない。

### 判定

**最終目的と直接衝突。P1。**

### 推奨

Private Memoryを「全文原文」「構造化Continuity Memory」「検索」の3層へ分ける。単純AI要約1枚へ潰すのではなく、少なくとも決定・約束・人物/嗜好・未解決話題・長期事実を構造化し、原文参照を残す。

BGE-M3等の意味検索を採用するかは別評価とし、まず正本データを失わない構造へする。

---

## P1-C: World Memoryが公開発言を240文字で切っており、長い発言の後半が長期記憶から消える

### 現状

`core/memory/world.py`:

```python
clean_text = " ".join(text.split())[:240]
```

Retrieverは`world_memory/episodes`をIndexするため、240文字より後ろはRetriever対象に存在しない。

UI Chat履歴には全文が残るが、Chat Sessionを削除してWorld Memoryだけ残した場合、後半は完全に失われる。

### 実利用への影響

長い仕様説明、約束、体験談等の重要部分が偶然241文字目以降にあればAIは後から思い出せない。

### 判定

**Memory正本の情報欠落。P1。**

### 推奨

公開会話の原文正本をlosslessに保持し、Episode / Retriever用の要約・chunkを派生データにする。表示用excerptと記憶正本を同じ240文字Fieldにしない。

---

## P1-D: 会話Session調停の設計と実装が一致せず、複数Master発話の順序保証が弱い

### 現状

詳細設計02は「同時にactiveな会話Sessionは1つ、FIFO」としている。

実装では`master_say`ごとに`_response_tasks[request_id]`を生成し、各TaskがResidentを順番に処理する。Brain呼び出し自体はglobal `_brain_call_lock`で直列化されるが、Master発話単位のSession Schedulerは存在しない。

### 実利用への影響

短時間に複数Master発話が来ると、request AのResident1 → request BのResident1 → request AのResident2等、意味的には不自然なinterleaveが起こり得る。

UIが通常入力を抑止していてもCore契約として順序が保証されていない。

### 判定

**設計と実装の乖離 + 会話整合リスク。P1候補。**

### 推奨

「全会話1本」ではなく、Conversation単位のTurn Queueを明示し、同一Conversation内は順序保証、独立Conversation間はPolicyで並列/優先度を決める。

---

## P2-A: global Brain Lockは「AIが暮らす世界」には過剰な直列化

### 現状

`CoreServer._brain_call_lock = asyncio.Lock()` 1個で、

- Master Say
- Whisper
- Resident Chat
- Task Consult
- Holo→Resident Conversation

のBrain呼び出しを全て1本に直列化する。

Brain 1回はProviderによって最大120秒級。

### 実利用への影響

- Serinaと雑談している間に別Residentの返答が待つ
- Task相談が長いと通常会話が止まる
- 独立Provider同士でも同時に考えられない

### 判定

**安全Invariantではなく、初期実装の過剰制約。P2。**

### 推奨

将来はProvider / resource単位のConcurrency Budgetへ変更する。

例:

- 同じConversation内は1 Turnずつ
- 同じProviderは必要なら1件
- 異なるProviderは並列可能
- Master direct conversationを生活tickより高優先度
- Task workは別Agent Runtime budget

ただしSubscription上限・PC負荷を見ながら設定可能にする。

---

## P2-B: 通常Taskが必ず「全Resident会議」を通るため、日常作業ではWorkflow taxになる

### 現状

`/task`は必ず、

1. 全Resident consult
2. volunteer
3. 必要なら追加巡
4. first eligible volunteer
5. Agent start

を通る。

### 実利用への影響

「Codexにこれ直して」「CursorにこのProject見てもらって」のような担当が明白な仕事でも、複数Brain呼び出し・待ち時間・Tokenを使う。

Niraiの世界観としてResident会議は魅力だが、それを全作業の必須関所にすると作業基地として非効率。

### 判定

**古い設計の足枷。P2。**

### 確定方針

標準経路は`direct/delegated`とする。

- Masterは指名Residentへ通常の言葉で「これやって」と依頼できる
- 指名Residentが必要と判断した場合にCouncilを提案・開始する
- Councilは誰に任せるか、方針が割れる、複数AIの意見が有益な場合に使う
- Niraiが通常会話を勝手にFile変更Taskへ昇格しない

全Resident会議を通常Taskの必須関所にはしない。

---

## P2-C: Agent Runtime同時1件は最終形のInvariantではない

### 現状

`AgentRuntimeManager.start_session()`は非terminal Agentが1件でもあれば全Providerで次を拒否する。

### 実利用への影響

- CodexがProject Aを作業中、CursorがProject Bをread-only reviewできない
- 長いTask中に別Providerへ短い仕様相談を出せない

### 判定

**M4安全化には合理的だが、AI team最終形には制約が強い。P2 / temporary simplification。**

### 推奨

Approval routingとworkspace isolationが十分安定した後、read-only consultationとwrite workを別laneにする等、限定並列から検討する。

---

## P2-D: 長期利用でChat / Whisper読み取りがO(total history)

### 現状

- `ChatStore._read_entries()`はJSONL全文を毎回parse
- `PrivateMemoryService.recent_whispers()`もwhispers.jsonl全文を毎回parse
- `public_history(limit=20)`でも裏ではSession全体を読む

### 実利用への影響

数か月〜数年利用すると「直近20件取得」が履歴総量に比例して遅くなる。

### 判定

**長期常用スケーラビリティ不足。P2。**

### 推奨

append-only正本を維持しつつ、offset index / SQLite metadata / tail-reader等で最近N件をO(N)にしない。

---

## P2-E: World Memory Episodeは追記ごとに全File rewrite

### 現状

`record_public_entry()`はEpisode全体をreadし、markerを探し、`open("w")`で全文 + 新Entryを書き直す。

### 実利用への影響

- 長Sessionほど1発言の保存Costが増える
- crash時の耐久性がappend-onlyより弱い
- Retrieverも変更Episode全体を再indexする

### 判定

**長期常用向けでない。P2。**

### 推奨

lossless append-only event/utterance正本と、再生成可能なEpisode/chunk/indexを分離する。

---

## P2-F: Core crashで実作業Agentをresumeしない

### 現状

Agent Runtime復旧時、非terminal Sessionは全て`interrupted`になる。

### 実利用への影響

30〜60分級の作業中にCoreが落ちると、Provider側にresume可能なThread/Sessionが存在しても作業Continuationを試さない。

### 判定

**安全なfail-closedとしては妥当だが、日常作業基地としてはResilience gap。P2。**

### 推奨

最初から自動resumeする必要はない。まず「resume可能 / fresh rerun / abandon」をMasterが選べる復旧UIを検討する。

---

## P2-G: 設計ガバナンス自体が設計書を過度に保護している

### 現状

`Docs/詳細設計/00_全体構成.md`は、

- 基本設計と矛盾したら実装を止めてMasterへ報告
- 担当Milestone外は実装しない
- 書いていないことを発明しない

を強く要求する。

これらはAIの暴走防止には有効だが、設計が古くなった時にも既存仕様を守る方向へ強い圧力をかける。

今回の「Provider native Sessionがあるのに直近20件を毎回再投入」も、既存のTemporary Context設計を守ることが自然な実装になっていた。

### 判定

**プロジェクト運用上の構造的リスク。P2。**

### 推奨

設計文書を次の2種類へ明示的に分離する。

1. **Invariant / Guardrail**
   - Private Memory leak禁止
   - Master Approval
   - Secret保護
   - allowed_dirs
   - fail-closed
2. **Current Design / Hypothesis**
   - global Brain 1件
   - Agent同時1件
   - 20件Context
   - first volunteer
   - 最大Turn等

Current Designはユースケース・Provider能力・実測により変更可能とし、「正本だから守る」ではなく「目的に合わなければ更新してから実装する」運用へ変える。

この方針は`Docs/Nirai_設計ガバナンス.md`として独立ルール化した。

---

## P2-H: 大規模実装前の先行実装調査が必須Gateになっていなかった

### 現状

AITuberKit等を個別に参考にする指示は存在したが、「新しいSubsystemや一般的な問題へ着手する前に、Webを広く検索し、公式機能・成熟OSS・Reference Implementationを比較する」というProject全体の必須工程にはなっていなかった。

そのため、AIAvatarKit等の優秀な先行実装を早期に把握していれば避けられた試行錯誤・再設計・独自実装が発生し得る。

### 実利用への影響

- 車輪の再発明
- 実装工数とReview工数の増加
- 独自方式ゆえの保守負荷
- Provider / OSSが既に持つSession、Retry、Audio、Turn-End等の成熟機能を使わない非効率
- 後から先行実装を発見した際の作り直し

### 判定

**設計・開発プロセス上の構造的な非効率。P2。**

### 確定方針

`Docs/Nirai_設計ガバナンス.md`のReference-First Gateを必須とする。

大規模実装、新Subsystem、外部Provider統合、主要方式の置換、独自Algorithm等へ入る前に、公式Documentation / SDK / Example、成熟OSS、GitHub Reference、類似製品、Maintainer Issue / Discussion等を横断調査する。

調査後は「採用する考え方 / 採用しない理由 / License / Nirai固有差分」を短く記録してから実装へ進む。

# 維持すべき現行設計

- Residentの人格 / 記憶 / Brain / Avatar分離
- World MemoryとPrivate Memoryの秘匿境界
- Holoを通常Brain Driverへ押し込まない

# 長期日常利用 READY Gate

本監査の総合判定を`READY for long-term daily use`へ変更するには、少なくとも次を満たす。

## Conversation

- 通常Residentの主要Providerで、同一Nirai ConversationをProvider native Session / Thread等へ継続できる
- 通常Turnで固定件数の過去原文を毎回無条件再送しない
- Provider native Context喪失・Provider交換時も、Nirai側のIdentity / Memory正本から安全にContextを再構成できる
- 同一Conversation内のTurn順序が保証され、独立Conversationまで不必要にGlobal直列化しない
- Public / Private / participantの異なるConversation Contextをnative Session上で混同しない

## Memory

- Public / PrivateともRaw Durable Sourceをlosslessに保持する
- 240文字excerptや小さな`context.md`だけが長期記憶の唯一の正本にならない
- Structured Continuityが重要事実・関係・約束・未解決事項等を単なる直近件数超過で失わない
- Public / Private RetrieverがAccess Boundaryを維持したまま関連過去を取得できる
- UI Chat履歴削除とMemory保持、明示Forgetが正しく分離される
- 明示ForgetではRaw / Structured / Derivedの対象が整合して消え、「Indexだけ見えなくした」状態を忘却扱いにしない
- 直近N件取得で全履歴scanせず、1件追記で巨大Memory File全体を書き直さない
- 5年相当のData量を想定したScaling Test / 実測根拠がある

## Living / Concurrency

- Masterが1 Residentと会話中でも、安全に独立した別ResidentのConversation / life processingが継続できる
- Global Brain Lockを本当に必要なProvider / Resource / Conversation Lockへ縮小する
- TTS / Bubbleの混線はPresentation層で制御し、思考全体を止める理由にしない
- Background生活処理がMaster direct conversationを不必要に遅延させないPriority設計を持つ

## Task / Agent

- Masterが指名Residentへ自然言語で直接Taskを依頼できる
- 明確なDirect Taskで全Resident会議を必須にしない
- Councilは必要時だけ開始でき、担当変更時はMasterへ明示される
- 通常会話が曖昧なまま勝手にFile変更Taskへ昇格しない
- Agent RuntimeのMaster Approval / allowed_dirs / Credential isolation / fail-closed安全境界を維持する
- 全体1-Agent制約を残す場合は実測上の必要性が説明できる。不要ならResource / Provider / Workspace単位へ縮小する
- Core crash後の長時間Workについて、少なくとも安全な`resume / fresh rerun / abandon`の判断材料をMasterへ提示できる。自動Write resumeはしない

## Design / Maintainability

- `Nirai_設計ガバナンス.md`のSource of Truth階層が入口・Active Designで一貫している
- Temporary / Provider Constraint / HistoryがProduct Invariantへ紛れ込んでいない
- AI_ENTRYがRouterとして短く、Review履歴の保管庫へ戻っていない
- 大規模実装でReference-First Gateを通したEvidenceが残る
- 採用方式が合理性・効率性・保守性・Operational Simplicity・5年Scalingの観点でReviewされている
