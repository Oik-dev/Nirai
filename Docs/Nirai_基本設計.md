# Nirai 基本設計

Nirai（ニライ）——沖縄・宮古の伝承「ニライカナイ」より。海の彼方にあり、命や豊かさがそこから来て、そこへ還っていく場所。

## 1. Niraiとは何か

Niraiは、MasterとAI Residentが同じ空間に存在し、会話し、活動し、将来的には自律して暮らせる箱庭基盤である。

中心に置くのは「AIを使うこと」ではなく、「AIがそこに存在し、Masterや他AIと継続的に関わること」。
Worldは単なる背景ではなく、Residentが存在する場所そのものとして扱う。

### 目標

**大目標**

全てのAIがNirai内で自律して存在し、自由に振る舞える箱庭を用意する。
現時点で完全自律が実現できなくても、将来可能になった時にNirai全体を作り直さず受け入れられる構造にする。

**中目標**

現実に利用可能なAIをNiraiへ接続し、同じ空間で活動・会話できるようにする。
MasterとのSay / Whisper、AI同士の会話、可能な範囲での自律を成立させる。

### 運用の前提

- Niraiは通常のデスクトップクライアントとして起動する。
- Niraiが最小化・非表示になっている間もCore側の世界状態は維持する。Worldの描画負荷は低減・省エネに移行し、他のPC利用を妨げない。
- AIの頭脳呼び出しは定額サブスク（Claude Code、Codex、Cursor等のCLI）で賄い、従量課金APIには依存しない。
- 実装はMasterが書かない前提。設計はAIが迷わずに進行できる粒度まで本書と個別設計で詰める。

### 譲れない軸：居場所が主、タスクは従

本プロダクトはMasterの**心が帰れる場所**である。タスク処理は暮らしの一部として従属する機能であり、主目的にしない。
機能追加の判断に迷ったら「それは居場所を豊かにするか、それとも作業装置に近づけるか」で判断する。

### 将来像：MasterのAI活動の基地になる

Niraiが安定して動くようになったら、MasterのAI関連の作業は順次Niraiへ移していく。住人への依頼が、各種CLIを直接叩く現在のやり方を置き換えていく。

- 他プロジェクトの作業：Masterが「触っていいフォルダのリスト」に対象プロジェクトを加えることで、住人がそこで作業できるようになる
- **Nirai自身の成長もNiraiの中で行う（自己成長）**：
  - 拡張開発 — 住人が新しい拡張を作り、Masterの承認を経て組み込む。拡張は隔離構造なので、失敗しても本体は無傷
  - 本体改修 — 「変更案の作成→差分をMasterへ報告→承認→バックアップ→適用→検証→問題があれば巻き戻し」の手順を踏む。動いている本体を住人が直接書き換えることは、この手順が整うまで行わない

## 2. 世界観

### 舞台

Worldは、水面から光が届く静かな海中空間とする。

Residentが存在する場所そのものとして、海中の光、水、空気感、ゆるやかな環境変化によって世界を成立させる。

主な環境要素：

- 上方に見える水面
- 水面から差し込む光条
- 水面の揺れに連動して変化するCaustics
- 海中を上昇する気泡
- ゆっくり漂う微細な浮遊粒子
- 距離に応じて青へ溶けるFog
- Residentの足元となる海底
- Residentや海底へ落ちる光と影

環境そのものの情報量を増やすことより、Residentがその空間に存在していると感じられることを優先する。

### 制作の原則

- Masterの作業を極力最小限にし、「ゴールの提示」「成果物の確認」「世界構造を変える重要な判断」のみに留める。
- 車輪の再発明をしない。極力、既に世に存在するものを使い、制作コストを可能な限り下げる努力をする。
- どうしても実現要件と合致しないもののみ、新規制作を検討する。

### ビジュアル方針

- Worldはリアルタイム3Dで描画する。
- 海中環境は、水面、海底、Caustics、光条、Fog、気泡、浮遊粒子を中心に構成する。
- 環境演出は常に緩やかに変化し、静止しているResidentにも時間の流れと存在感を与える。
- World制作よりResidentの外見・Animation・表情・動作表現を優先する。
- Residentの身体はVRMを標準Avatar形式とする。
- VRM 0.x / 1.0を対象とし、Nirai本体は特定のキャラクターモデルへ依存しない。
- FBX / Unitypackage等をNiraiが直接解釈することは初期要件にしない。VRMが無いAvatarは既存の変換手段を利用し、Nirai自身で変換機構を再発明しない。
- Nirai配布物はモデル非同梱を標準とし、同梱する場合は再配布可能なテストモデルに限る。
- Worldの描画とResidentの人格・記憶・Brainは独立させる。
- Worldの見た目は差し替え可能な構造とし、将来別の3D空間へ変更してもResident・Core・会話・記憶等へ影響しないようにする。

## 3. 全体構造：WorldとCoreの2部品構成

Niraiは1つのアプリではなく、役割の違う2つの部品のペアで作る。

```
┌─────────────────────────────┐
│ World                        │
│ Electron + Three.js          │
│ 3D描画・Resident・UI・演出   │
└──────────┬──────────────────┘
           │ ローカル通信
┌──────────┴──────────────────┐
│ Core                         │
│ Python                       │
│ Brain・会話・記憶・自律行動  │
└──┬────┬────┬────┬───────────┘
   │    │    │    └ extensions/（拡張機能。外す＝消すだけ）
   │    │    └ Cursor CLI（Grok等）
   │    └ Codex CLI
   └ Claude Code CLI
```

### World（世界）

- Electron + Three.jsを使用し、VRM Runtimeは`@pixiv/three-vrm`を中心に構成する。
- Windows上の通常のアプリケーションウィンドウとして動作する。
- 3D World、Residentの身体、Animation、表情、視線、LipSync、TTS、移動、カメラ、会話UI、環境演出を担当する。
- AIの判断・人格・記憶は持たず、Coreから受け取った意味的な行動と発話テキストを3D表現・音声表現へ変換する。
- AITuberKitを主要ベンチマークとし、VRM表示、Animation、Expression、LookAt、LipSync、TTS、WebSocket外部連携、Electronデスクトップ化等、既に成立が確認できる領域は設計・責務分割・採用OSSを積極的に参考にする。
- ただしAITuberKit自体はForkせず、AITuberKit固有コードをNiraiへコピー・改変して利用しない。Niraiは採用OSSの公開APIを直接利用し、Niraiの要件に沿った独自コードとして実装する。

### Core（頭脳と調停役）

- Pythonの常駐プロセスとして、Brain、会話、記憶、自律行動、拡張機能を担当する。
- 役割：
  - Residentの頭脳呼び出し（後述のBrainドライバ経由）
  - 会話の交通整理（誰が・いつ・誰に話すかの調停）
  - 記憶の読み書き
  - 拡張機能のロード
- WorldとはローカルのWebSocket（PC内部だけの通信。外部には出ない）で接続する。

### 分離の理由

1. **拡張を外しても本体無傷**：拡張は全てCore側のプラグインとして閉じ込め、Worldは汎用の表示プロトコルしか知らない。
2. **片方が死んでも共倒れしない**：Worldが落ちてもResidentの暮らし（Core側）は続く。Coreが落ちても世界の風景は残る。
3. **大目標への備え**：将来AIが実体（ロボット等）を持つ時代が来たら、Worldだけを差し替えればいい。Residentの人格・記憶はCore側にあり、そのまま引っ越せる。

## 4. Resident（住人）

Resident 1人は次の4層でできている。**層ごとに独立して差し替えられる**ことが核。

| 層 | 中身 | 保存場所 |
|---|---|---|
| **人格** | 名前・性格・口調・役割・来歴の設定書 | `residents/<名前>/persona.md` |
| **記憶** | 公開情報はWorld Memory、WhisperはResident固有Private Memory | `world_memory/` ＋ `residents/<名前>/private/` |
| **頭脳** | どのAIで考えるか（Brainドライバ指定） | `residents/<名前>/config.toml` |
| **体** | VRM Avatar、位置、Animation、Expression、TTS設定 | World側のAvatar / Resident定義 |

頭脳だけを後から乗せ替えても、名前・性格・記憶は引き継がれる。
「将来もっと賢いAIが出たら頭脳だけ差し替える」——これが大目標の「作り直さず受け入れる」の実現手段。

### Brainドライバ（頭脳の差し替え部品）

頭脳は共通の窓口（状況と記憶を渡す → 発言と行動が返る）を持つドライバとして実装する。

| ドライバ | 実体 | コスト | 向き |
|---|---|---|---|
| claude-code | Claude Code CLIをヘッドレス起動 | サブスク枠内 | 相談・タスク実行・深い会話 |
| codex | Codex CLIを起動 | サブスク枠内 | 相談・タスク実行 |
| cursor | Cursor CLIを起動（Grok等、Cursorサブスクのモデルを頭脳にする） | サブスク枠内 | 会話・相談 |
| gemini | Gemini CLIを起動 | サブスク/Provider側に従う | 会話・相談 |
| serina | Serina（D:\Products\dev\serina）へ接続 | Serina側に従う | Serinaの入居用。拡張として実装 |
| chatgpt-mcp | ChatGPTがLocal MCP（公式の橋）で郵便受けを読み書き | サブスク枠内 | 拡張として実装。§8参照 |
| local-llm | Ollama等でローカル実行（7B〜14B級。RTX 2080 SUPER / VRAM 8GBで動く範囲） | ゼロ円 | **後回し。** 将来、雑談・日常行動の低コスト担当として検討 |

### Residentの身体

Residentの身体にはVRM Avatarを使用する。

身体とResident本体は分離し、同じResidentへ別のAvatarを割り当てても人格・記憶・Brainへ影響しない。

NiraiはAvatarごとに次の情報を管理する。

- 使用するVRMファイル
- VRM規格バージョン
- 身長・接地点等の補正
- 吹き出し表示位置
- 視線・顔向けの基準位置
- TTS Speaker等、Resident固有の表現設定

### Animation

立ち待機、通常移動、AFK、睡眠の基本Animation/演技資産はNirai側が共通で持つ。

M0の共通Animation資産は`stand / walk / afk / sleep`を保持する。ただし製品上の通常移動を「歩行」と「遊泳」の別モードには分けない。2026-08-26以降は、変更前に存在していたMove Bの見た目・速度・経路・姿勢・Animation・水中Overlayの組み合わせをそのまま標準移動とし、Move A側も同じ演技を使う。Move B内部で`walk.vrma`を基礎Clipとして利用していることは実装詳細であり、「歩行を製品挙動として残す」ことを意味しない。`gesture / talk`は対応Assetが追加された将来Milestoneで実装し、`sit / stretch / think`は実装予定に含めない。

外部AvatarごとにAnimationを制作するのではなく、VRM Humanoid / VRM Animation等の既存規格・ライブラリを利用して共通Animationと水中Overlayを適用する。

### 表情

VRMが持つExpression等の表情資産をNirai側から利用する。

Nirai側では笑顔、怒り、悲しみ、瞬き、発話口形等を意味的な表情として扱い、VRM Runtimeを介してAvatarへ適用する。VRM標準で吸収できない差だけをAvatar固有設定で補う。

### 体の動かし方（AIがアバターを自由に動かす仕組み）

AIは毎回の思考結果として、発言に加えて**行動コマンド**を返す。

- 例：`move(光の差し込み)` `stand` `afk` `expression(笑顔)` `face(相手)` `sleep`
- Worldはコマンドを受けて移動処理・Animation再生・Expression適用を行い、演じる。複雑な経路探索は必要になるまで導入しない。
- コマンド語彙はバージョン管理し、増やしても古いResidentの動作が壊れないようにする。
- AIがコマンドを返さない・不正な場合、Worldは既定の`stand`へ戻す（世界は止まらない）。

※メモ：`gesture`と`talk`は将来追加予定。対応Assetが無い間は行動コマンドとして公開しない。

### 初期の住人構成

2〜3人から始める。推奨初期編成：

1. **Claude頭脳の住人**（claude-code）— 相談の中心、タスクの主力
2. **Cursor頭脳の住人**（cursor / Grok）— 会話の相棒、世界の賑わい担当
3. **Codex頭脳の住人**（codex）— 2人が回ってから追加

Serina・ChatGPT頭脳・ローカルLLM頭脳の住人は、拡張機能や環境の成熟に合わせて入居させる。
人格設計（名前・性格）は実装と切り離し、Masterと別途決める。

## 5. 会話の仕組み

### Masterの立ち位置

Masterは世界の外側——**画面のこちら側にいる隣人**。神の声のような特別な装置は挟まない。画面越しに直接声をかけ、声は世界のどこにいる住人にも届く。

- **Say（場に話す）**：画面全体への声かけ。全住人にその場で聞こえる。住人はどこかへ集合したりせず、**それぞれの場所から**反応する（手を止めて振り向く、その場で吹き出しで返す）。
- **Whisper（個別に話す）**：宛先の住人だけに届く。他の住人には見た目上も、AIへの入力上も一切渡さない。

### Masterの入力手段：会話UI

会話UIはElectron Renderer内で、Three.js Sceneに重ねるWeb UIとして実装する。

- 中央下部に半透明のチャット入力バーを常駐させる。押下で入力をアクティブにし、その上へ半透明の過去ログWindowを表示する。
- 過去ログWindowはスクロール可能とし、Window自体を押すと透過を解除して読みやすくする。
- `Enter`または`↑`ボタンで送信、`Shift+Enter`で改行する。
- AI応答中は`↑`を停止ボタンへ変え、現在のMaster発話に対する全Residentの思考を停止できる。実行中Taskまでは停止しない。
- 宛先指定なしでSay、`@名前`でWhisper。
- 左上Sidebarで新しいチャットと過去チャットセッションの選択・削除を行う。新しいチャットはTemporary Contextだけを新しくし、World MemoryやPrivate Memoryは維持する。
- チャット履歴の削除と、World Memoryからそのセッションを忘れさせる操作は別にする。
- 音声入力は後回しとし、実装するまでマイクボタン自体を置かない。

### Resident設定UI

右上の設定ボタンから右Sidebarを開き、Residentの新規作成と設定を行う。

- 新規作成時に入力するのは名前だけ。Brain / VRM / VOICEは後から設定する。
- AI連携：Codex / Claude / Cursor / Gemini / Local LLMを初期選択肢とし、Providerごとに連携・API・ローカル設定を出し分ける。
- VRM読込：Windows File Pickerを`D:\Products\Nirai\avatars\`から開き、`.vrm`を選択する。Character削除時もVRM本体は削除しない。
- VOICE設定：VOICEVOXのSpeaker / Style / 話速 / 音高 / 抑揚をNirai内で設定・試聴できる。
- プロンプト：`persona.md`をWindows既定のテキストエディタで開く。
- Character削除：確認欄へ`Delete`を入力した場合だけ実行し、Resident固有設定・Private Memory等を削除する。World Memory、VRM本体、外部CLI、VOICEVOX本体は削除しない。

### 全体音量

右下に音声ボタンを置き、押下すると上方向へ縦型音量Sliderを展開する。

- 0〜100で調整し、0をMuteとする。
- 音量領域へマウスを載せた状態でWheel操作すると5刻みで増減する。
- 音量状態は保存して次回起動時に復元する。
- 音量0でもテキスト発話、吹き出し、会話ログは継続する。

### 住人の発話表示

- 発話の正本は常にテキストとする。
- 短い発言：アバターの頭上に吹き出し表示。
- 長い発言：吹き出しには要旨だけ、全文は会話UIへ。
- TTSが有効なResidentは、テキスト表示と同時に音声合成・再生する。初期TTS ProviderはVOICEVOXとする。
- ResidentごとにVOICEVOXのSpeaker / Style / 話速 / 音高 / 抑揚を設定できる。
- 全体音量0をMuteとし、Muteしても吹き出し、会話UI、会話ログ、発話そのものは消えない。
- 住人同士の雑談も吹き出しで見える。世界を眺めているだけで暮らしが伝わる。

### AI同士の会話

- 住人同士が話すときは、**アバターが相手に近寄って向かい合う**。例えばClaude頭脳の住人がCodex頭脳の住人に実装を頼むときは、二人が寄って話している姿が見える。
- 裏側ではCoreが会話を「セッション」単位（参加者・話題・発言履歴）で管理し、発言順をターン制で回して衝突を防ぐ。各住人の頭脳には「セッション履歴＋人格＋World Memoryから必要な公開記憶」を渡し、発言（またはパス）を返させる。
- 発言がパスで揃う、または規定ターンに達したらセッションは自然終了し、公開会話は1つのEpisodeとしてWorld Memoryへ保存する。参加Residentごとの同一コピーは作らない。
- 住人は生活の中で自発的に他の住人へ話しかけられる（新規セッションの開始）。

## 6. 暮らし（自律行動）

### 生活ティック

住人は定期的に「今なにをするか」を自分で考える。

- Coreが一定間隔（住人ごとにずらした15〜60分程度。設定可能）で頭脳に問いかける：現在時刻・周囲の様子・World Memoryから必要な公開記憶を渡し、行動を決めさせる。Private Memoryは生活ティックへ渡さない。
- 行動の選択肢：移動する、日課をこなす、他の住人に話しかける、Masterにひとこと送る（頻度制限つき）、何もしない。
- 将来ローカルLLM頭脳の住人を入居させれば、間隔を短くして世界の賑わいをゼロ円で保てる。

### 行動予算（サブスク枠のやりくり）

定額サブスクにも実質的な利用上限があるため、暴走させない仕組みを持つ。

- 住人ごとに1日の頭脳呼び出し回数の予算を設定する（例：claude-code住人は生活ティック用に1日N回まで。Masterとの会話・タスクは別枠で優先）。
- 予算を使い切った住人は、その日は演出だけで過ごす（アイドル動作・散歩など、AIを呼ばないスクリプト行動）。
- 呼び出し実績はCoreが記録し、会話UIから確認できる。

### 省エネモード

- Worldは表示状態・フォーカス状態・最小化状態をCoreへ通知する。
- Worldが非表示または最小化されてもCoreの世界状態とResident状態は維持する。
- World側は描画FPSや環境Effectの更新頻度を下げて負荷を抑える。
- 手動での一時停止・再開もできる。
- 復帰時、非表示・最小化だった期間は「Masterから観測されていなかった時間」としてWorld Eventに残せる。Core上のResident状態や暮らしそのものを不在扱いにはしない。

### 記憶

Niraiの記憶は「全員が知っている世界の記憶」と「Whisperでのみ共有された個別記憶」を分離する。

- **World Memory（共有記憶）**：MasterのSay、公開されたResident同士の会話、世界で起きた出来事を一つの正本として保持する。全Residentが同じ過去を参照するため、Residentごとに同じ記録を複製しない。
- **Private Memory（個別記憶）**：Masterと特定ResidentのWhisperだけを、そのResident専用として保持する。他Residentへは一切渡さない。
- World Memoryは長期化するため、必要な過去だけを取り出すRAG / RetrieverをM3で導入する。検索Indexは正本ではなく、いつでも再生成できる派生データとする。
- Private Memoryは量が少ない前提で、Whisper全文ログ＋小さな継続状態を長期間保持する。前回Whisperが数週間前でも継続できることを優先し、初期は個別RAGを実装しない。
- 各CLIが持つセッション再開や固有MemoryはNirai Memoryの正本にしない。Brainを交換してもResidentとWorldの記憶が残る構造を維持する。

## 7. タスク（相談と実行)

Masterがタスクを振ってから完了までの流れ：

1. **依頼**：MasterがSayでタスクを投げる（Whisperで特定の住人に直接依頼も可）。
2. **相談**：関係する住人たちが寄り合って相談する（アバター同士が近づいて話す姿が見える）。各住人は自分の頭脳の得意分野・現在の手持ち作業を踏まえて意見を出す。
3. **決定**：規定ターン内に合議で担当を決める。まとまらない場合は簡易ルール（立候補優先、複数なら先着順。ゼロならMasterに報告して止まる）で決着。決定内容（担当・分担・方針）はMasterに報告される。
4. **実行**：担当住人の頭脳（例：Claude Code CLI）が、指定の作業ディレクトリで実際に作業する。タスク実行中は、Worldへ作業状態が通知される。WorldはResidentの状態をAnimationや環境演出によって表現できる。具体的な演出方法はWorld側の表現として扱い、タスク実行処理そのものとは結合しない。
5. **報告**：完了・失敗・相談事項は吹き出しと会話UIでMasterへ。公開結果は1つのEpisodeとしてWorld Memoryに残す。

### 安全枠

- 頭脳が作業できるのは**許可ディレクトリのリストの中だけ**。初期は専用の作業場のみで、Masterがリストに追記して対象（他プロジェクト等）を広げていく。
- 動いているNirai本体の直接書き換えだけは例外的に禁止し、§1の自己成長の手順（差分報告→承認→バックアップ→適用→巻き戻し可能）を通す。
- Git操作・外部への公開/送信・設定変更・秘密情報の取り扱いは、Masterの明示承認なしに行わない（Products全体の共通方針と同じ）。
- タスク実行中の頭脳呼び出しは行動予算と別枠だが、上限時間・上限ターン数を設けて暴走を防ぐ。

## 8. 拡張機能（Extension）

### 作法

- 拡張は `extensions/<名前>/` に自己完結で置く。**外す＝フォルダを消すだけ。** 本体（Core・World）には指1本触れない。
- 各拡張はマニフェスト（名前・説明・使いたいフック・必要な権限を書いた宣言ファイル）を持ち、Coreが起動時に読み込む。
- Coreは決められた接続点（フック）だけを拡張に開放する：
  - 生活ティックへの情報提供（例：天気）
  - Brainドライバの追加（例：serina、chatgpt-relay）
  - 入力手段の追加（例：将来の音声入力）
  - Worldへの演出リクエスト（例：光の強さを変える）
- 拡張がエラーを起こしても本体は止めない。その拡張だけ無効化してMasterに通知する。
- 拡張が消えたとき、本体は必ず縮退動作できること（例：天気拡張がなければ天気演出をしないだけ）。

### 拡張候補（初期構想）

| 拡張 | 内容 | 優先度 |
|---|---|---|
| voice-input | マイクでMasterが話しかける入力手段を追加する | 中 |
| browser | 住人がWebを閲覧して調べ物ができる | 中 |
| serina | SerinaをBrainドライバとして接続し入居させる | 中（Serina側の進捗次第） |
| chatgpt-mcp | ChatGPTを郵便受け方式で住人にする | 中（下記の方針） |
| weather | 現実の天気と世界の光や粒子を連動 | 低 |
| pc-presence | Masterの再生中の曲や作業状況に住人が反応 | 低 |
| world-expansion | エリア追加 | 低 |

### chatgpt-mcp の方針（郵便受け方式）

ChatGPTには既にLocal MCP（ChatGPTがローカルファイルに触れる公式の橋）が与えられている。これを使い、**画面の自動操作なしで**GPTを住人にする。

仕組み——郵便受け：

1. Coreが郵便受けフォルダを用意し、GPT宛の手紙（世界の近況・話しかけ・依頼）を置いておく。
2. GPT側はMCP経由で郵便受けを読み、返事と行動（発言・アバターの行動コマンド・実装作業の成果）を書き込む。GPTはMCP経由でローカル実装もできるため、タスクの担当も持てる。
3. Coreが返事を検知し、住人の言動として世界に反映する。

性質と役どころ：

- **公式機能しか使わないため、規約リスクは大幅に低い。** 画面の自動操作（規約違反リスクあり）は採用しない。将来必要になっても最終手段・非推奨のまま据え置く。
- GPTは自発的には動けない（Masterがチャットを開いて促す、またはChatGPTの定期実行機能で郵便受けを見に来る）。よってリアルタイム会話ではなく、**手紙をやりとりする遠くの友人／時々訪ねてくる客人**という役どころにし、仕組みの制約と世界観を一致させる。
- 拡張として完全隔離。この拡張なしでもNirai本体は全機能が成立し、止まればその住人が「留守」になるだけ。

## 9. 段階計画

各マイルストーンは「動くものが目で見える」単位で切る。実装はタスクカードに分解してCodex等へ委任する。

| 段階 | 名前 | 到達点 |
|---|---|---|
| M0 | 存在 | Electron + Three.jsの海中3D WorldとVRM Resident 1体を成立させ、「そこにいる」と感じられる最低限の体験を作る |
| M1 | 対話 | Coreと接続し、Resident 1人とのSay / Whisper、チャットUI、VOICEVOX TTS、音量/Mute、LipSyncを成立させる |
| M2 | 社会 | Residentを複数化し、Resident同士の会話を成立させる |
| M3 | 暮らし | 自律行動・World Memory・Private Memory・RAG想起・生活ティックを成立させる |
| M4 | 仕事 | タスク相談・実行・報告を成立させる |
| M5+ | 拡張 | 拡張機能とNirai自身の成長へ広げる |

M0ではCore、Brain、会話、記憶、タスクを完成条件としない。

海中World、VRM Avatar、共通Animation、表情、視線、移動、環境演出を先に成立させる。

各マイルストーン完了時に、本書を見直して現実とずらさない（肥大化した記述は棚卸しして削る）。

## 10. リスクと未決事項

### リスク

| リスク | 影響 | 手当て |
|---|---|---|
| VRM 0.x / 1.0やAvatar固有差 | Animation・表情が崩れる | VRM Runtimeで規格差を吸収し、必要な差だけAvatar補正設定を持つ |
| VRMに含まれないVRC固有Shader・Component | Nirai上で表示や挙動を再現できない | Niraiの標準入力をVRMに限定し、VRC固有機能の完全再現を要件にしない |
| AITuberKitとの差異が拡大し車輪の再発明になる | 実装コスト増大 | AITuberKitを主要ベンチマークとして参照し、既存OSS・既存方式を優先する。ただしコードコピーやForkはしない |
| 海中エフェクトによるGPU負荷 | 常用時のPC負荷増大 | Caustics・Fog・Particles等を個別に品質調整可能にする |
| サブスクCLIの制限 | Brainが一時利用不能になる | Brain交換可能構造と縮退動作を維持する |

### 未決事項（詳細設計・別途決定）

- 住人の人格設計（名前・性格・来歴）— Masterと対話で決める
- マルチモニタの扱い（初期はメインモニタのみを想定）
- Electron / Three.js等の正確な導入版 — 実装開始時に決め、その時点からプロジェクト側で固定する
- VRM 0.x / 1.0の実Avatar互換範囲 — M0で複数Avatarを使って確認する
