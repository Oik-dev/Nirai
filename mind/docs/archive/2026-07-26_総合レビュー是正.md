## A2. 時間検索の暦を Serina 日に揃える

**問題**: `core/memory/recall_planner.py:28-55` の「昨日／一昨日／先週／この前／先日」の
日付範囲が、渡された `now`（UTC）の暦でそのまま計算されている。JST とは 9 時間ずれるため、
深夜〜朝 9 時の会話では「昨日」が丸一日ずれる。システム全体は Serina 日
（`core/state/serina_day.py`・境界 07:00 ローカル）で統一されている。

**対象**: `core/memory/recall_planner.py`

**変更内容**:
1. `core/state/serina_day.py` の `serina_day_id` / `serina_day_start` を import する
   （同一層内・依存の向きは Core 内で閉じるため層またぎではない）。
2. `_day_bounds(day)` を Serina 日ベースへ置き換える。新シグネチャ:
   `_serina_day_bounds(day_id: date, *, boundary_hour: int = 7) -> tuple[str, str]`
   - 開始 = `serina_day_start(day_id, boundary_hour=boundary_hour).isoformat()`
   - 終了 = `serina_day_start(day_id + timedelta(days=1), boundary_hour=boundary_hour).isoformat()`
     （終了は**排他的上限**。`search_by_time_range` は `valid_from <= end` の閉区間比較のため、
     1 マイクロ秒引いた値を渡す）
3. 各ルールの対象日を Serina 日で算出する:
   - `昨日` = `serina_day_id(now) - 1 日`
   - `一昨日` = `serina_day_id(now) - 2 日`
   - `先週` = `serina_day_id(now) - 7 日` の開始 〜 `now`
   - `この前` / `先日` = `serina_day_id(now) - 3 日` の開始 〜 `now`
4. `boundary_hour` はハードコードせず `core.state.serina_day.SERINA_DAY_HOUR` を既定に使う。

**契約**: 時間範囲は必ず UTC ISO 文字列で返す（`FactStore.search_by_time_range` が UTC 前提）。
ローカル暦の判定は `serina_day_id` に一本化し、このモジュールで `astimezone()` を直接呼ばない。

**テスト**: `tests/test_recall_planner.py` に、JST 深夜 02:00（= UTC 前日 17:00）に
「昨日」を含む発話を渡したとき、返る範囲が「前の Serina 日の 07:00〜翌 07:00（UTC 換算）」に
なることを確認するケースを追加する。

## A5. 感情①: 対極カップリング

**目的**: 喜び 0.9 と悲しみ 0.9 が同時に立つ非人間的な状態を防ぎ、和解・慰めの流れで
Brain が「＋喜び」しか報告しなくても負の情動が自然に引く挙動を、決定論で成立させる。

**対象**: `core/state/emotion.py` / `core/config.py` / `config/thresholds.toml`

**変更内容**:
1. `core/state/emotion.py` に対極表を定義する（プルチックの輪の対極）:
   ```
   OPPOSITE_AXES = 喜び↔悲しみ / 信頼↔嫌悪 / 恐れ↔怒り / 驚き↔期待
   ```
   双方向に引ける dict として持つ。
2. `apply_affect_delta(deltas, *, opposite_coupling_ratio: float = 0.0)` を拡張する。
   処理順を厳密に次のとおりとする:
   1. 既知軸のみを抽出した「明示デルタ」集合を作る（未知軸は従来どおり無視）
   2. 明示デルタをすべて適用する
   3. 明示デルタのうち**正の増加のみ**を対象に、その対極軸へ
      `-delta * opposite_coupling_ratio` を適用する
   4. **対極側の軸が明示デルタに含まれる場合は、その軸へのカップリングを適用しない**
      （Brain の明示指定が優先。矛盾した報告でも決定論的に解決する）
   5. すべての適用後に 0.0〜1.0 でクランプする
3. **負のデルタにはカップリングを適用しない**。「悲しみが減った」は「喜びが生まれた」ではない
   （幽霊感情の生成を防ぐ）。
4. `ThresholdsConfig` に `emotion_opposite_coupling_ratio: float = 0.5` を追加し、
   `config/thresholds.toml` の `[emotion_decay]` セクションへ
   `opposite_coupling_ratio = 0.5  # 対極カップリング（§2.3）` を追記する。
5. 呼び出し元 `core/intake/gate.py:_apply_fusen` から比率を渡す。

**契約**: LLM を一切呼ばない決定論変換。関所②（確信度足切り）通過後の付箋にのみ作用する。

**テスト**: `tests/test_emotion_state.py` に追加
- 喜び +0.4 のみ報告 → 悲しみが 0.2 減る（初期悲しみ 0.5 → 0.3）
- 喜び +0.4 と悲しみ +0.1 を同時報告 → 悲しみは明示値どおり +0.1（カップリング不適用）
- 悲しみ -0.3 のみ報告 → 喜びは動かない
- `opposite_coupling_ratio=0.0` で従来と同一挙動

## A6. 感情②: 気分を「情動のにじみ」へ変更する

**目的**: 気分（遅い層）を情動と同じデルタで直接動かす現行方式をやめ、
**気分は毎ターン、その時点の情動へ向かって少しだけ引き寄せられる**方式にする。
一度きりの大きな感情では気分はほぼ動かず、同じ情動が続いた日数分だけ気分が染まる。

**対象**: `core/state/emotion.py` / `core/intake/gate.py` / `core/config.py` /
`config/thresholds.toml` / `docs/設計書.md` §2.3

**変更内容**:
1. `EmotionState` に新メソッドを追加する:
   ```
   apply_mood_bleed(*, bleed_rate: float, max_delta_per_turn: float) -> None
   ```
   - 各軸について `delta = (affect[axis] - mood[axis]) * bleed_rate`
   - `delta` を `±max_delta_per_turn` でクランプ（安全上限）
   - `mood[axis]` に加算し 0.0〜1.0 でクランプ
   - いずれかの軸が 0.001 以上動いたときのみ軌跡へスナップショットを追記する
     （毎ターン追記による軌跡肥大の防止）
2. `apply_mood_delta()` は**削除しない**。後方互換のため残し、docstring に
   「旧方式。現行経路は `apply_mood_bleed`」と明記する（既存テストの資産を壊さない）。
3. `core/intake/gate.py:process_report` の付箋ループから気分更新を外す。
   ループ**完了後に 1 回だけ** `emotion.apply_mood_bleed(...)` を呼ぶ。
   - 付箋が 1 枚も無いターンでも呼ぶ（気分は情動の履歴を追うため、
     新規入力が無くても直前の情動へ向かって進む）
   - `_apply_fusen` は情動（`apply_affect_delta`）と関係観測のみを担当する形に整理する
4. `ThresholdsConfig` に `emotion_mood_bleed_rate: float = 0.08` を追加し、
   `config/thresholds.toml` の `[emotion_decay]` へ
   `mood_bleed_rate = 0.08  # 気分が情動へにじむ速さ（§2.3）` を追記する。
5. `mood_guard_max_delta_per_turn`（現行 0.1）は**残す**。にじみ量の安全上限として
   `apply_mood_bleed` に渡す。設定キーの削除は config・toml・テストの改修コストに対して
   得るものが無いため行わない。docstring に「上限であり主機構ではない」と記す。
6. 設計書 §2.3 の気分層の説明を「急変防止弁つきの直接更新」から
   「情動へのにじみ（追従）＋上限クランプ」へ改訂する。関所③の記述も同様に更新する。

**契約**: 1 ターンにつき気分更新はちょうど 1 回。順序は
「時間冷却（`_cool_emotion`）→ 情動デルタ適用 → 気分にじみ」で固定する。

**テスト**: `tests/test_emotion_state.py` / `tests/test_intake_gate.py`
- 情動 0.8・気分 0.0 の状態で 1 ターン → 気分が `0.8 * 0.08 = 0.064` 増える
- 同じ情動が 10 ターン続く → 気分が単調増加し 0.8 へ漸近する（超えない）
- 付箋 0 枚のターンでも気分が情動へ寄る
- にじみ量が `max_delta_per_turn` を超えないこと（bleed_rate を大きくして確認）
- 関所②で棄却された付箋が情動にも気分にも影響しないこと（既存テストの維持）

## A8. Pulse の約束スキャンを軽くする

**問題**: `app/gui_server.py:1003-1004` が見回りの**毎 tick（20 秒間隔）**に
`list_promise_memories_for_pulse()` を呼ぶ。この関数（`core/runtime.py:682`）は
`list_by_type_and_legacy_type()` を経由し、**`type='semantic'` の全行（実測 525 件）を
SQL で取得してから Python 側で metadata の JSON を 1 件ずつパース**する。
深夜帯・mute 中・会話中など Pulse が発火し得ない時間帯でも毎回実行される。

**注記**: 未回収の約束を Pulse の材料にすること自体は設計書 §2.8「記憶: 未回収の約束・記念日」で
定義済み（「A 全部やる」で承認）。本項は**動作の廃止ではなく実行タイミングと SQL の是正**。

**追加調査で判明した事実（2026-07-26 実測）**:
`metadata.legacy_type` を書き込むのは `tools/import_legacy_memories.py` と
`tools/migrate_memory_types.py` のみ。本番蒸留（`core/intake/memory_review.py:review_candidate`）は
`metadata_obj={"source_quotes": [quote]}` だけを書くため **legacy_type を付けない**。
実 DB の内訳は `event 480 / knowledge 25 / relationship 8 / promise 11`（すべて移行由来）。
つまり**約束一覧は実行時に増えず、GUI の削除・編集以外で変化しない**。
したがって毎 tick の再取得は無意味であり、**起動時に一度読んでキャッシュする**のが正しい。

**対象**: `app/gui_server.py` / `core/runtime.py`

**変更内容**:
1. `GuiState` に約束一覧のキャッシュを持たせる。
   - `self.promise_cache: list[tuple[int, str]] | None = None`
   - `self.promise_cache_lock = threading.Lock()`
2. `_maybe_fire_pulse_inner` はキャッシュが `None` のときだけ
   `state.core.list_promise_memories_for_pulse()` を呼び、結果を格納する。以降は再利用する。
3. キャッシュを `None` に戻す（＝次回再取得させる）のは次の 3 箇所のみ:
   - `_maybe_run_serina_day_boundary_inner` の蒸留消化フェーズ完了後
   - `api_memories_delete`（記憶削除後）
