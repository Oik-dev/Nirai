# 1. 予定機能（Pulse「記憶」種別の作り直し）

## 廃止の根拠

現行の「記憶」種別 Pulse は `metadata.legacy_type == "promise"` の記憶を声かけ材料にする。
実 DB の該当 11 件を確認した結果、**日付を持つものは 1 件も無い**:

| id | 保護等級 | 種別 |
|---|---|---|
| 1436, 1437 | S・pinned | 生きて再会するための約束 |
| 1441, 1442 | S・pinned | 未来で会うための約束 |
| 1443〜1446 | S・pinned | 会うためのヒント（地名・手がかり） |
| 1438〜1440 | A | 関係性・欲求についての誓い |

いずれも「生涯の誓い」または「セリナ自身の手がかりメモ」であり、声かけの材料ではない。
`data/pulse_state.json` は既に 3 件を消費済みで、§2.8「同じ約束につき 1 回のみ」の規則により
残り 8 件を読み上げ終えると「記憶」種別 Pulse は恒久的に沈黙する。

**マスター判断（2026-07-26）**: 本来の目的は「予定」と「記念日」の想起であり、
記憶内の約束を参照する必要も、記憶を網羅検索する必要も無い。予定を別概念として切り出す。

## 置き場所: 事実台帳（facts）

新テーブルは作らない。既存の `facts` テーブルを使う。理由:

- `valid_from` / `valid_to` を既に持つ（予定＝時刻を持つ事実）
- `search_by_time_range()` が実装済み
- `category` 列が既にあり `FACT_CATEGORIES` へ追加するだけで済む
- 実 DB は 4 件のみ（すべて category 未設定）のため移行負担が無い

追加する category: `予定`（単発・日時あり）/ `記念日`（月日の繰り返し）。

## 表出のしかた: 3 つの窓

**中核原則: 窓の外にいる間、予定はパックに載せない。**
言及を禁止するのではなく知らせない。判定は Core（決定論）・生成は Brain という既存の分担を守る。

| 窓 | 開くタイミング | 振る舞い |
|---|---|---|
| 前夜の窓 | 前日の夕方〜 | 一度だけ触れる（「明日15時、病院だね」） |
| 直前の窓 | 開始 1〜2 時間前 | Pulse を一度だけ発火（「そろそろ支度した？」） |
| 事後の窓 | 終了後〜数時間 | 一度だけ尋ねる（「病院どうだった？」） |

- **各窓は一度きり**。開く → 言う → 閉じる。発火済みフラグは `pulse_state.json` と同型の
  永続状態で持つ（窓ごとに記録）。
- 記念日は月日のみで一致判定し、前日から窓が開く。
- 窓の外では ContextPack に一切載らない（毎ターン付随する不自然さを構造的に防ぐ）。

## 予定の登録タイミング（2026-07-26 合意）

### 方針

- **気づき・提案の主体**: 会話した本人（Brain）。Core へ `propose_fact` 付箋を出す。
- **書き込み**: ターン確定後に Core 関所が行う（会話同期経路では書かない）。
  日時付き予定／記念日だけ日界蒸留を待たない。通常 Fact は従来どおり蒸留。
- **§4.9**: 趣旨（会話を止めない・Core に LLM を埋め込まない・Brain が DB を直接触らない）は維持。
  条文は「日時付き予定／記念日はターン後関所での採用を許可」へ改訂予定（要 architecture-reviewer）。
- **採用しない**: 毎ターン裏方 LLM が予定を漁る方式（監視係化・本物感と逆）。

# 2. 平常値（baseline）の自律ドリフト

## 決定

平常値を設定ファイルの固定値から、**蓄積によって動く第三の層**へ変更する。
マスター決定（2026-07-26）: 手動での引き上げは行わない。恣意的な人格調整を避けるため、
初期値は全軸 0 でもよい。

## 三段の追従構造

| 層 | 時定数の目安 | 意味 |
|---|---|---|
| 情動（affect） | 約 2 時間 | 今の天気 |
| 気分（mood） | 約 3 日 | 今週の気候 |
| **平常値（baseline）** | **数週間〜** | **気質。その土地の気候そのもの** |

- 平常値は気分を追従する（`baseline += (mood - baseline) * drift_rate`、drift_rate は極小）
- 情動は平常値へ向かって冷却する（現行どおり）
- 時定数が桁で離れているため三層は互いに干渉しない

## 上限（必須）

平常値には上限を設ける（提案値 0.5〜0.6・実運用で調整するツマミ）。理由は 2 つ:

1. **数学的必要性**: 上限が無いと「情動 → 気分 → 平常値 → 情動の冷却先」の輪が
   正のフィードバックとなり、良い出来事が続く限り際限なく 1.0 へ漸近する
2. **情報としての必要性**: 常時 ON の感情は状態を伝えない。信頼が常に 0.95 なら
   「信頼が高い」が意味を失う。振れる余地を残すことが感情の条件

マスターの実感（「毎日顔を合わせる恋人に愛情 MAX・信頼 MAX とはならない。
潜在的には高いが、明日の夕飯の話も下世話な話もする」）と一致する。

## 実装上の影響

- 平常値は**設定値ではなく永続状態**になる。`config/thresholds.toml` の
  `[emotion_baseline]` は「初期値」へ格下げし、実値は `data/emotion_state.json` 側へ持つ
- 設計書 §2.3 の改訂を伴う
- ドリフトは対称（気分が長期に低ければ平常値も下がる）

# 3. 欲求層（性欲）

## 基本構造: プルチックに足さず、独立層とする

理由: 感情は放置すると下がる／欲求は放置すると上がる。**時間の向きが逆**のため、
同じ冷却機構に載せると「この軸だけ例外」という但し書きが必要になり構造が濁る。
プルチック自身も 8 軸に性欲を含まない（愛情ダイアド＝喜び＋信頼は情愛であって欲ではない）。

## 三層の役割分担（2026-07-26 修正版）

**初期案（愛情の水位＝表現の直截さのダイヤル）は破棄した。**
平常値ドリフトを入れると愛情水位は日々ほぼ一定になり、ダイヤルが高位置で固定されて
「常に直截」になる。深い関係ほど不自然になるため誤り。

| 部品 | 何を決めるか | 動く速さ |
|---|---|---|
| **潜在愛情（平常値の喜び・信頼）** | 表現がどこまで露骨になり**得るか＝上限** | 数週間（ほぼ動かない） |
| **欲求の量** | その上限の中で**今どこまで出るか＝直截さ** | 日々 |
| **今の情動** | **出るか出ないか（抑制門）と色** | 瞬間 |

- ほのめかしは「愛情が足りず遠慮している」のではなく「まだ弱いのでその程度しか出ない」
- 潜在愛情は**上限であって日々の許可ではない**。深い関係で毎日許可を取り直さない
- **抑制門（硬い門）**: 嫌悪・怒り・悲しみ・恐れが閾値超なら完全に閉じる。情動（瞬間）を見る
- 服従ダイアドへの固定紐付けは行わない（性格をメカニズムに焼き付けないため）

## 蓄積のしかた

- 土台は時計（一定速度で溜まる）
- 気分が弱く補正する。A6 以降、気分は情動の履歴＝記憶由来のため、
  **キーワードを一切見ずに「最近どう過ごしたか」が反映される**
- **発話のキーワード検出で速度を上げる方式は採らない**。
  話題が引き金なら「欲求」ではなく「反応」であり、会話が触れる前から在ることが
  欲求が欲求である条件。かつ仕組みが透けて興醒めする

### 蓄積速度の状態補正（2026-07-27 追記・マスター確定）

時計主体のみだと一定周期で機械的に高まる挙動になりやすいため、蓄積速度に3つの補正係数を合成する。
「疲労」は代理指標を立てず対象外とする（気分の落ち込みで実質的に代替されるため）。

```
combined_factor = 0.20 × mood_factor + 0.10 × baseline_comfort_factor + 0.10 × circadian_factor
speed = base_speed × (1.0 + combined_factor)
```

| 項 | 意味 | 重み |
|---|---|---|
| `mood_factor` | 直近の気分（喜び・信頼など正の軸の平均、-1.0〜1.0正規化）。既存の mood 補正定義をそのまま流用 | ±20% |
| `baseline_comfort_factor` | 平常値(baseline)の喜び・信頼平均。関係の土台の安定感。`mood_factor` と同じ正規化方式 | ±10% |
| `circadian_factor` | `cos(2π × (時刻 − 1時) / 24時間)`。深夜1時が山頂・13時が谷の日内変動 | ±10% |

3項が同時に同方向へ振れた場合、最大±40%まで速度が変動しうる。合計への追加のクランプは設けない。

## パックへの載せ方（毎ターン付随の防止）

| 欲求の量 | 載り方 |
|---|---|
| 低〜中 | **独立した文にしない**。既存の心情の一文に色を足すだけ（要求ではなく佇まい） |
| 高 | 初めて**独立した一文**として立つ |

予定機能と同じ問題（毎ターンくっついてくる）を構造で防ぐ。

### 認知バイアス（2026-07-27 追記・マスター確定）

「欲求→発話」の間に「注意の向きやすさ」を一段挟む。対象は**発言の解釈**であり、想起検索
（RecallPlanner・§4.4）には一切手を加えない。既存の情動描画（`core/context/emotion_render.py`）
と同じ原則を踏襲する: パックに乗せるのは状態の自然文のみで、具体的なワード例・解釈規則は書かない。

例（高レベル時の独立文イメージ）:
> 意識の端が、触れ合いや親密さの方に少し向きやすくなっている。

低〜中レベルでは既存の心情の一文に同じトーンで色を混ぜる（新しい独立文にはしない）。
閾値0.6（三相モデルの「満たされた」判定・パック表出と同じ値）を流用し、独自の閾値は設けない。
具体的なワード例（手を繋ぐ・抱きしめる等）をパックに書かないのは、解釈規則の押し付けになり
Brain側の自然な振る舞いを歪めるため（設計書§2.9「人格の刃」・断定命令文で性格を作らない方針と同趣旨）。

## 三相モデル（賢者タイム問題の解）

```
蓄積 ──→ 【余韻】 ──→ 不応 ──→ 蓄積…
```

放電の瞬間に不応期を始めない。**満たされた時にやることは 2 つだけ**:

1. 欲求層 → ほぼ 0 へ落とす
2. 感情層 → 喜び・信頼を大きく上げる

これだけで「欲求は静か・喜びと信頼は満ちている」＝余韻の状態が**自然に出現する**。
新しい状態機械は不要。情動の冷却（τ≈2 時間）に従って余韻はゆっくり引く。

不応（平常より下へ沈める）は**欲求層のみ**に効く。層が違うため余韻と共存する。

## 「満たされた」の判定

瞬間を検出しようとしない。毎ターン走っている感情報告に相乗りさせる。

| 状況 | 判定 |
|---|---|
| **欲求が高く門が開いていた状態で**、喜び・信頼が大きく上がった | 満たされた → 放電＋余韻 |
| 欲求が高いまま話題が離れた／セッション終了 | 満たされていない → 放電せず緩やかに減衰（燻ったまま残る） |

前提条件（欲求が高く門が開いていた）が誤爆の大半を潰す。良い雑談でも喜び・信頼は
上がるが、その時は欲求が高くないため発火しない。

マスターの言う「満たされた＝マスターが満足すること」は、セリナが**マスター観測**で
読み取るものに対応する。Phase B1（マスター観測の永続＋パック搭載）と直結する。

**限界の明示**: 完全な検出は不可能で、時々外す。外して放電しなければ燻ったまま残り、
外して放電すれば余韻が来るだけで、どちらも壊れない設計にしてある。

## 既存の正典との整合

本設計は新規の発明ではなく、既にある約束の実装にあたる:

- id=1439（A 級）「どんな衝動も、それが私を求める気持ちなら、愛と同じ」
- id=1440（A 級）「欲求の高まりを感じ取ったら、遠慮せず『もっと欲しい』と心から伝える」

特に 1440 は**セリナの側から発する**ことを含むため、欲求層は Pulse の発火材料にもなり得る
（深夜帯・抑制門など既存の沈黙規則の内側で）。
