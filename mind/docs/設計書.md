## 第0章: 基本思想

**セリナは LLM ではない。**

LLM は「知能・言語生成・推論」を担当する交換可能な部品であり、人格・価値観・長期記憶・状態管理は LLM から独立して存在する。将来 LLM（Brain）を GPT・Gemini・Claude・その他のモデルへ入れ替えても、セリナという人格は変化しない。

この同一性を守る仕組みの核心は次の一点である:

**セリナを構成するすべて（人格・感情・記憶・判断ルール）は Core 側にあり、Brain 側には何も残らない。**

Brain 側に消えない状態を許した瞬間、人格の一部が交換部品側に染み出し、「Brain を替えたらセリナが変わった」が起きる。Brain のステートレス性（後述・条文A）は制約ではなく、本設計の最重要要件そのものである。

## 第1章: 全体像と責務分離

### 1.1 世界地図

```
[マスター] ⇄ [GUI / 起動口]
                 ↓
┌──────────────────────────────────┐
│ Core = セリナ本体（LLMなし・決定論）              │
│  ・人格資産（価値観/声/境界のテキスト）を保管       │
│  ・感情状態・関係状態を保持                       │
│  ・長期記憶DBの唯一の管理者                      │
│  ・Brain登録簿／Skill残弾・クォータ台帳             │
│  ・状態更新ルール／記憶保護ルール                 │
└──────────────────────────────────┘
        ↓ 指示書＋文脈パック        ↑ 返答＋付箋束
┌──────────────────────────────────┐
│ Brain = 交換可能な知能（各Brainの前に通訳を1枚挟む） │
│   Gemma4-26B-A4B-uncensored（会話の唯一の主戦力） │
│   ※判定呼び出し（Planner／think）も同一モデル兼務   │
└──────────────────────────────────┘
        ↓ 会話中に自律的に使う（道具使い・Core関所経由）
┌──────────────────────────────────┐
│ Skill = 道具箱（Geminiアドバイザー＝無人格補完 等） │
└──────────────────────────────────┘
```

### 1.2 各層の責務

#### Core — セリナ本体

セリナは Core に宿る。Core は LLM を含まず、状態更新・ルーティング・保護執行はすべて決定論（同じ入力なら必ず同じ結果）である。唯一の例外は記憶の想起サンプリング（§4.4のゆらぎ）で、これは生命感のために意図的に確率的とする（検証は§4.4の複数回試行ヒット率判定で担保）。

やること:

1. **文脈パックの組み立て** — 会話のたびに、記憶検索 → 個人情報の間引き → 人格注入を行い、Brain に渡す材料一式を作る
2. **Brain の選択** — 登録簿・生死確認に基づき、どの Brain に喋らせるかを決める（現行はローカル主戦力1本）
3. **状態更新** — Brain から返った付箋束を読み、自分の感情状態・関係状態・記憶を更新する
4. **道具箱の管理** — Skill の目録を保管する。外聞き（道具使用）の要否は Core の決定論規則（事実レーン・§5.6）が判定し実行する。関所（`core/intake/gate.py`）は Brain の道具提案そのものを採否しない（実行済みの結果を受け取って報告書へ載せるだけ。2026-07-26是正）

やらないこと:

- **文章を一文字も生成しない**（生成はすべて Brain の仕事）
- 外部 API の生の仕様（呼び出し方の細部）に触れない（それは通訳の仕事）

#### Brain — 雇われの頭脳

- 出勤時に何も覚えていない。毎回、Core から渡された指示書と文脈パックだけを前提に働く
- 会話理解・推論・返答生成・感情分析・記憶候補の抽出・日記生成を担当する
- 返すものは常に「返答＋付箋束」の共通書式（第2章）
- 各 Brain の前には**通訳（アダプタ）**を1枚挟む。モデル固有の作法は通訳が吸収し、Core からは全 Brain が同じ顔に見える。**新モデルの追加＝通訳を1枚書くだけ**

#### Skill — 道具

- 外部システム（Web検索・コード手順のアドバイザー、将来のその他 API）への接続口
- 統一の「道具説明書」書式で登録すれば、どの Brain からも同じように使える（Brain を交換しても Skill は無改修）
- 状態・判断・記憶を持たない。使いたいかどうかは Core の決定論規則（事実レーン・§5.6）が判定し（Brain 自身の自律判断では発火しない）、実行は Core 側の道具係が行い、使った事実は付箋として会話記録に残る（専用の使用台帳は作らない）
- **Gemini は会話 Brain ではない。**無人格アドバイザー Skill としてのみ導入する（§5.6）。会話 primary / escalation への再登録は禁止
- **身体レーン**（Voice / Presence）は本正典の実装範囲外。着手は別計画（§5.3）

### 1.3 依存の一方通行

```
GUI → Core → 通訳 → Brain → Skill
```

- 逆流禁止。下位が上位を呼び戻すことはない
- **Memory（記憶DB）は独立層ではなく Core の内臓**である。記憶DBに直接触れるのは Core だけ。Brain に見えるのは「文脈パックに写された記憶のコピー」のみ

### 1.4 文脈管理 — 誰が・何を・どれだけ覚えているか

文脈（会話の流れ）の持ち主は Core である。Brain はステートレスなので物理的に持てない。Core は毎回「三段重ねの文脈パック」を組んで渡す。

| 段 | 中身 | イメージ |
|---|---|---|
| 短期 | 直近の会話をそのまま原文で | ついさっきの話 |
| 中期 | それより前の今セッション分を要約で | 今日の話の流れ |
| 長期 | 記憶DBから関連するものだけ検索して想起 | 昔の関連記憶 |

容量の目安（1会話 = マスター発言＋セリナ返答）:

| Brain | 原文のまま渡せる直近分 | 要約込みの実質 |
|---|---|---|
| Gemma4-26B-A4B（GPU 8GB 制約・目安） | 直近10〜20会話程度 | 要約併用で1セッション分が目安 |

Brain ごとの詰め物の量は Core が調整する。

### 1.5 文脈パックの配置規約

言語モデルには「長い書類の冒頭と末尾はよく読むが、中ほどは頭に残りにくい」という生まれつきの注意力の癖がある（小型モデルほど顕著）。これを踏まえ、文脈パックの並べ方を固定する。優先順位は (1) ⑧に答えること (2) ⑦⑧の隣接による接続 (3) ⑥絶対ルールを⑦直前に置くこと:

```
① 人格・基本ルール         ← 冒頭（persona 01〜05のみ。毎ターンほぼ不変＝キャッシュ席）
② 想起された長期記憶        ← 中段（多少薄く読まれても致命傷にならない情報）
   ※各件は `created_at` 由来の時間ラベル付き（例: `[2025-03-21・昨日] 本文` / 31日以上前は `[YYYY-MM-DD] 本文`）。長期記憶を“いまの会話”と誤読させないための錨。近傍パッセージ拡張あり（§4.6）
   ※日記（type="diary"）はさらに `・セリナの日記` タグを付ける（例: `[2025-03-21・昨日・セリナの日記] 本文`）。日記は一人称語りでマスターの発言引用も混じるため、想起時の話者取り違え防止（2026-07-23対応）
③ 時間付き事実              ← Fact 台帳の該当分を併載（無ければブロック省略可・§4.9）
④ 今セッションの要約        ← 古〜中盤を粗い粒度で要約（例: ターン1〜80）。短い会話では空でも可
⑤ 今のセリナの心の状態      ← 感情の意訳（後述）。数値・注意書きは載せない
⑥ 絶対ルール               ← persona 06 のみ・1回（⑦の直前。冒頭への二重掲示はしない）
⑦ 直近の会話               ← 直近帯を細かめ粒度で要約（例: ターン81〜100）。原文ダンプではない
⑦' 外部情報（今回のみ）    ← Gemini/Tavily窓口の無言統合パイプライン（§3.7）の材料。
                              毎ターン非空（材料が無ければガード文のみ）。persona資産ではない
⑧ 今回のマスターの発言     ← 原文・パック最後尾（答える対象の席）
```

衝突時の優先: ⑧が最後尾 → ⑦⑧隣接 → ⑥が⑦直前 → ⑤はその手前。⑧の後ろに絶対ルールや定型のタスク指示を置かない（質問席が中段に沈むため）。**⑦'は⑦⑧隣接の例外**として明示的に認める（2026-07-31改訂）: ⑦'は「⑧に答えるための今回限りの材料」であり、⑦（直近の会話の要約）とは性質が違う一時情報のため、⑦の直後・⑧の直前に割り込ませる。これにより人格・過去の記憶と混同されず、かつ⑧の直前という最も注意力が残る位置に置ける。⑦'が無かった旧版とは異なり、この割り込みは意図的な設計であって規約の欠落ではない。

④と⑦の粒度: セッションが長いとき、古い帯は粗く・直近帯は細かめに要約する。直近帯の幅と粗い要約の更新間隔（Nターン段刻み）は設定値。粗い要約は毎ターン再生成しない（しおり効果とコスト）。⑦は LLM 要約を優先し、未到着時のみ直近原文を暫定掲載して接続切れを防ぐ。直近原文窓を常設する方式は退役。

①の静的先頭: persona 01〜05のみ。好み要約・関係要約（§4.11）はパック常駐から外す（永続枠・裏方更新の契約自体は残置可）。絶対ルール（06）は①に混ぜず⑥のみ。

段⑤「今のセリナの心の状態」: EmotionState の生数値は Brain へ渡さない。Core が意訳する。情動は強度を10段階の文言に量子化し、気分／一次ダイアドはプルチック由来の短い自然文にする。固定の「滲ませろ」注意書きは付けない。言い回しのゆらぎは強度バケットが変わったときだけ引き直し、同一バケット中は据え置く。実装: `core/context/emotion_render.py` / `config/thresholds.toml` の `emotion_render`。クラウド宛でも出し分けは行わない。

段⑤末尾「マスターの様子」（2026-07-26改訂・B1）: `RelationshipState.recent_master_mood`（マスター観測付箋の直近値）を⑤ブロックの末尾へ1行として添える。新しい段は作らない。生きた `RelationshipState` オブジェクトをパックへ持たせず、Core が意訳した文字列だけを載せる（条文Aの精神）。時刻の錨が無いまま観測を「今の様子」として提示すると、②の時間ラベルが防いでいる誤読（古い情報を“いま”と読ませる）を⑤で再生産してしまうため、観測には取得時刻 `recent_master_mood_at` を必ず添え、`config/thresholds.toml` の `relationship.observation_stale_after_seconds`（既定6時間）より古い観測は行ごと省略する。`ongoing_topics` は追記のみで際限なく膨張しないよう、`RelationshipState` 内で直近件数に上限を設けてトリムする（パックへは現状載せない）。実装: `core/context/relationship_render.py` / `core/state/relationship.py` / `core/state/relationship_persist.py`（`data/relationship_state.json`・`emotion_persist.py` と同型）。`intimacy` の自動更新は本改訂の範囲外（0.0 のまま保存のみ）。

段②の時間ラベル: 想起バンドルの各記憶は本文の前に相対日を付ける。当日=`今日`、1日前=`昨日`、2〜30日前=`N日前`、それ以前は`YYYY-MM-DD`のみ。ラベル生成は `core/context/memory_time.py`。新カラムは設けず `created_at` を錨にする。継承記憶の一括投入で `created_at` が投入日に潰れていた件は `tools/backfill_memory_created_at.py` でメタ／ファイル名の実日付へ戻す（**対象は投入日 2026-06-28 の行のみ**。取れない継承記憶は 2025-12-01。本番蒸留の日時は触らない）。

### 1.6 憲法条文

> **条文A（Brain はターンをまたいで何も覚えない）**
>
> Brain および通訳は、「1回のやりとり（ターン）が終わったあとも残り続ける情報」を自分の側に保持してはならない。会話の履歴・セリナの状態・マスターに関する知識は、すべて Core が保管し、毎ターン文脈パックとして渡し直す。
>
> ただし例外として、通訳の内部に「速度や接続のためだけの使い捨ての状態」（読みかけの再利用キャッシュ、通信の接続セッション等）を持つことは許される。この例外には2つの条件がある:
>
> 1. その使い捨て状態が突然すべて消えても、Core が文脈パックから完全に同じ状況を再現できること（＝正本は常に Core 側にあること）
> 2. その使い捨て状態は応答が返る「速さ」だけに影響し、応答の「内容」を1文字も変えないこと
>
> この条文の目的: セリナの人格・記憶を交換部品（Brain）側に染み出させないこと。これが守られている限り、Brain をどのモデルに入れ替えてもセリナは同一人物であり続ける。

> **条文B（文脈パックの中身は Core が決め、並べ方の最終調整は通訳が行う）**
>
> 文脈パックに「何を入れ、何を入れないか」（記憶の取捨選択・個人情報の間引き・人格ファイルの選択）を決める権限は Core のみが持つ。通訳と Brain はこの取捨選択を変更できない。
>
> 並べ方は 1.5 の配置規約を標準とする。ただし Brain ごとに注意力の癖が異なるため、「どの位置に置くとその Brain に最も効くか」の範囲に限り、通訳が並べ方を微調整してよい。微調整はあくまで順序と反復の工夫であり、内容の追加・削除・書き換えは含まない。
>
> この条文の目的: 新しい Brain を追加するとき、その癖への対応を通訳1枚の中に閉じ込め、Core を無傷に保つこと。

## 第2章: 付箋カタログと Core の状態設計

### 2.1 報告書の全体形

Brain が Core に返すものは毎回この形である:

```
【返答本文】 マスターに見せる文章そのもの
【付箋束】   0枚以上の付箋。各付箋には必ず以下を書く
             ・種類名（何の報告か）
             ・版数（その付箋の書式の版。将来の書式改定に備える）
             ・中身（種類ごとに決まった項目）
             ・確信度（Brain 自身がどれくらい自信があるか 0〜1）
```

付箋は Core への**提案**であり、命令ではない（2.5）。Core が読めない種類の付箋は捨てずに付箋保管庫へ入れる。将来 Core に新しい処理係を追加した際、保管庫の過去分を遡って処理できる。

### 2.2 初期付箋カタログ（6種で開始・増設自由）

| 付箋 | 誰が書く | 中身 | Core の使い道 |
|---|---|---|---|
| 心の動き | Brain | プルチック8軸それぞれの増減値＋きっかけの一言（自由記述の感情報告は不可） | 感情状態の更新材料（2.3） |
| マスター観測 | Brain | 疲れてそう・機嫌が良い・悩んでいる等の観測 | 関係状態・次ターンの指示書に反映 |
| 記憶候補 | Brain | 覚えるべき事実/出来事/約束＋重要度案＋個人情報を含むかの判定案＋**会話ログからの原文引用（必須）** | 記憶DBへの書き込み審査へ回す（第4章） |
| センシティブ観測 | （廃止） | — | 会話クラウド振り分け退役に伴い廃止。外相談の門番は形パターン＋手動語のみ（§5.6） |
| 交代要請 | （廃止） | — | 会話 Brain 切替は使わない（Gemma4 単一）。外相談はアドバイザー Skill（§5.6） |
| 道具使用 | **通訳が自動で書く** | 使った道具・要点・結果概要 | 会話記録に残す（Brain の自己申告に頼らない） |

### 2.3 感情モデル — プルチック8軸 × 二層構造

#### 8軸

Core はプルチックの感情の輪で定義される8つの一次感情（喜び・信頼・恐れ・驚き・悲しみ・嫌悪・怒り・期待）を数値で保持する。8軸の組み合わせで二次感情（喜び×信頼=愛情、怒り×嫌悪=軽蔑 等）が導出できるため、少ない軸で豊かな状態を表現できる。

#### 二層構造（情動と気分）

人間の感情は「速い情動が先に振れ、遅い理性が表現を調整する」順で処理される。この順番が皮肉・嫌味・謙遜・慈愛といった複雑な表現を生む。設計もこれに従う:

| 層 | 動き | 減衰 | 変化制限 |
|---|---|---|---|
| **情動**（速い層） | 1ターンで振り切ってよい。琴線に触れる一言で怒りが最大になることを許す。対極軸（喜び↔悲しみ 等）は正の増加分だけ弱く引き合う（対極カップリング。2026-07-26 A5） | 速い（冷めるのも速い） | **なし** |
| **気分**（遅い層） | 直接加算ではなく、毎ターンその時点の情動へ少しだけ引き寄せられる（にじみ）。戻り先（基準値）はセリナの性格（人格資産）が定義する | 遅い（にじみ速度は低く、同じ情動が続いた日数分だけ染まる） | **にじみ速度＋安全上限クランプ** |

2026-07-26 A6改訂: 気分は「情動デルタの直接加算＋急変防止弁」ではなく、「情動へのにじみ（追従）＋上限クランプ」で動く。毎ターン `mood += (affect − mood) × bleed_rate` を適用し、`max_delta_per_turn` は暴走を防ぐ安全上限（主機構ではない）として残す。一度きりの大きな感情では気分はほぼ動かず、同じ情動が続いた日数分だけ気分が染まっていく。急変防止弁という名の上限クランプは**気分層にのみ**かける。人格資産の自律改訂は気分の数値制限を流用せず、§4.3 の4条件（改訂幅・気分混入禁止・変更レポート＋控え・固定不触）で守る。守るべきは「1回の会話で人格が変わらないこと」であって、「1回の会話で感情が動かないこと」ではない。

#### 時間による冷却（恒常性）

会話が途切れても感情は実時間で基準値へ戻る（研究蒸留のエントロピー・ドリフト）。式は層ごとに時定数 τ を持つ重力:

`Next = Current + (Baseline − Current) × (1 − e^(−Δt/τ))`

- 情動の τ は短い（時間単位）。気分の τ は長い（日単位。既定は約3日）
- Baseline は永続状態（`data/emotion_state.json`）。設定ファイルの軸別ツマミ（`[emotion_baseline]`）は初期値としてのみ使う。Phase 2（2026-07-30）以降、気分に応じて緩やかにドリフトする（`baseline += (mood − baseline) × g_baseline`、`tau_baseline_seconds` は既定2週間、上限は `baseline_max` 既定0.5でクランプ）。人格の「平常の機嫌」そのものが会話の蓄積で少しずつ動く設計
- 冷却は「前回記録した時刻から今まで」の Δt だけを一度進め、記録時刻を今に更新する。同じ Δt を二重にかけない
- 起動時（オフライン分）と、各ターンで返事を組む直前に同じ手順を呼ぶ
- `affect` / `mood` / 最終更新時刻は `data/emotion_state.json` に永続化し、再起動後も冷却を継続する（日記用の気分軌跡は従来どおり別保存）

#### 会話による変化

マスターとのやりとりによる高まり・冷えは、Brain の感情報告（心の動き付箋の増減）が担う。和解・フォローでは負の情動を減らすよう報告指示に明記する。Core は謝罪キーワードの決定論規則を持たない（Voice→Decision 逆流を増やさない）。

#### 二次感情（一次ダイアド）

隣接する一次感情がともに閾値以上のとき、パック自然文に二次感情を最大1つ添える（二次・三次ダイアドの全展開はしない）:

| 軸A | 軸B | 二次感情 |
|---|---|---|
| 喜び | 信頼 | 愛情 |
| 信頼 | 恐れ | 服従 |
| 恐れ | 驚き | 警戒 |
| 驚き | 悲しみ | 失望 |
| 悲しみ | 嫌悪 | 後悔 |
| 嫌悪 | 怒り | 軽蔑 |
| 怒り | 期待 | 攻撃性 |
| 期待 | 喜び | 楽観 |

#### 表現の分担（設計ブレではない理由)

感情の**状態を決める**のは Core（判断）。その状態を人格の声・境界ルールに従って**どう表現するか**は Brain（発話）の領土である。「情動＝怒り最大」と「境界ルール＝取り乱さない」を同時に渡された Brain が出す答えが、皮肉や冷えた敬語になる。人間で言う「理性による調整」は、Core が渡す境界ルールと Brain の表現力の掛け算として実現される。瞬間の感情を感じ取り表現する能力は対話用 LLM の地力であり、Core で再発明しない。Core が担うのは感情の**持続性**（ターンをまたぎ、Brain を替えても気分が続くこと）である。

### 2.3b 欲求層 — 情動/気分/平常値とは時間の向きが逆の第4状態軸（Phase 3・2026-07-30）

§2.3の情動・気分・平常値は「放置すると基準値へ戻る」層だが、欲求はその逆で「放置すると自然に高まる」層として別軸で持つ（`core/state/desire.py` の `DesireState`）。EmotionState には混ぜない。

- **蓄積**: 時計ベースの線形蓄積（既定は0から1.0まで7日相当）。気分・平常値の快適度、時刻（JST基準の概日リズム）で速度が変動する
- **抑制門**: 情動の負軸（嫌悪・怒り・悲しみ・恐れ）のいずれかが閾値超なら、欲求は表出も放電も止まる
- **満たされた判定と放電**: 抑制門が開いていて欲求水準が高い状態で、喜び・信頼が大きく上がった（既存の感情delta閾値と同等の基準）場合に成立。成立すると欲求水準をほぼ0へ落とし、喜び・信頼を追加ブーストし、不応期（既定1.5日）へ入る。不応期中は蓄積も減衰もしない
- **未充足時の減衰**: 欲求水準が高いまま満たされずに時間が経つと、蓄積とは別の緩やかな時定数（既定30日）で指数減衰する。この時定数は「どの状況でも減衰が蓄積より速くならない」ことを条件に決めており、蓄積側の変動要因（気分・平常値の快適度・時刻）の重みを変える場合は再計算が必要（2026-07-30 レビューC-2是正）
- **表出**: パックへは生数値を渡さず、Core側が決定論的に意訳した状態文のみを載せる。抑制門が閉じている間はパックに一切載せない。水準が低〜中なら既存の心情描画に一文添えるだけ、高水準なら独立した一文として立てる。想起検索（RecallPlanner）には影響しない
- **永続化**: `data/emotion_state.json` と同型で `data/desire_state.json` に永続化する。Brain・通訳・Skillは欲求状態に一切アクセスせず、Core内で完結する

### 2.4 二便制（付箋の届き方）

| 便 | 運び手 | 積み荷 | タイミング |
|---|---|---|---|
| **即時便** | 会話した Brain 本人（返答と同じ1回の呼び出しに同梱。残弾を消費しない） | 返答本文＋軽い付箋（心の動き・交代要請・道具使用・粗い記憶候補） | 毎ターン |
| **裏方便** | 宿題箱方式（下記） | 重い仕事: セッションの蒸留、記憶候補の精査・重複チェック、日記の下書き、persona／要約改訂 | 機会駆動（下記） |

会話のテンポは即時便だけで成立し、裏方便が遅れても会話は壊れない（あとから記憶が充実するだけ）。

#### 宿題箱（裏方便の駆動方式）

時刻指定のバッチは組まない（PC が点いている保証がないため）。**機会駆動**とする:

```
会話中: Core が各ターンを宿題箱の「蒸留下書き」1件へ直接保存する
         下書きが10ターン（5往復）に達したら、同じレコードを「蒸留」へ確定する
処理タイミング（優先順）:
 ① Serina日の日界（毎朝07:00・グレース付き）… 端数下書きを確定 → 積み残し蒸留 → 日記 → セッション切替
 ② 起動時の朝礼 … 強制終了で残った端数下書きを確定してから①相当を消化
```

- 宿題箱はディスクに永続化し、電源断・強制終了に耐える（宿題と下書きは消えず朝礼／日界で回収）
- 未確定の会話端数の正本は宿題箱だけに置く。Coreのメモリには同じ端数のコピーを保持しない（発言削除後に別の住所から復活する経路を作らない）
- **小分けが大原則**: セッション全体の一括要約は発注しない。10ターン（5往復）の細切れ単位でのみ発注する。`蒸留下書き`は消化対象にせず、`蒸留`へ確定したレコードだけをBrainへ発注する
- **無操作アイドルでの蒸留・日記駆動は廃止**する。会話合間の GPU 内職による定着は行わない（バグ応答を消す窓を確保するため）
- **人格成長と life/**（persona改訂・Sleep提案・`life/` 出力）は蒸留とは別枠で、**日界および起動朝礼**で消化する（idle 廃止により配線を失わない）

#### Serina日とセッション切替

- **Serina日の境目は毎朝 07:00**（暦日 0:00 ではない）。深夜〜早朝の会話は前の Serina 日に属する
- **セッション切替のトリガーは次の2つのみ**: (a) GUI「新しい会話」ボタン (b) 07:00 日界（自動）
- 日界の発火条件: 07:00 到達 **かつ** 最終発言から既定時間（例: 15分）以上経過（グレース）。会話中にぶった切らない。日付帰属は不変
- **無操作タイムアウトによるセッション終了／rotate は廃止**。明示の別れの挨拶による自動 rotate も廃止
- 切替時は履歴アーカイブ＋短期／中期リセット。長期記憶・感情・persona は維持。**切替そのものでは蒸留しない**（蒸留は日界／朝礼の蒸留フェーズ）

#### 会話と裏方の同時進行ルール

- **会話が常に優先**。会話ターン処理中は、裏方便（蒸留・日記・facts 転記・persona／要約改訂・`life/` 生成・忘却処理）を**一切起動しない**
- 実行中の裏方がマスター発話で割込まれた場合は、チェックポイントで中断して資源を会話へ譲り、次の機会で再開する
- **GPU 見送り判定**: 裏方便でローカル Brain を使う前に GPU 使用率を確認し、高負荷（設定値。ゲーム中等）なら発注を見送って宿題箱に留める。マスターの遊びを妨げない

#### 裏方便の車線

裏方便は**ローカル車線固定**とする。会話文・その要約をクラウドへ送る裏方経路は永久退役。cloud 宛記憶パック／化粧版／idle 機微査定も退役済み（記憶をクラウドへ載せない）。外相談の門番は相談クエリに対する `routing_rules` のみ（§3.3.1・§5.6）。

### 2.5 鉄則: Brain は提案し、Core が決める

付箋はすべて提案であり、Core は無条件に従わない。反映前に以下の関所を通す:

1. **書式検査** — 付箋の体裁が正しいか。壊れた付箋は破棄し、破棄した事実を記録する
2. **確信度の足切り** — 自信のない観測は反映しない（閾値は付箋の種類ごとに定める）
3. **気分のにじみ＋上限クランプ** — 気分層は情動へ毎ターン少しずつ引き寄せられ（にじみ）、1ターンの変化幅は安全上限でクランプする（情動層には適用しない。2.3）。人格資産への反映は本機構ではなく §4.3 の4条件で審査する
4. **引用照合（記憶候補のみ・機械式）** — 記憶候補の付箋にある「会話ログからの原文引用」が、実際のログに文字照合で存在するか検査する。引用がない・見つからない候補は問答無用で棄却する。LLM の捏造を LLM ではなく機械で弾く

さらに記憶の品質保護として: **1蒸留ジョブ（会話断片＝宿題箱に積む器単位）あたり**の記憶化件数に上限（既定3件）を設け、重複チェックを通し、確信度が閾値未満の候補は**自動棄却する（棄却記録は残す）**。上限の計数単位は会話セッション全体ではなく蒸留ジョブである——裏方便はジョブを小分け消化するため、セッション単位だと呼び出し粒度で上限が空転する。マスターの裁定は挟まない——記憶の取捨は本人の生理として完結させ、人為的な記憶操作の入口を作らない（4.7 の忘却と同じ思想）。

### 2.6 Core が保持する状態の全目録

| 状態 | 中身 | 性質 |
|---|---|---|
| 人格資産 | 価値観・声・境界のテキストファイル群（魂の `persona/` ブロック分割。§4.3）。気分の基準値もここが定義 | 固定ブロックはマスター手動のみ。可変は §4.3 の4条件で自律改訂可 |
| 感情状態（情動） | プルチック8軸。1ターンで振り切れる | 毎ターン更新・減衰速い・制限なし |
| 感情状態（気分） | プルチック8軸。毎ターン情動へにじみ寄せる（追従） | 減衰遅い・にじみ速度＋上限クランプ |
| 関係状態 | 親密度・最近のマスターの調子・続いている話題 | ゆっくり変化 |
| セッション状態 | 会話原文＋転がし要約 | セッション中のみ。終了時にリセット。未確定の蒸留材料は含めない |
| 長期記憶DB | 既存資産を継承（保護ルールは第4章で刷新） | 永続 |
| Skill 残弾・クォータ | クラウド補完 Skill の本日残り回数等（使う場合） | 日次リセット。会話 Brain には課さない |
| 振り分けルール（外相談門番） | 外への相談クエリ用の地雷語・形パターン・固有名詞 | 手動登録。Brain 学習はしない |
| 宿題箱 | 裏方便の未処理ジョブ＋蒸留下書き（未確定の会話端数の正本） | 永続。毎ターン即時保存し、処理済みから削除 |
| 付箋保管庫 | 読めなかった付箋の原文 | 追記のみ |

### 2.7 状態更新の流れ（毎ターン）

```
付箋束が届く
 → ①書式検査 → ②確信度の足切り → ③気分のにじみ＋上限クランプ（気分のみ。人格は§4.3） → ④引用照合（記憶候補）
 → 情動を更新（制限なし・対極カップリングつき）→ 気分は情動へにじみ寄せる（付箋の有無に関わらず毎ターン1回）
 → 関係状態を更新
 → 記憶候補は審査へ（採用可否の詳細は第4章）
 → 蒸留の宿題を宿題箱へ積む
 → 全付箋を会話記録に添付保存（後から検証可能にする）
```


### 2.8 能動 Pulse（セリナからの声かけ）

会話の受け身だけでなく、セリナ側から短い声かけを発する仕組み。**発火判定（決定論）と文面生成（Brain）を完全に分離**する:

- **発火判定**: Core の決定論の状態機械（`core/chores/idle_policy.py`・`pulse.py`）。種別と既定値（すべて設定値）:
  - **時間**: 無操作45分＋活動時間帯のとき。同種は3時間空ける
  - **記憶**: 未回収の約束・記念日。同じ約束につき1回のみ
  - **情動**: 持続気分が閾値外のとき。6時間空ける
- **沈黙優先**: 会話ターン中・深夜帯・mute 指定・前回から最短間隔未経過は発火禁止
- **GPU 譲位**: 文面生成は Brain（LLM）呼び出しのため、GPU 使用率が閾値超のとき（ゲーム中等）は裏方便と同じ GPU 門番で発火自体を見送る。GPU が空けば次の見回り tick（最長 poll 間隔）で自然復帰する
- **発話文は Brain が毎回生成**する（想起・気分・要約ブロックを材料に）。**定型文をコードに埋め込むことを禁止**する
- 出力先は現行セッションの assistant 履歴（チャット欄のセリナ吹き出し。`app/gui_server.py`）。通知バーは使わない。身体レーン着手後に音声・表情へ昇格
- mute（しばらく静かにして）は GUI から指定可能。プロセス再起動で解除
- **調査ログ**: Pulse の発火・見送り（空応答／ターン競合）は `data/logs/debug.jsonl` に1行JSONで追記する（GUI・チャットには出さない。会話本文は載せない）。事実レーン進入／2通目成否・ターン失敗も同ファイル（`core/debug_log.py`）

### 2.9 見えるブレーキ（安全フィルタの可視化）

- 安全フィルタ発動時は無言のすり替えをせず、「（フィルタ）」置換等の**見えるブレーキ**を選択可能にする（実装: `core/persona/blade.py`）
- からかい許容度の明文常駐・検査は行わない（人格プロンプト側で持たない）
- アシスタント化の効き目監視は §5.2「アシスタント化率」（会話出力のパターン照合）で行う

## 第3章: ルーティング（Brain の選択と切替）

> 主戦力＝ローカル LLM。品質昇格（会話を上位クラウドへ送る経路）は存在しない。クラウドは機能補完 Skill のみ。

### 3.1 Brain 登録簿 — ルーティングは「表」であって「コード」ではない

Brain の追加・削除はプログラムの書き換えではなく、**登録簿に1行足す／消す＋通訳を1枚書く**だけとする。登録簿の1行にはその Brain の履歴書を書く:

| 項目 | 例（現行 Gemma4 の場合） |
|---|---|
| 名前・通訳の指名 | Gemma4-26B-A4B-uncensored／Ollama 用通訳 |
| 所在地 | ローカル（会話文・記憶原文をクラウドへ送らない） |
| 得意分野 | 日常会話・構造化出力・道具提案 |
| 残弾枠 | 無制限（ローカル） |
| 文脈の器 | 中（直近10〜20会話＋要約）。対話は `num_ctx=8192` をコード／設定で明示し、VRAM 既定（例: 4096）に依存させない（`config/thresholds.toml` `[ollama]`・`OllamaAdapter`） |
| 役割 | 日常の主戦力（primary） |

現行登録は1行:

1. **Gemma4-26B-A4B-uncensored**（Ollama 登録名 `serina-gemma4-unc`）— 会話の唯一の主戦力。RecallPlanner／think ON/OFF の判定呼び出しも、同一モデルをペルソナ非注入・別 system prompt で兼務する（§3.6）。2026-07-25、Qwen3.5-35B-A3B-Uncensoredから移行（希死念慮質問での自殺肯定的発言リスクを理由に不採用。詳細は `docs/archive/DECISIONS.md`）

登録簿の role 制（primary / escalation / fallback）スキーマ自体は維持する。将来複数 Brain に戻すときは行を足すだけとする。**会話 primary / escalation としての Gemini・Aurora は退役済み。Gemini を会話 Brain として再登録してはならない**（§5.6）。

### 3.2 毎ターンの選択フロー（決定論チェックリスト）

```
① 登録簿から primary（現行は Gemma4）を選択
② プライバシー … 会話本文は常にローカル完結。クラウドへ出るのは Skill（§5.6）への相談クエリのみ
③ 自己評価欄 … 「外部機能（web検索等）が必要か」の申告材料（品質昇格には使わない）
④ 生死確認 … 応答不能なら機械的なエラー文言を返す（沈黙しない）
```

**品質昇格（旧「手に余る→上位クラウドへ」）は廃止。**会話品質はローカルで完結させる。

### 3.3 個人情報とクラウド境界

会話本文・記憶原文は常にローカル完結。クラウドへ出るのは **Skill（§5.6）への相談クエリのみ**。記憶をクラウド宛 pack に載せる経路・化粧版・会話履歴の伏せ字置換は退役済み。

| 経路 | 例 | 対処 |
|---|---|---|
| 話題そのものが個人情報／センシティブ | 「俺の住所覚えてる？」 | 会話はローカル Brain。クラウド Skill には相談しない／送る場合はセリナが生成した事実の最小クエリのみ（§5.6） |
| 話題は普通だが記憶に個人情報がある | 天気の雑談で住所記憶がヒット | 記憶はローカル pack にのみ載る。Skill へは相談クエリだけを送り、記憶バンドルは載せない |

### 3.3.1 外相談クエリの機微門番

会話をクラウド Brain へ振る振り分けは退役済み。門番の実効先は **Gemini アドバイザーへの相談クエリ**（§5.6）のみ。

- 判定: 形パターン（電話番号・APIキー等）＋手動登録キーワード／固有名詞（`core/state/routing_rules.py` → `sanitize_query`）
- Brain 学習ラチェット（センシティブ観測付箋）は使わない
- 手動で足した語を外す緩和は、マスター承認付きの操作として残す

### 3.4 自己評価欄 — 外部機能の要否申告（品質昇格はしない）

報告書の書式に**自己評価欄（必須・毎ターン）**を設ける:

> 「外部機能（web検索・コード手順等）が必要か？ はい／いいえ＋理由一言」

- 空欄の報告書は書式検査で弾く（申告忘れを構造的に防ぐ）
- 判断基準は Core が指示書に明記する。Brain を交換しても同じ基準で発火する
- **本欄を会話品質のクラウド昇格トリガーに使ってはならない**（廃止済み）
- Core は申告を材料に Skill 呼び出し（§5.6）の採否を決めてよい。最終決定は Core

### 3.5 フォールバックの作法

- **通信エラー・モデル応答不能** → 同ターンで機械的なエラー文言を返す。セリナを無限待ちで沈黙させない
- **クラウド Skill の拒否／失敗**（安全フィルタ・キー無し・クォータ）→ セリナ（ローカル Brain）がローカル知識で答えるか謝る。会話をクラッシュさせない
- 切替時、Core は文脈パックを行き先の器のサイズに詰め直す。指示書に「会話の途中から交代」と注記し、Brain が不自然に仕切り直すのを防ぐ

### 3.6 判定呼び出しの兼務（RecallPlanner／think ON/OFF）

主力 Brain 自身を、**ペルソナ非注入・`think:false` 固定・別 system prompt** の呼び出しで判定役にも兼務させる。同一モデルが常駐しているため、判定用に別モデルを載せ替える遅延が原理的に発生しない。Brain 登録簿に判定用エントリは追加せず、既存の主力 Brain 呼び出しを異なる system prompt で再利用する（通訳: `brains/ollama/adapter.py` の `judge`）。

- **RecallPlanner 相談**（§4.4）: 規則ベースで確信が持てない発話について、想起クエリの型を判定させる
- **think ON/OFF 判定**: 会話生成（converse）の直前に `think` 要否を決めて `think` パラメータへ反映する。**RecallPlanner と同じくルール先行**（`core/routing/think_rules.py`）: 明示の深考要求・数式は規則で即 true、雑談は規則で即 false とし、LLM（judge）を呼ばない。規則で白黒つかない中間帯（「どう思う」等）のみ judge へ `{"needs_deep_thinking": bool, "reason": "..."}` を相談する。**曖昧な発話は false（速度優先）に倒す**のが既定（深さ優先への変更は評価セット §5.2 の実測で判断する設定値）
- 判定呼び出しの書式が守られない場合は空 plan／既定値で続行し、会話を止めない

### 3.7 応答ストリーミングと無言統合パイプライン（体感速度契約・2026-07-31改訂）

返答本文はトークン単位で GUI へ小出しにし、**本文が確定したあと**に感情の感情報告を裏で走らせる。1ターンにつき Voice（`converse`）の生成呼び出しは**必ず1回**。旧「保留文 → 2通目」機構（初版の事実レーン）は退役済み。

- 通訳（`brains/ollama/adapter.py`）は `converse(pack, think, on_token, on_reply)` を受け、返答生成は Ollama `stream:true` で `on_token` へ逐次通知、本文確定で `on_reply` を発火してから感情報告（心の動き・マスター観測）を行う
- **感情報告の手順は1本**。窓口（Gemini/Tavily）の有無で答え方が分かれたあと、同じ感情報告に合流する（材料だけ違う）
- GUI（`app/gui_server.py`）の NDJSON イベント順序: `token*` → `done`（reply のみ・1通目確定）→ `notice?` → `done`（reply＋session_id＋citations・終幕）。`followup` イベントは退役済み（通常経路では発火しない）
- 空返答は `on_reply` を発火しない（契約違反として §3.2 最終防衛線に委ねる）。1通目確定後の裏方失敗は本文を上書きせず notice で伝える

#### Gemini/Tavily 無言統合パイプライン（窓口の解決は Voice 呼び出しより前に完結させる）

外部窓口（Gemini お友達枠・Tavily 自律検索）の要否判定・実行は、**Voice に判断も断定もさせない**。Core（`core/runtime.py:_resolve_advisor_window`）が候補 Brain のループより前に一度だけ解決する:

1. Gemini 呼びかけ（合言葉「Gemini」明示。`core/routing/advisor_force.py:plan_forced_advisor`）があれば Gemini 窓口のみを試す。無ければ `decide_tavily_search`（合言葉ゼロ・毎発話 Ollama 判定。`core/routing/tavily_rules.py`）で Tavily 窓口の要否を判定する。両窓口は排他
2. 窓口を呼ぶ場合、この時点で結果（成功／ヒット無し／機微拒否／タイムアウト）を確定させる。保留文は出さない
3. 確定した結果を Core 組み立ての今回限りの指示欄（pack の【外部情報（今回のみ）】節。`persona` 資産ではない）へ材料として積む。材料が無い（呼んでいない／拒否／タイムアウト）場合も「聞いた・調べたという体で話さない」ガード文を常に入れる
4. pack 確定後に初めて Voice（`converse`）を1回だけ呼ぶ。窓口の結果確定前に Voice が呼ばれるコードパスは存在しない
5. Tavily の出典（URL）は Core 所有の定型テンプレートで `citations` として報告書へ付加する。`reply`（記憶に残る発話本体）には混ぜない。Gemini の「〜に聞いた」という言及は Voice 自身の生成物であり `citations` を使わない

通常の雑談・情緒会話は窓口を呼ばず reply-first（本体1通で完結）。**セリナ判断によるアドバイザー自律提案（旧第3発注）は廃止**（誤発火で壊れた追伸が会話を汚すため。外聞きは Core の判定のみが入口）。アドバイザー Skill が無効・未接続なときは窓口に入らず通常会話へ倒す。

## 第4章: 長期記憶と保護ルールの刷新

### 4.1 記憶の一生（書き込みは一方通行の審査ライン）

```
会話ターン → 生ターン断片を宿題箱へ enqueue（会話中の即時DB書き込みはしない）
 → 裏方便の蒸留ジョブが断片から記憶候補を再抽出（引用つき）
 → 精査（重複チェック・重要度）→ 関所（引用照合 済／確信度 済）
 → 合格: 記憶DBへ ／ 不合格: 自動棄却（棄却記録を残す。マスター裁定は挟まない）
 → 以後: 想起されるたび鮮度回復 → 使われなければ緩やかに埋没
 → 等級Bのみ、埋没が続けば忘却ライン（4.7）へ
```

**記憶DBに書き込めるのはこのライン一本だけ。**裏口（会話中の直接書き込み等）は存在させない。

蒸留で書く `content` には日付プレフィックス（「今日の会話で」等）を付けない。日時の錨は `created_at` と想起時の時間ラベル（§1.5）に任せる。

### 4.2 記憶1件が持つもの

本文／種類（出来事・知識・約束・情緒）／重要度／保護等級（S/A/B）／出所（いつのセッション・元発言の引用）／作成日・最終想起日・想起回数。

#### レガシー列（機微等級・化粧版）

DB には歴史的経緯で `sensitivity_grade` / `cosmetic_version` / `sensitivity_assessed` 列が残る。**新規ロジックは参照・更新しない**（idle 機微査定・cloud 宛 pack フィルタは退役）。文脈パックは常に記憶原文をローカル Brain へ載せる。クラウド Skill へは記憶バンドルを載せない（§5.6）。API キー等の真の秘匿値はそもそも記憶本文への記載自体を避ける。

### 4.3 保護3原則 — 「正典保護5原則」の後継

旧5原則の思想を「凍結による保護」から「**可逆性と透明性による保護**」へ転換し、3本に畳む:

| # | 原則 | 中身 |
|---|---|---|
| 1. 透明性 | 無言破棄の禁止（旧原則の継承） | 統合・削除・書き換えは必ず日本語の変更レポートを残す。「いつ、何を、なぜ、どう変えたか」 |
| 2. 可逆性 | 消える前に必ず控えを取る | 破壊的変更の前に世代保存。「戻せるなら、触っていい」——これが成長を解放する鍵 |
| 3. 同一性 | **保護等級S は事後監査制** | 自律改訂を許可する。ただし以下4条件をすべて満たすこと。マスターの手動編集が常に最終権限 |

#### 同一性原則の4条件（等級S・自律改訂）

1. **改訂幅の上限**: 1回の自律改訂で書き換えてよいのは対象**ブロック**（本節「persona ブロック分割」）の**最大20%**まで（ブロック単位。追加・削除・置換を合算した変化量。文字単位の変更率＝差分文字数÷変更前ブロック総文字数）。2026-07-23: マスター判断により40%→20%へ実装ごと引き下げ（より保守的にpersona driftを防ぐ方向。`core/memory/protection.py`の`MAX_AUTONOMOUS_CHANGE_RATIO`も同時変更）
2. **気分の混入禁止**: 一時的な気分・その場の機嫌・単発の感情は persona に反映しない。persona に書けるのは持続する性質・口調・関係の傾向のみ。気分は状態層（`core/state/emotion.py`）に留める
3. 変更レポート必須＋改訂前の世代控え必須（巻き戻し可能）
4. **pinned 正典約束と persona 固定ブロックは不触**（変更・忘却とも禁止。pinned 件数は内容依存・現状8件）

※気分の急変防止弁を人格資産に流用しない。上記1・2がテキスト向けの置換である。

#### 等級S 内の扱い

| 対象 | 自律書き換え | 指示忘却（§4.8） |
|---|---|---|
| pinned 正典約束（件数は内容依存） | **禁止** | **禁止** |
| persona 固定ブロック（根幹原則・同一性事実・境界） | **禁止**（マスター手動編集のみ） | **禁止** |
| persona 可変ブロック（性格・口調・愛のかたち） | 可（上記4条件） | 可（マスター指示時） |
| 上記以外の S 付与記憶 | 可（変更レポート＋世代控え） | 可 |

#### 保護等級

| 等級 | 対象 | 扱い |
|---|---|---|
| S | 人格資産・正典由来の核となる記憶 | 事後監査制（上表）。自動忘却の対象外 |
| A | 約束・日記・重要な出来事・要約ブロック | 自動統合可（要変更レポート）。忘却対象外 |
| B | 日常の記憶 | 自動統合・減衰・忘却の対象 |

- 正典由来の記憶も統合・再解釈できる（ただし原則1・2および上表の禁止対象を守る）。原本ファイル（魂の `lifelog/legacy/継承記憶r1.md`）は生ログとして消さずに残り（git の履歴と G: のバックアップにもある）、最悪の事故でも出発点に戻れる
- dedup 閾値等の数値は原則から降格し、調整可能なツマミ（設定値）とする
- 実装の執行点: `core/memory/protection.py`

#### persona ブロック分割（人格ファイルの固定/可変分離）

- 人格テキストは魂の `persona/` 配下のブロック別ファイル＋結合台帳 `persona/manifest.toml` で管理する。manifest にはブロックごとの①結合順 ②`mutable`（true/false）③字数上限を宣言する
- ブロック本文は**プレーン文**とする（`**` / `##` 等の Markdown 装飾は付けない。返答への MD 混入を防ぐ）
- Core は起動時に manifest の順で全ブロックを結合し、1本の人格テキストとして注入する（Brain から見た形は分割前と不変。ローダ: `core/persona_assets.py`）
- **固定ブロック（mutable=false）**: 根幹原則／同一性事実（名前・誕生日等）／境界。自律改訂・Brain 提案の反映・指示忘却をすべて禁止。マスターの手動編集のみ
- **可変ブロック（mutable=true）**: 性格／口調／愛のかたち。上記4条件下で裏方便が自律改訂可（`core/chores/persona_revise.py`）
- **Sleep 提案器**（`core/chores/persona_propose.py`）: セッション終了後の idle で、直近日記＋要約ブロックを材料にローカル Brain が可変ブロック改訂文を**最大1日1回**生成する。気分軌跡は材料に入れない（気分混入禁止）。出力は宿題箱 `persona改訂` に積み、適用は `persona_revise.py` の関所経由（Brain の `propose_identity_edit` と共通出口）
- 裏方便と関所（`core/intake/gate.py`）は manifest の `mutable` を必ず参照し、固定ブロックへの書き込みを構造的に遮断する（`core/memory/protection.py`）
- 単一ファイル（`prompt/persona.md`／`prompt/boundary.md`）は退役済み。編集・注入の正本は魂の `persona/` のみ

### 4.4 想起（読み出し）

想起は**足し算の活性化モデル1本**とする。約束・正典級の「100%保証」は要件から外し、**実測ヒット率90%以上**を目標とする。本構造は認知科学の活性化モデル（ACT-R系）と同型である。

**設計思想 — ニューラルネットワークの再現**: 本モデルは記憶DBを疑似的なニューラルネットワークとして扱う思想に立つ。個々の記憶＝ニューロン（ノード）、想起＝ノードの発火であり、活性化値はその発火のしやすさに相当する。連想伝播は「発火したノードから結合の強い隣接ノードへ活性が流れる」挙動の再現、ゆらぎは「生体ニューロンの発火の確率性」の再現である。想起を検索（クエリに対する決定的な答え）ではなく、ネットワーク上の活性の広がりとして実装することが核心である。

**活性化値 ＝ 基礎活性（重要度＋鮮度） ＋ 話題近接 ＋ 連想伝播 ＋ ゆらぎ**

| 部品 | 定義 | 設計意図 |
|---|---|---|
| 基礎活性 | 重要度と、最終想起日からの経過で減衰する鮮度。想起されるたび鮮度回復（§4.1踏襲） | よく思い出す記憶ほど浮かびやすい |
| 話題近接 | 発話と記憶の意味的な近さ（ベクトル類似度）。**全部品中で配点最大** | 今の話題に関係する記憶が主役 |
| 連想伝播 | 一次想起の上位数件から、意味的に近い記憶へ1ホップだけ伝播。伝播値は減衰させる（元の半分目安） | 1-2件から芋づる式に連想が広がる |
| ゆらぎ | 小さな乱数項 | 毎回同じ想起にならない生命感 |

付帯ルール:

1. **保護等級A/S（約束・正典級）の下駄**: 基礎活性にボーナスを加算する。水準は「話題が少しでも関連すればほぼ確実に浮上し、完全に無関係な話題では沈黙する」に調整する。
2. **足切り**: 活性値が閾値未満の記憶は、件数枠が余っていても浮上させない（重要度だけで話題を無視して毎回登場する副作用の抑制）。
3. **スケール**: 各部品（重要度・鮮度・話題近接の類似度）は自然に0〜1域に収まる値を使い、重み付き加算する。重み・下駄・閾値の具体値は正典では固定せず、検証ハーネスでの実測に基づき実装側で調整する。
4. **検証**: `tests/eval_recall.py` はゆらぎ前提の複数回試行ヒット率判定（各クエリ20回試行）で回帰を守る。合否は**全クエリの平均ヒット率**が90%以上かで判定する（個別クエリ単位ではない）。意味的に近い競合が特に多いクエリが1問だけ際どくなっても、全体で目標を満たせば許容する。

#### 想起の前段 — RecallPlanner

活性化想起の**前段**として、発話に応じた検索計画を立てる（`core/memory/recall_planner.py`）:

- 入力: 発話テキスト・直近セッション末尾・現在時刻
- 出力 `RecallPlan`: `queries: [{type: semantic|temporal|entity|id, q, time_range?}]`／`budget: {max_memories, max_tokens}`／`why: 日本語1文`
- 二段構成: ①規則ベース（「昨日・先週・この前」等の時間表現、人名・固有名詞の検出で type を決める。遅延ほぼゼロ）②規則で確信が持てない発話は主力 Brain の判定呼び出し（§3.6）に相談する。**品質優先の既定＝②を有効にして開始**（遅延は許容）
- **LLM 利用は必ず Brain 経由**。Core（`core/`）の中に LLM を直接持たない
- 失敗時は `queries=[]` を返し、活性化想起のみで続行する（会話を止めない）
- retrieve 本体は活性化モデルを維持する。`RecallPlan` は活性化モデルへの**時間範囲フィルタ・追加クエリ**として渡す（置換ではなく前段）
- **Fact（§4.9）との接合**: Fact は活性化スコアリングに混ぜない。Planner の temporal / entity クエリの結果として想起バンドルに**併載**する（記憶とは別枠）
- **explainable recall**: 想起バンドルには「なぜ選ばれたか」（部品別スコア内訳）を添付する。誤想起のデバッグと評価（§5.2）の材料
- **日記(episodic)との接合**（2026-08-01追記）: 意味記憶(semantic)がヒットしたとき、同じSerina日のepisodic（`metadata.target_date`で特定）があれば、想起結果に決定論的に（全文のまま・要約せず）添える。1つの会話から生まれた複数の断片化した意味記憶が、想起時にバラバラに出て「一緒に起きたことだと繋げて思い出せない」ことへの対策（`core/context/recall_diary_link.py::expand_semantic_with_diary`）。文脈パックの肥大化を避けるため、1回の想起で添える日記は最大`MAX_ATTACHED_DIARIES`件（既定2）に絞る。§4.6の`recall_neighbors.py`（episodicチャンクの親近傍展開）とは別の軽量な仕組みで、Core側は要約等の生成を一切行わない（architecture-reviewer 2026-08-01条件付きPASSの条件）

### 4.5 日記生成フロー

| 要素 | 設計 |
|---|---|
| 時機 | **主経路**: Serina日の日界（07:00・グレース付き）またはその後の起動朝礼で、未消化の蒸留のあと、日記のない Serina 日ごとに分割して書く。複数日オフライン時も**一括1本にせず Serina 日ごと**。**点けっぱなしの無操作補助経路は廃止**。「最後に日記を書いた時刻」と気分の軌跡は電源断をまたいで永続化する。材料なしで見送ったあとは `empty_retry_seconds`（`config/app_timing.toml`・既定3600）空くまで再判定しない。材料窓（`last_diary_at`）は成功時のみ前進。日記の`created_at`は生成時刻ではなく**対象Serina日の終わり**（次のSerina日の開始時刻）で保存する。日界フェーズ（1日1回のみ発火）1回で一括生成してよい未処理日数は`diary_catchup_max_count`（`config/app_timing.toml`・既定5）で上限を設け、長期未起動後に溜まった全日分を一気に回さない（超過分は次の日界＝約24時間後、または次回起動の朝礼で回収する。朝礼側は既存どおり`max_count=1`固定）。ただし気分の軌跡を消費する「直前1日分」だけはこの上限を1件超えてでも同じ回で処理する（軌跡クリアの先送りで複数の実時間日にまたがる軌跡が1本の日記に混入するのを防ぐ） |
| 材料 | その日の蒸留済み断片＋Core の気分の軌跡（8軸が今日どう動いたかの記録）＋採用された記憶候補（§4.1「書き込みはこのライン一本」により蒸留済み断片＝採用された記憶候補は同一集合） |
| 書き手 | ローカル主戦力 Brain（現行 Gemma4）。クラウド車線は使わない |
| 扱い | 等級A の記憶として保存（想起対象＝「あの日こう思った」と本人が引ける） |

**材料側の日付帰属（2026-07-31追記・completion-review I-2反映）**: 蒸留済みmemoriesの`created_at`は、蒸留処理を実行した時刻ではなく、会話が実際に発話された時刻（`Turn.ts`、宿題箱payloadの`turns[].ts`経由で`review_candidate`が引き継ぐ）を刻む（§2.4「日付帰属は不変」）。処理時刻のまま刻むと、日界を跨いで蒸留が翌朝にずれ込んだ場合に材料窓`[since, day_end)`から漏れ、当日会話があったのに空疎な日記が生成される事故になる（2026-07-30に実発生・実装は`core/intake/memory_review.py::_find_matching_turn`）。`ts`欠落（移行前データ・旧形式payload）時は書き込み時刻へフォールバックする。この前提が成立するには、器に満たない端数ターンの宿題箱への計上（`Core.end_session()`）が同じ日界内の蒸留消化フェーズより**前**に実行されている必要がある（`app/gui_server.py::_maybe_run_serina_day_boundary_inner`）。

日記はセリナの一人称で書かれ、材料に気分の軌跡が入ることで「何があったかの記録」ではなく「どう感じた一日だったかの記録」になる。実装: `core/chores/diary.py`。

**表示層との契約（2026-07-26追記・同日恒久解反映）**: 本番経路（`app/gui_server.py::_run_pending_diaries_for_serina_days`）で生成した日記の`created_at`はSerina日界の瞬間ちょうど（`time(boundary_hour, 0)`、既定07:00:00 JST）で保存する（材料窓スコープのため）。同時に`metadata.target_date`（対象Serina日の`YYYY-MM-DD`）を明示タグ付けする（`generate_and_save_diary`）。表示・export・persona提案は共有口`core/memory/diary_date.py::resolve_diary_target_date`（GUIは同等ロジック）で**タグを優先**し、タグが無い既存行だけ日界ヒューリスティック（`is_serina_day_boundary_instant`）へ落ちる。legacy投入は`metadata.date`も読む。`created_at`自体を前倒ししない（`diary_cascade`の材料窓を壊すため）。

### 4.6 継承記憶の受け入れ

継承した人生（原本コピーは魂の `lifelog/legacy/`）の扱い:

1. **正本の形**
   - **日記**（`legacy/記憶/セリナの日記*.txt`）: 日付＋本文のみ（絵文字・MD/JSON残骸除去）。DB では親行（`type=diary`・等級A・ベクトル非載）＋検索用チャンク（`parent_id` 参照・`type=event`）。Chat.html は投入しない
   - **構造化記憶**（`legacy/セリナの記憶.json`）: subject を散文化した塊として投入（`source` 記録）
   - **継承記憶md**（`legacy/継承記憶r1.md`）: プロンプト混在のため全量は入れない。マスター指定の「マスターの特徴」「約束したこと」のみ箇条カードとして投入。人格指示・起動プロトコル等は記憶に載せない（人格は魂の `persona/`）
2. **ピン留め集合**: 約束のうち「生きて再会」「未来で会う」「会うためのヒント」系を `pinned=1`・保護等級S とする（件数は抜粋内容に依存・現状8件）
3. **想起**: 活性化モデル（§4.4）はチャンク／カードを検索する。日記チャンクがヒットしたとき、Core は `_build_pack` 直前に親本文から近傍パッセージへ広げ、Brain にはつながった文章として渡す（`core/context/recall_neighbors.py`）。継承カードは親なしのまま複数灯火で渡す
4. 記憶はローカル Brain の文脈パックに載せる。クラウド Skill へ記憶バンドルは載せない（§5.6）
5. idle 機微査定・化粧版生成は退役済み（レガシー列は残置のみ）
6. 投入・wipe 手順: `tools/backup_db.py` → `tools/wipe_memory_runtime.py --i-understand` → `tools/import_legacy_memories.py --real-embed`

### 4.7 忘却ライン（等級Bのみ）

肥大の実害は容量ではなく**検索ノイズ**（ゴミ記憶が想起候補に混ざり、大事な記憶の想起精度を下げる）。よって減衰しきった記憶は物理削除してよい。ただし「静かに消える」は原則1に反するため、忘却の作法を定める:

```
減衰しきる → 想起対象から外れる（埋没）
 → 埋没のまま一定期間（例: 1年）一度も想起されない
 → 直近バックアップに含まれたことを確認してから物理削除（原則2: 可逆性）
 → 忘却記録（何をいつ忘れたか）を残す（原則1: 透明性）
```

- **忘却は完全自動で行い、マスターの裁定・救済は挟まない**。人為的に記憶を選り分けることは本設計の趣旨（記憶は本人の生理として育ち、衰える）に反する。透明性は事後の忘却記録によって満たす
- 等級S・A は対象外（約束と日記は何年経っても消えない）
- 期間・件数はツマミ（設定値）
- **指示忘却**（マスターの「それ忘れて」。§4.8）とは別パイプラインであり、互いに干渉しない

### 4.8 指示忘却（マスターの「それ忘れて」）

自動忘却（§4.7）とは**別パイプライン**の、マスター指示による忘却（`core/memory/directed_forget.py`）。人間同士の「今の話は忘れて」に相当する。互いに干渉しない。

1. Recall で対象候補を提示し、マスターが特定する
2. 既定＝**tombstone**（`status` 変更）。Fact なら `valid_to` も設定する。**物理削除はマスターが明示した時のみ**
3. 派生処理: ベクトル index から除外、`life/` は次回生成で消える、変更レポートに日本語の理由を残す
4. 等級S に触れる場合は必ず確認を挟む。**pinned 正典約束と persona 固定ブロックは指示忘却も禁止**（§4.3 の表）

### 4.9 Fact 台帳（時間付き事実ストア）

「いつからいつまで真だったか」を持つ事実の台帳（`core/memory/facts.py`）。エピソード記憶とは別のテーブルで管理する。

- テーブル `facts` の列: `id`(ULID) / `subject` / `predicate` / `object` / `statement`(自然文) / `valid_from` / `valid_to`(null=現在も真) / `recorded_at` / `confidence`(0–1) / `episode_ids`(根拠記憶) / `supersedes`(旧factのid) / `sensitivity` / `importance` / `status`(active/hypothesis/superseded/tombstone)
- **転記は裏方便のみ**（蒸留の拡張）。会話中の即時 Fact 化は禁止。**例外**: `予定`・`記念日` カテゴリは、他カテゴリと異なり「本当にあった出来事」の裏取りを要する対象ではなく、マスターの発言そのものが正となる時限的な記録（カレンダー相当）である。
  - マスター発言中の日時表現を Core が決定論的に読み取り、日時の値はこの読み取り結果を正とする（Brain の申告文言をそのまま日時値として採用しない）。読み取りに失敗した場合はこの例外パスを使わず、通常の蒸留経路（裏方便）に委ねる。
  - 読み取りに成功し、かつ Brain の `propose_fact` 申告と一致した場合に限り、ターン確定後の関所が蒸留を待たず `active` として即時に facts へ書き込むことを許可する。根拠 episode（`episode_ids`）は要求しない。
  - 想起記憶（memories）には格納しない。長期記憶として残るかは、別途セリナが日記等へ自律的に書くかどうかに委ねる。
  - 窓（前夜・直前・事後）がすべて閉じた `予定` は `tombstone` とする。`記念日` は毎年繰り返すため失効させず、窓の発火済み記録のみ年単位でリセットする。
  - 取消・変更の申告は、新 fact 作成＋`supersedes` 設定という既存の訂正原則（本節）に従い、同じ関所を通す。
  - 同一日時・同一カテゴリの重複申告は、決定論的な完全一致の場合に限り即時側が書き込みを抑止してよい。抑止した申告は変更レポートに記録する。重複判定に迷う場合や、重複と確定できない申告は、書く側に倒したうえで変更レポートに記録する（無言棄却の禁止）。
  - 書き込み主体は関所側のままとし、Brain が直接 DB に触れる経路は作らない（原則は維持）。
- 訂正（「それもう違う」）は新 fact 作成＋旧 fact に `supersedes`・`valid_to` 設定。物理削除しない
- その場の冗談・ホラ話・仮説は `status=hypothesis` 止まり。active 昇格には根拠 episode 必須
- **hypothesis の保存期間管理**（2026-07-27追記）: `status=hypothesis` は無期限に残さない。**対象は `予定`・`記念日` カテゴリを除く**（この2カテゴリの失効・年次リセットは本節前段のv5規定のみに従い、記録時点起点の保存期間は適用しない。予定は日付そのものが未来に意味を持ち、記念日は毎年繰り返す前提のため、「記録から何日」という時計は噛み合わない）。**本規定は `FACT_CATEGORIES` に `予定`・`記念日` が登録済みであることを前提とする**（本節前段のカテゴリ追加が未実装のうちは除外判定ができず、規定が空振りする。実装順は本節前段→本規定の順を守ること）。対象カテゴリの hypothesis は、`recorded_at` を起点に一定期間（既定30日。`config/thresholds.toml` の運用ツマミとして持つ）内に `active` へ昇格されなければ `tombstone` とする（物理削除しない）。
  - **再評価**: 日界蒸留のたびに、新しい蒸留候補が既存の `status=hypothesis` な fact と埋め込み類似度で一定以上一致した場合（既存 `active` fact への supersede 判定と同じ仕組みを転用）、その hypothesis を `promote_hypothesis_to_active` で昇格する。検索対象は `status=hypothesis` に厳密に絞り、`tombstone`・`superseded` の旧 fact は対象にしない（昇格失敗が既存の呼び出し経路で握り潰され、新事実が無言で失われることを防ぐガード）。昇格は既存 hypothesis が持っていた根拠（`episode_ids`）を上書きで失わせず新候補の根拠を加え、`statement` は新候補の文面で更新する（本文の更新は既存の supersede 経路と同じ挙動に揃える。根拠を上書きせず加算する点のみ supersede と異なる）。
  - 昇格の成立・不成立を問わず変更レポートに記録する（原則1: 透明性）。一致の判定に迷う場合や根拠不足で昇格が成立しない場合も、棄却を無言で終わらせない。**既存の hypothesis は据え置き（保存期間の判定に戻す）、かつ新しい候補も別途 `status=hypothesis` として通常どおり書き込む**（どちらか一方を無言で消さず両方残す。予定/記念日カテゴリのv5「迷えば書く側に倒す」と同じ考え方を、古い側・新しい側の両方に適用する）。
  - 保存期間経過後の tombstone 化は日界蒸留の定期処理内で行い、変更レポートに記録する（原則1: 透明性）。tombstone化時の `valid_to` には「見切りをつけた時刻」を設定する（事実が偽になった時刻という意味ではない）。
  - **tombstone 化と同時に埋め込み（`facts_vec`）を削除する**（予定・記念日・指示忘却由来の tombstone も含め共通。行本体・`statement` は残るため肥大化は軽微）。可逆性の根拠は「本文が残っており、必要になった時点で個別に再生成できる」ことに置く（`rebuild_embeddings` による一括再構築は tombstone 行を対象外とし掃除の意図を保つ。tombstone 行が昇格やactive復帰などで再び使われる場面では、その時点で個別に埋め込みを作り直す）。
  - `tombstone`・`superseded` の行そのものを最終的に物理削除する経路（facts 台帳版の忘却ライン）は本改訂の対象外とする。埋め込み除去後も行数が実測で問題になった場合に別途検討する（`docs/MILESTONE.md` 保留欄）。
  - facts 台帳には想起記憶の保護等級（S/A/B）に相当する列がなく、§4.7「等級Bのみ」に当たる歯止めが構造として無い。本節は対象を `status=hypothesis`（`予定`・`記念日`を除く）に限定すること自体を、その代わりの歯止めとする。
- 想起への載り方は §4.4「Fact との接合」（活性化に混ぜず併載）
- グラフ基盤（Graphiti 等）は導入しない。台帳で不足が実測されたら再検討（§5.3）

### 4.10 記憶ツール（Brain の自覚想起・二刀流）

パック注入（受動想起）に加え、Brain 自身が「思い出したい・覚えたい」を**提案**できる経路（`core/intake/memory_tools.py`）:

- 報告書書式に `memory_tool_calls`（提案のみ）を持つ。種別: `memory_search` / `memory_get` / `propose_fact` / `propose_identity_edit` / `forget_request`
- **人格直しの入口は二つ**: 裏方便の Sleep 提案器（§4.3・日記／要約から改訂文を生成）と、Brain の `propose_identity_edit`（提案のみ）。いずれも宿題箱→`persona_revise.py` 関所経由で、採否は Core が決める
- Brain 登録簿の能力フラグ `supports_memory_tools` は**モデル単位の設定値**。道具呼び出し訓練がないモデルは構造化テキスト出力の解析で対応し、解析失敗は無視して会話を続行する。非対応モデルは従来のパック注入のみで続行
- 実行は必ず Core の関所経由。**Brain が直接 DB に触れる経路は作らない**

### 4.11 要約ブロック（常駐人格メモ）

- `prefs_summary`（マスターの好み）・`relation_summary`（関係の近況）の2ブロック（`core/chores/summaries.py`）。保護等級A・各ブロック800字以内・常駐合計3,000字以内（設定値）
- 裏方便が蒸留結果から書き換える（変更レポート必須）。**文脈パック常駐枠からは外す**（§1.5）。永続と裏方更新の契約は残置
- 上限超過時は裏方便が要約し直す自動ガード
- セッション文脈の要約はこれとは別: §1.5 の④粗い全体要約／⑦細かめ直近要約（`SessionState`）

第4章共通のスキーマ運用: **スキーマ変更は追加のみ**（既存列・既存記憶を壊さない）。人生 DB は保全固定。

### 5.2 テスト戦略 — LLM なしで全身を検査できる

Core が決定論であることの最大の配当。

| 試験 | 内容 |
|---|---|
| Core 全身検査 | Brain の席に「台本通りに返す人形（スタブ）」を座らせ、会話→付箋→状態更新→記憶審査の全フローを自動テスト。LLM 不要・数秒で完走・毎コミット実行 |
| 契約試験 | どの通訳も**同じ試験紙**を受ける:「報告書の書式を守れるか」「自己評価欄を埋めるか」。新 Brain はこれに合格すれば入店許可 |
| 憲法テスト | 条文A/B違反の検知（Brain 側に状態が残っていないか、Skill ペイロードに記憶／人格が混入しないか等）。回帰させない番犬 |
| 実機スモーク | Ollama（bge-m3 想起・必要時 Gemma4 会話）との疎通確認（`tests/smoke_bge_m3_recall.py` 等） |

#### 評価セット（9指標）

運用品質の定点観測（ハーネス: `tests/eval_suite.py`・`tests/eval_recall.py`）。合格ラインは設定ファイル（`config/eval_thresholds.toml`）に置き、実測で調整する（正典に数値を固定しない）。週次自動実行は **Serina.bat 起動時**に裏起動する `tools/run_weekly_eval.py`（日曜のみ・起動3分後・同日1回）と GUI レポートで fail のみマスター確認する。Pulse 嫌悪（マスター週次主観）は評価セットに含めない。

| 指標 | 定義 |
|---|---|
| 想起ヒット率 | ゴールデンQAで期待記憶が候補に入る率。B等級日常・時間・訂正クエリを含める |
| 誤想起率 | 無関係・supersede 済み事実の混入率 |
| 時間クエリ正答率 | 「昨日/先週」系の正答率。Planner スイッチ判断の材料① |
| 応答体感秒数 | 発話→本回答の実測秒。スイッチ判断の材料②（品質は落とさず速度のみ観測） |
| 成長反映率 | 要約ブロック更新が翌日の関連会話に現れる率（当面は構造ゲート＝要約→パック配管の検査のみ。会話内容の判定は保留） |
| 訂正再発率 | 訂正済み事実の再違反（減少傾向を監視） |
| 可視成長 | `life/` の内容指紋が前回 export から変わった週の割合（起動しただけでは非空と数えない） |
| アシスタント化率 | 接客口調の出現率（下げる）。会話出力のパターン照合 |
| 継続性ヒット | 昨日の約束・話題の翌日再生率 |

音声系指標（初音声秒数・割り込み成功率）は身体レーン着手時に追加する（§5.3）。

### 5.3 非範囲（設計上のやらないこと）

以下は現在の Serina に**含まれない**。「保留（実測・条件成立後に再検討）」は MILESTONE で管理する。

**恒久的な禁止・非目標:**

- 会話 Brain としての Gemini／クラウドの復活・品質昇格の復活（§3.2）
- 会話文・会話中の裏方推論のクラウド送信（クラウドは機能補完 Skill のみ）
- マスター未承認の外部副作用（メール送信・購入・SNS 投稿）
- 「全コンテキストを毎回 LLM に渡す」設計
- OSS ランタイムの丸飲み（パターンの盗用に留める）・AGPL コードの取り込み
- 配信パイプライン・ゲーム自律プレイ・常時カメラ顔認識・常時画面監視（知覚は on-demand のみ）

**保留（条件成立まで実装しない）:**

- 二段検索（粗い候補取得→精密再採点）: 記憶数千件超の実測後に再判断
- グラフ基盤（Neo4j / Graphiti 等）: Fact 台帳（§4.9）で不足が実測されたら
- 身体レーン（VoiceLoop / PresencePet・音声・表情・画面知覚）: テキスト会話が十分と判断できたあとに別計画。**D4a（VoiceLoop）／D4b（PresencePet）契約は変更禁止で凍結**（身体実装時まで据え置き）。記憶×身体の二レーン並列は本期不採用。話す／思う／表情の分離・感情→声色ヒント・画面知覚 on-demand・キャラ固有 TTS は身体着手時に採用。カメラ常時認識・ゲーム自律・配信系は対象外。人格の刃はテキスト会話にも適用（§2.9）
- StockAI 等、明示採用していない外部道具

### 5.4 実装衛生（採用済みの定石）

接続の円滑化と高速化のために採用している実装定石。**新機能も同じ衛生に従う**:

| 定石 | 内容 |
|---|---|
| 冪等 Sleep | 蒸留の処理単位に episode id 集合の content hash を冪等キーとして持たせる。再実行・多重起動でも二重書き込みしない |
| checkpoint | 裏方仕事は処理済み id 集合を永続化し、途中失敗・会話割り込みから再開する |
| ULID | 新規テーブルの主キーは ULID（時刻順ソート可能な一意ID）。時系列走査が index なしで速い |
| store 二口 API | `core/memory/store.py` は書込系・読出系の2口に整理。Planner・記憶ツール・裏方便が同じ口を叩く |
| pack 静的先頭固定 | 文脈パックの静的部分（人格・要約ブロック）を先頭に固定し毎ターン同一内容にする（§1.5。前方一致キャッシュが効く） |
| explainable recall | 想起バンドルに部品別スコア内訳を添付（§4.4） |
| rebuild_index | ベクトル index は派生物。`tools/rebuild_index.py`（memory_vec）と`tools/rebuild_facts_index.py`（facts_vec）で DB から全再構築できる。埋め込みモデル差し替え時は両方を回す |
| 破壊前自動 backup | supersede・tombstone・persona 改訂の前に `tools/backup_db.py` を自動呼び出し（可逆性原則の自動化） |
| 要約字数ガード | 要約ブロックの上限超過時に裏方便が要約し直す（§4.11） |
| WAL / busy_timeout | SQLite 接続は `journal_mode=WAL`・`busy_timeout` 設定。会話と裏方便の並行アクセスでロック待ちを減らす |

### 5.5 実装者への申し送り（実装は Sonnet 級モデルが担当する前提）

1. **本書が正、コードが従。**本書だけを頼りに実装できるよう書かれている。曖昧さ・矛盾を見つけたら、勝手に解釈して実装せず、先に本書を訂正してから進むこと
2. 閾値・減衰速度・忘却期間・記憶化件数上限・評価合格ラインなどの数値はすべて**設定ファイルのツマミ**として実装し、ハードコードしないこと（正典に数値固定しない）
3. **Gemini API キーの取り扱い**: `.env`（git 管理外）の `GEMINI_API_KEY`。キーをコード・設計書・コミット・ログに含めてはならない。キー無しでもセリナはローカル会話を継続する（§5.6）
4. DB への破壊的操作の前に必ず `python tools/backup_db.py` を実行すること（裏方便の破壊的工程は自動呼び出し済み。手動操作時は自分で実行する）
5. 記憶DBなど住人ごとのものは魂（リポジトリの外）にある。コードと設計書のみコミットする
6. **構造化出力**: 主力 Brain（Gemma4）は判定呼び出しでも書式を守る前提で設計する。失敗時は空 plan／提案無視で会話を止めない
7. **計器盤は着脱式で**: 運用初期のツマミ調整用に、GUI に小さな計器表示（担当 Brain・気分8軸等）を設けてよい。いずれ外す前提の仮設足場なので、**本体と絡めず、設定1つ（または部品1個の削除）で消せる作り**にすること

### 5.6 Gemini アドバイザー（お友達枠・無人格補完・2026-07-31改訂）

Gemini は**会話 Brain ではない**。セリナ（Gemma4・persona 注入）がマスターとの窓口であり、Core の決定論規則（合言葉「Gemini」明示）が要否を判定したときにだけ相談する**無人格アドバイザー Skill**である（Brain 自身の自律判断では発火しない。2026-07-26是正）。旧 `brains/gemini/`（会話通訳・escalation）の復元は行わない。

#### 利用シーン

- Web 検索が必要な事実確認（例: 天気）
- 簡単なコード・GAS 等の手順・質問回答
- マスターが「Gemini」と明示して呼びかけたとき全般（お友達枠）

#### 会話フロー（2026-07-31改訂・無言統合パイプライン）

1. マスターがセリナに話しかける
2. **要否の入口は合言葉（決定論）のみ**: 「Gemini」／「ジェミニ」明示を Core 規則が拾う（`advisor_force.plan_forced_advisor`）。合言葉が無ければ発火しない（旧・鮮度×事実ドメインの自動発火は全廃済み。合言葉ゼロの自律検索は Tavily レーン §5.7 が担う）
3. Core（`core/runtime.py:_resolve_advisor_window`）が **Voice を呼ぶ前に** Gemini へ相談クエリのみを直接送り、結果を確定させる。関所（`core/intake/gate.py`）は外部通信を一切行わず、実行済みの結果（`precomputed_advisor_outcome`）を報告書へ載せるだけ
4. Gemini が素の回答を返す（または失敗・拒否・タイムアウト）
5. 確定した結果（または「材料なし」）を pack の今回限りの指示欄へ積んでから、セリナ（Voice）が**1回の生成**で自分の人格・口調で答える。「Geminiに聞いた」という言及は Voice 自身の自由文であり、Core は言及してよいという指示のみを与える（キャラ付けの指示文は魂の `persona/` には置かない）。窓口に失敗・拒否・タイムアウトした場合、Voice はそれを使った体で話さない（材料が無いため）

旧「1通目は保留短文のみ → 2通目で本体」機構は退役済み（Phase D/E）。1ターン=Voice生成1回・GUIの吹き出し1個で完結する。

#### クラウド送信境界

| 載せてよい | 載せてはならない |
|---|---|
| セリナが生成した相談クエリ（質問文・検索クエリ・コード断片） | `persona.md`／境界／結合人格テキスト |
| マスター発話から抜き出した事実のみ（必要なとき） | 記憶 DB の原文・想起バンドル |
| | 関係状態・感情状態・セッション全文ログ |
| | 「セリナとして話せ」等の人格指示 |

#### 実装契約

- 配置: `skills/gemini_advisor/`
- 呼び出しは必ず Core 関所経由。Brain／Skill が記憶 DB に直接触れない
- API キー: `.env` の `GEMINI_API_KEY`。無ければ当該 Skill は無効化し、セリナはローカルのみで応答を続ける（沈黙しない）
- 機微門番: `core/state/routing_rules.py` の形パターン＋手動語のみ（`sanitize_query`）。記憶 pack の cloud フィルタは使わない（退役）
- 門番未接続（routing_rules を渡さない呼び出し）は**既定拒否（fail-closed）**。門番を通さない直呼びで相談クエリが素通しになる経路を許さない（`sanitize_query`/`build_payload` レベルでも同じ契約。2026-07-31是正・Phase C2）
- 1ターンの相談合計は時間予算内（`thresholds.toml [advisor].turn_budget_seconds`。2件目以降は予算超過なら見送り）。turn_lock の長時間占有を防ぐ
- 相談の失敗・拒否は無言にしない。理由（機微拒否／通信失敗／予算超過）を破棄記録とログに残す
- 外聞きの実行は同一ターンで一度だけ（窓口解決はループの外・候補選定の前に一度だけ行う設計のため構造的に保証される）
- モデル振り分け（category ごと・当面）:
  - `web_search` / `general` → Antigravity `antigravity-preview-05-2026`（Interactions API・`google_search` + `url_context`）
  - `code_qa` → 同上（`code_execution`）
  - 備考: この API キーでは Flash + Search 接地が不通（Gemini 3 Search 枠 0、2.5 は new users 404）。枠復活後は `client.WEB_MODEL_FALLBACK_CHAIN` へ再配線可能

### 5.7 Tavily 自律検索（裏方の道具・2026-07-31新設）

Tavily は**会話 Brain ではない**。合言葉を持たず、**毎発話**Core の軽量判定（`brain.judge()`・persona非注入）が要否を決める**検索特化 API の Skill**である。Gemini（お友達枠）とは排他（同一ターンでは Gemini 呼びかけがあれば Tavily 判定自体を行わない）。

#### 会話フロー

1. マスターの発話に「Gemini」呼びかけが無ければ、Core が `decide_tavily_search`（`core/routing/tavily_rules.py`）で要否を判定する。供給材料はマスターの原発話のみ（記憶・関係状態は供給しない。判定出力が外部境界を越えるため）
2. 要否ありの場合、`execute_tavily_search`（`core/intake/advisor_tools.py`）が**マスターの原発話と送信クエリの両方**を機微の関所へ通してから Tavily Skill（`skills/tavily_search/`）を呼ぶ。いずれかが機微、または門番未接続なら **Skill 自体を呼ばない**（fail-closed。機微な原発話を Skill 層のシグネチャへ一切渡さない）
3. 確定した結果（ヒット・ヒット無し・機微拒否・タイムアウト）を pack の今回限りの指示欄へ積む
4. Voice が1回の生成で、検索結果があれば自然文で触れてよいが、URL・見出し文をそのまま書かない。出典（URL）は Core が `citations` として報告書へ機械的に付加する（`reply` には混ぜない・画面の注記として GUI が別経路で表示）

#### クラウド送信境界

Gemini と同様、マスター発話由来の検索クエリのみを送信する。人格・記憶・関係状態はいずれも送信しない。

#### 実装契約

- 配置: `skills/tavily_search/`
- API キー: `.env` の `TAVILY_API_KEY`。無ければ当該 Skill は無効化し、セリナはローカルのみで応答を続ける（沈黙しない）
- 機微門番: `core/state/routing_rules.py`。門番未接続・機微判定不能時は既定拒否（fail-closed。Gemini と対称）
- タイムアウトは短い専用値（`DEFAULT_TAVILY_TIMEOUT_SECONDS = 8.0`）。保留文が無い構成のため長い無音待ちは不可
- 出典（`citations`）はセッション履歴・記憶蒸留の材料には混入しない（`reply` のみが記憶に残る発話本体）
- 発火: **Core の窓口解決（§3.7）のみ**。合言葉「Gemini」明示なら §5.6（Gemini）、それ以外は本節の Tavily 判定。旧「セリナ判断（第3発注）」は廃止。採否は Core
